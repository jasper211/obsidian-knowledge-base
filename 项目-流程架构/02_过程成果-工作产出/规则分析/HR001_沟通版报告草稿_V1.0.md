我们对 HR 域涉及的 **30 张数据表** 做了一次系统性"体检"——不是看数据对不对，而是看**谁负责、规则写没写下来、出了问题谁来修、有没有只有一个人知道怎么做的事**。体检下来发现了 **29 个规则空白**，按紧迫程度分三档。下一步是通过访谈把这些规则说出来、记下来，建立共同标准。

## 板块2：数据链全景

HR 数据从员工信息录入，经过薪资、考勤、绩效、奖金各条链路，最终汇聚成财务层的人工成本聚合表。

```
【段0 · 基础配置层】
  全公司快码字典（dim_lookup_code）← 所有枚举值的来源，全域消费
  职级维度（dim_position_grade）← 员工当前职级的标准参照
  岗位归一映射（config_position_alias）← 原始岗位名→标准岗位名的转换表
  评分→奖金系数表（config_score_coefficient）← ★待实施，绩效奖金计算的关键参数
  薪酬带宽维度（dim_salary_band）← ★新建待实施，外部顾问数据来源，更新机制未定义
  岗位×职级桥接表（bridge_position_grade）← ★新建待实施，一个岗位可对应多个职级

【段1 · 员工基础链】
  HR-001/002 → 员工维度（dim_employee，23字段，含6个PII字段）
            → 组织维度（dim_organization）
            → 岗位维度（dim_position，★v2.3已瘦身）
            → 员工月度快照（fact_emp_monthly）← 人员数据的核心源头
            → 员工异动事件（fact_employee_events）
            → 一致性校验表（consistency_check）← 事件与快照交叉校验

【段2 · 薪资链】
  HR-004 → 月度薪资主表（fact_salary_monthly，25字段）← ★财务结算核心
        → 个税明细（fact_salary_tax_detail，16字段）
  HR-007 → 月度社保公积金（fact_social_insurance_monthly，26字段）← ★合规核心
  参数输入：薪资项维度（dim_salary_component，6字段，C1全命中）
           保险类型维度（dim_insurance_type，5字段，C1全命中）

【段3 · 考勤链】
  HR-003 → 月度考勤事实表（fact_attendance_monthly，53字段）← 字段最多
           含HK/深圳双城市年假余额，跨城市规则差异未文档化

【段4 · 绩效奖金链】
  HR-005 → 绩效评估事实表（fact_performance_eval，15字段）
        → 评分→奖金系数表（★待实施，是整条链的断点）
  HR-006 → 部门绩效包维度（dim_bonus_pool）
        → 绩效奖金核算（fact_bonus_calculation，20字段）← ★财务结算核心

【段5 · 聚合层】
  fact_emp_monthly + fact_salary_monthly + fact_social_insurance_monthly
  → 人工成本月度聚合表（AGG_labor_cost_monthly，25字段）← 财务部门源头数据
    ★ 含用户决策字段（includes_outsource/includes_consultant），每次聚合口径可能不同
```

## 板块3：集群风险

**本次发现集群风险：HRD 同时是全部 30 张表 386 个字段的名义 Owner（治理集中风险）**

数据字典显示，30张表中 362 个字段的 Data Owner 均为 HRD（HR Director），仅 24 个字段归属 BizD。

但实际数据分工如下：
- 事实表和桥接表由 **IT数据团队** 执行 ETL 维护
- 维度表由 **HR业务方** 录入维护
- 快码字典由 **数据治理** 负责

这意味着：**Owner 标注（HRD）与实际执行维护方在多个表上存在不一致**（C4信号命中 35 个字段）。当数据出现问题时，责任归属不清晰。

| 典型问题 | 表名 | 说明 |
|---|---|---|
| Owner=HRD但由ETL生成 | fact_emp_monthly | snapshot_key / ETL计算字段挂名HRD |
| Owner=HRD但由IT维护 | fact_attendance_monthly | etl_load_date / data_quality_flag等 |
| Owner=HRD但外部数据来源 | dim_salary_band | 薪资区间来自外部顾问，HRD未必能核查准确性 |
| Owner=BizD但与HR域交界 | dim_segmentation / dim_ka | 业务细分和KA维度由BizD维护，HR域消费时依赖方不明确 |

**通俗比喻**：HRD 相当于在所有账本上都签了"负责人"的名字，但很多账本实际上是 IT 团队在记、业务方在填、外部顾问在提供数据——名义负责人和实际维护人不是同一批人，出了问题会陷入互相推诿。

## 板块4：P0规则空白（8条，立即处理）

### P0-001：薪资核算口径没有写下来，contract_region跨表依赖规则不明
**技术描述**：`fact_salary_monthly` 薪资各细项计算口径无文档，`contract_region` 字段来源依赖 `dim_employee` 而非 HR-004，跨表依赖规则未定义
**访谈岗位**：HR薪资经理
**通俗说法**：月度薪资表是财务结算的核心依据，但"基本工资怎么算、津贴包含哪些项、绩效按什么口径发"从来没有写成文档。更特殊的是，确定员工适用哪套薪资标准的关键字段（合同地域），不是从薪资系统直接来的，而是去员工档案表里取的——如果员工档案和薪资系统的地域信息不一致，没有人知道该用哪个。

### P0-002：绩效奖金系数链有断点，关键配置表还没建
**技术描述**：`fact_bonus_calculation` 的奖金系数依赖 `config_score_coefficient`，但后者为待实施状态（Phase 3），配置表不存在则奖金系数无法查表
**访谈岗位**：HR绩效经理
**通俗说法**：绩效奖金的计算流程是：评分 → 查系数表 → 算出奖金。但"系数表"这张表还没建好——相当于餐厅的菜单还没印出来，就要开始结账了。hire_adjustment（入离职调整）和probation_adjustment（试用期调整）的计算规则也没有写成文档。

### P0-003：人工成本聚合表的口径每次可能不一样，没有版本记录
**技术描述**：`AGG_labor_cost_monthly` 含用户决策字段 `includes_outsource`/`includes_consultant`，每次聚合是否含外包/顾问人员由人工决定，无版本溯源；触发条件和授权主体均未定义
**访谈岗位**：HR数据负责人
**通俗说法**：这张表是财务部门看人工成本的"总账"。但每个月的总账到底算不算外包人员、算不算顾问，是有人临时决定的——而且这个决定没有记录在任何地方。这意味着财务可能在拿两份口径不同的数字做比较，但没有人意识到它们是不同口径算出来的。

### P0-004：薪资项维度全部字段人工定义，只有一个人知道，没有审批流程
**技术描述**：`dim_salary_component` 全部6字段 C1 全命中，无变更审批流程，SPOF集中
**访谈岗位**：HR薪资经理
**通俗说法**：薪资项表（dim_salary_component）定义了哪些收入算应税、哪些算入社保基数——这直接影响每个员工的税和社保。但这张表的所有内容都是人工定义的，改动没有任何审批流程，也没有人知道历史上改过什么。谁有权新增一个薪资项？新增了会不会影响税务合规？都没有规定。

### P0-005：绩效评分→奖金系数的转换规则，触发机制和版本控制都没有
**技术描述**：`config_score_coefficient` 全部3字段人工定义，更新频率=按需，触发条件和版本控制均未定义，表为待实施状态
**访谈岗位**：HR绩效经理
**通俗说法**："评分60分对应奖金系数0.8、评分90分对应系数1.0"——这套转换规则是手工录入的，何时改、谁来改、改之前要不要审批、改了之后已经算好的奖金要不要重算，全都没有定义。而且这张表还没正式建好。

### P0-006：薪酬带宽表是新建的，外部顾问数据如何更新完全不知道
**技术描述**：`dim_salary_band` 为 v2.3 新建表，薪资区间上下限来自外部顾问（C1信号），更新机制、频率、录入流程均未定义
**访谈岗位**：HR薪酬负责人
**通俗说法**：公司要新建一张"每个职级应该拿多少钱"的参照表，数据来自外部薪酬顾问。但顾问的数据多久更新一次？谁来录入？如果顾问换了怎么办？新增一个职级×岗位族组合时谁来填表？这些都没有定义。

### P0-007：社保公积金计算规则随政策变化，但更新机制没有文档
**技术描述**：`fact_social_insurance_monthly` 26字段，深圳社保各分项（pension/medical/unemployment等）计算口径随政策调整，变更时无文档化流程
**访谈岗位**：HR社保专员
**通俗说法**：社保和公积金的缴纳比例每隔一段时间会随政策调整，深圳和香港的规则也不一样。但"政策变了，谁来更新系统里的计算基数、更新后历史月份要不要补算"——这套处理流程从来没有写下来。如果社保专员换人，新人不会知道该怎么处理。

### P0-008：岗位×职级桥接表是新建的，多职级匹配规则和失活机制都未定义
**技术描述**：`bridge_position_grade` 为 v2.3 新建桥接表，N:1关系（一个岗位对应多个职级）处理规则未定义，`is_default`/`is_active` 字段的业务逻辑未知
**访谈岗位**：HR岗位治理负责人
**通俗说法**：公司新建了一张"这个岗位允许什么职级的人担任"的配置表——一个岗位可能允许P5、P6、P7三个职级。但如果一个员工的实际职级在允许范围之外，系统怎么处理？"默认职级"（is_default）由谁来设？一个职级配置失效后（is_active=0），历史上已经按这个配置发过的薪资怎么追溯？都没有定义。
