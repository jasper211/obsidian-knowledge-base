## 二、Step 2：交付物四标签分析

---

### 交付物1 · 《源头佣金录入表》（原始Excel）

**交付物定位**：EFA域核心手工产出，是佣金数据的源头输入。目前下游（财务/结算/测算）主要依赖此表，因为新脚本表尚未被下游接受。

#### A · 交付物类型规则风险

- **交付物类型**：人工录入类交付物
- **类型规则风险**：手工从PDF/Excel提取信息天然存在看错、看错格式、理解偏差的风险；不同保司PDF格式差异大导致提取规则无法标准化
- **核心规则信号**：
  - 不同保司PDF格式差异（永明最难：每个产品表头形式不同；太平洋最简单：表头固定从未变过）
  - 保司格式会季度性变化（永明、监管后多家保司换格式）
  - 无OCR/结构化提取，纯人工录入
  - 录入错误类型：数字看错（0.34 vs 0.43）、PI/PPI区分遗漏、有效期写错（2026→120）

#### B · 交付物责任与执行断点

- **责任模式**：刘敏然单人录入 → 自己double检查 → **自填自审🔴**
  - 以前有小溪参与录入和交叉检查，小溪离职后未交接给其他人
  - 部门缺人，目前只有刘敏然一人执行
  - 未来计划招B角交叉检验，但尚未到位
- **执行断点**：
  - 录入和检查为同一人，无独立复核
  - 下游财务/结算仅"看"表，不做录入准确性复核
  - 市场佣金人员（MOMO兼）可能发现数字异常，但这是事后发现
- **字段级补充**：⛔（无Carrie数据表，字段信息待确认）

#### C · 交付物流转验证断点

- **验证链位置**：保司PDF/Excel → **手工录入** → 《源头佣金录入表》→ 下游财务/结算/测算
- **断点类型**：
  - **交接断点**：录入完成后无独立签收/复核节点，直接传递至下游
  - **触发缺失**：保司格式变化无预警机制，被动应对
- **验证盲区**：
  - 录入错误何时被发现？刘敏然确认：只要自己没发现，下一个发现的人是"做市场佣金的人"（目前MOMO兼）或结算人员——但发现时已在下游环节，纠正成本高
  - 尊享五事件：保司口头通知管理层变更加佣，信息未传递至录入环节，导致按旧费率执行数月

#### D · 交付物授权级别

- **授权级别**：🔴 **高**（直接影响佣金计算准确性和财务结算金额）
- **裁定责任人**：刘敏然 / 财务负责人
- **匹配性**：❌ **不匹配**（高授权交付物采用自填自审模式，无独立复核链）

**综合优先级：P0**（B=🔴自填自审/单点责任 + D=🔴高授权 + ❌复核机制完全缺失）

### 交付物2 · 《佣金准入表》（脚本输出）

**交付物定位**：EFA域系统化替代方案，由Carrie脚本从数据库自动生成。理论上未来将替代原始Excel表，但目前处于未成熟状态，与旧轨道并行。

#### A · 交付物类型规则风险

- **交付物类型**：系统自动生成+人工校验类交付物
- **类型规则风险**：脚本逻辑不透明、变更无版本控制、边界情况未覆盖
- **核心规则信号**：
  - 脚本修改由刘敏然提需求、Carrie执行，回归测试范围不明确
  - 同一个产品两条费率有效期重叠时，系统**不会报错**，可能"两个都写"
  - 新字段添加（如是否预缴、是否融资单）需要工程师改脚本，存在时间延迟
  - 脚本聚合逻辑（源头佣金宽表从commission plan聚合）由业务定义表头，工程师提取

#### B · 交付物责任与执行断点

- **责任模式**：Carrie脚本开发 / 刘敏然业务校验 → **交接模糊🟡**
  - 脚本出问题谁负责？技术问题还是业务需求描述问题？
  - 脚本修改流程：刘敏然提需求 → Carrie改脚本 → 刘敏然手工校对验证
  - 验证仅靠刘敏然手工比对旧Excel和脚本输出，无独立测试人员
- **执行断点**：
  - 新脚本尚未"最终确认可宣发"，但已在部分场景使用
  - 财务/结算看不懂新版本，未做用户验收
- **字段级补充**：⛔（待Carrie数据表交叉验证）

#### C · 交付物流转验证断点

- **验证链位置**：数据库 → **脚本生成** → 刘敏然校验 → 下游聚合/财务
- **断点类型**：
  - **触发缺失**：脚本升级后无自动预警机制；新脚本未确认最终版就投入部分使用
  - **验证盲区**：脚本输出与业务预期是否一致？仅靠刘敏然个人手工抽查（她说"会检查全部"，但范围是自己定义的）
  - 有效期写错等脚本层面的问题，被发现具有偶然性（Carrie偶然打开表才发现）

#### D · 交付物授权级别

- **授权级别**：🔴 **高**（财务结算的基础数据来源，理论上的权威数据源）
- **裁定责任人**：Carrie（技术）/ 刘敏然（业务）/ 财务负责人
- **匹配性**：❌ **不匹配**（高授权交付物的脚本稳定性未经验证，无正式UAT流程）

**综合优先级：P1**（B=🟡交接模糊 + D=🔴高授权 + ❌回归测试/UAT缺失）

> **注意**：本交付物单独看是P1，但结合交付物1的双轨并行现状，两表不一致的风险实际更高。P0-001已覆盖"自填自审"核心风险，本交付物的脚本风险在P1-001中处理。

### 交付物3 · 《佣金计算公式文档》

**交付物定位**：EFA域知识沉淀载体，记录各保司各牌照的佣金计算方式。是新人交接和脚本开发的重要输入。

#### A · 交付物类型规则风险

- **交付物类型**：规则文档/知识库类交付物
- **类型规则风险**：文档与实际计算逻辑不同步，导致脚本实现错误或新人学习偏差
- **核心规则信号**：
  - 公式变更靠刘敏然手动维护文档
  - 脚本实现由Carrie基于需求开发，文档→脚本的传递无自动同步
  - 复杂保司（永明）计算公式涉及PI/PPI区分、档位倒推、额外加佣方式，理解门槛高

#### B · 交付物责任与执行断点

- **责任模式**：刘敏然单人维护 → **单点责任🔴**
  - 只有刘敏然掌握各保司计算逻辑的完整知识
  - 复杂保司（永明）上手需1.5-2个月，说明知识转移效率低
  - 交接方式：录音+现场举例，无书面SOP
- **执行断点**：
  - 文档改了，脚本是否同步改？无明确流程
  - 脚本改了（工程师调整），文档是否同步更新？无明确流程
- **字段级补充**：⛔

#### C · 交付物流转验证断点

- **验证链位置**：保司原始文件 → **公式文档** → 脚本实现 / 新人学习
- **断点类型**：**交接断点**——文档到脚本实现之间无自动比对机制，靠人工传递需求
- **验证盲区**：
  - 脚本实现与文档是否一致？目前无自动校验
  - 新人按文档操作是否能得出正确结果？缺乏标准化测试案例

#### D · 交付物授权级别

- **授权级别**：🟡 **中**（影响计算正确性，但不直接决定结算金额）
- **裁定责任人**：刘敏然
- **匹配性**：🟡 **部分匹配**（文档存在但维护方式为人工，无版本控制）

**综合优先级：P1**（B=🔴单点责任 + D=🟡中 + ❌版本控制/同步机制缺失）

**交付物定位**：EFA域下游服务产出。原始Excel表只有RA档（真实佣金），脚本表有RA-D档。测算/市场佣金调整需要其他档位时，由刘敏然按需提取提供。

#### A · 交付物类型规则风险

- **类型规则风险**：提取规则不明确，下游可能误用或理解偏差
- **核心规则信号**：
  - 永明有RA-D六个档位，倒推逻辑复杂（需从total值倒推每年佣金）
  - 不同下游需要不同档位，需求无标准化记录
  - 提取后MOMO会做市场佣金调整，调整依据不透明

#### B · 交付物责任与执行断点

- **责任模式**：刘敏然按需提取 → **自填自审🔴**
  - 谁需要什么档位、什么时候需要、以什么格式提供，无标准流程
  - 提取过程无记录、无审批
  - 若刘敏然不在，其他人不知如何提取
- **执行断点**：
  - MOMO/测算要数据时直接找刘敏然，无统一入口
  - 永明档位倒推最复杂，是知识密集环节

- **验证链位置**：脚本表/原始表 → **刘敏然提取** → MOMO/测算
- **断点类型**：**交接断点**——提取后无确认机制，MOMO调整依据不透明
- **验证盲区**：
  - 提取的数据是否准确？永明档位倒推无独立校验
  - MOMO调整后的市场佣金表与源头数据的关系无追溯

#### D · 交付物授权级别

- **授权级别**：🟡 **中**（影响市场佣金外发，但不直接决定结算金额）

- **匹配性**：❌ **不匹配**（提取标准缺失，授权边界模糊）

**综合优先级：P1**（B=🔴自填自审 + D=🟡中 + ❌提取标准缺失）
