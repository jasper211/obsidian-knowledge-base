## 一、V0.3核心变更说明

### 变更1：报告生成链路合并（Teresa建议，采纳并修正）

**Teresa的建议**：B3/B4/B5/B7应该是一个Agent。

**我的判断**：Teresa的方向正确，但B7需要单独保留。

| | Teresa建议 | V0.3采纳方案 | 理由 |
|--|-----------|------------|------|
| B3岗位匹配 | 合并 | ✅ 合并入B-RPT | 用户不感知中间步骤，属内部Sub-function |
| B4架构分析 | 合并 | ✅ 合并入B-RPT | 同上 |
| B5报告生成 | 合并 | ✅ 合并入B-RPT | 同上 |
| B7报告交互 | 合并 | ❌ 保留为B-INT | 触发时机不同（追问是独立多轮对话，非一次性管道） |

**合并逻辑**：B3→B4→B5是一次性的串行管道，用户输入岗位名称，输出报告，中间步骤对用户不可见。合并为B-RPT后，内部仍保留三个Sub-function，对外是一个统一接口，降低编排复杂度，同时保持内部可测试、可替换。

**B7保留独立的理由**：B-INT（原B7）是多轮对话能力，用户看完报告后可以追问"这个岗位和B族的协同是什么"，这与初次生成报告的触发时机和状态管理完全不同，合并会造成逻辑混乱和故障传导。

---

### 变更2：新增B-GRP 企业全局报告Agent

**背景**：Teresa的数据字典和FACT_CARD数据模型的最终目的，不只是生成单个岗位报告，而是支撑一份**企业全局架构分析报告**——跨价值流、跨岗位族、跨战略层级的全景视图。这需要一个专门的Agent。

## 三、B-RPT 岗位报告生成Agent（V0.3合并重设计）

### 定位
**用户面向的报告生成入口。** 接收自然语言输入，端到端输出完整的岗位分析报告，内部包含三个Sub-function。

### 内部Sub-function设计

```
用户输入："保司交付这个岗位的全景分析"
                    ↓
        ┌──── B-RPT 岗位报告生成Agent ────┐
        │                                  │
        │  Sub-1：岗位识别                  │
        │  （原B3逻辑）                     │
        │  自然语言 → {job_family:'A',      │
        │              vs:'VS-1'}           │
        │            ↓                     │
        │  Sub-2：数据组装                  │
        │  （原B4逻辑）                     │
        │  查询L1-L5 + VS + Agent评分       │
        │  + confirmation_status可信度标注  │
        │            ↓                     │
        │  Sub-3：报告渲染                  │
        │  （原B5逻辑）                     │
        │  填充TMPL_岗位分析报告_V1模板      │
        │  输出结构化JSON                   │
        └──────────────────────────────────┘
                    ↓
            Teresa交互界面渲染
```

### 输入/输出规范

**输入**：
- 岗位名称（如"保司交付"）
- 或工作场景描述（如"负责保司合同谈判的人需要了解什么"）

**输出**：结构化报告JSON，对应`TMPL_岗位分析报告_V1.md`全部章节：
- M0-M8战略涉及点
- L1归属价值链
- L2业务能力
- L3协同关系+RACI
- L4活动+Agent化程度
- L5日常任务
- 价值流归属
- KPI与绩效
- 工作标准与规则
- 数据可信度标注（来自A0的confirmation_status）

### Skill规划

| Skill编号 | Skill名称 | 对应原Skill |
|----------|---------|-----------|
| B-RPT-S01 | 自然语言岗位识别 | 原A2-S01 |

## 四、B-GRP 企业全局报告Agent（V0.3新增）

### 定位
**管理层视角的企业全景报告生成器。** 基于Teresa的FACT_CARD星型数据模型，跨所有价值流、所有岗位族、所有战略层级，生成一份完整的企业架构全局分析报告。

### 与B-RPT的本质区别

| 维度 | B-RPT 岗位报告 | B-GRP 全局报告 |
|------|-------------|-------------|
| 视角 | 单岗位/单场景 | 全企业/全架构 |
| 触发者 | 岗位员工/HR/部门负责人 | Mark/管理层 |
| 数据范围 | 1个岗位族的相关数据 | 全部5条VS + 7族 + M0-M8 + 全部KPI |
| 输出长度 | 单岗位报告（约10-20页） | 企业全景报告（约50-100页） |
| 频率 | 按需随时生成 | 定期（月度/季度）或里程碑触发 |
| 依赖数据 | dim_job_family + fact_activity | FACT_CARD全表 + 所有DIM表 |

### 全局报告的章节结构

```
企业架构全局报告
│
├── 第一部分：企业价值链全景（L1层）
│   └── 5条价值流的运转状态 + Agent化覆盖率
│
├── 第二部分：各价值流深度分析（L3层）
│   └── 每条VS的流程健康度 + RACI覆盖 + SLA达标率
│
├── 第三部分：岗位族架构分析（组织层）
│   └── 7族的编制现状 + KPI达成 + Mark减负状态
│
├── 第四部分：Agent化进展（技术层）
│   └── Auto/Aug/Hybrid/Human分布 + M4建设优先级
│
├── 第五部分：KPI穿透分析（经营层）
│   └── 企业KPI → L3流程 → 岗位 的三层穿透
│
└── 第六部分：战略对齐分析（M0-M8层）
    └── 各战略层级的流程覆盖度 + 缺口识别
```

### 数据依赖

B-GRP直接依赖Teresa的完整数据架构：

| 报告章节 | 依赖的数据表 | Teresa数据字典对应 |
|---------|-----------|----------------|
| 价值链全景 | FACT_CARD + DIM_VS | DV系列字段 |
| 流程健康度 | FACT_CARD + DIM_PROCESS | DP系列字段（SLA/rework/error） |
| 岗位族分析 | DIM_ORG + FACT_CARD | DO系列字段 |
| Agent化进展 | DIM_AGENT + FACT_CARD | DA系列字段 |
| KPI穿透 | DIM_KPI + FACT_CARD | DK系列字段（Week 6后） |
| 战略对齐 | DIM_M_STRATEGY + FACT_CARD | DS系列字段 |

B-GRP是所有Agent中依赖数据最重的，启动需要满足：

- ✅ FACT_CARD有至少3个月的运行数据

## 八、Agent协作模式（V0.2保留）

**整体：Plan-and-Solve**（任务链路已知，先规划再执行）
**局部：Multi-Agent**（B-RPT处理A族的同时，可并行处理B族报告请求）

各Agent推荐协作模式：

| Agent | 推荐模式 | 理由 |
|-------|---------|------|
| A0 | Toolformer | 有明确的数据字典校验规则，工具调用密集 |
| A1 | ReAct + Toolformer | 遇到意外编号格式需动态推理 |
| B-RPT | Plan-and-Solve内部串行 | Sub-1→2→3路径固定 |
| B-GRP | Plan-and-Solve | 聚合顺序固定，先查哪张DIM表都是确定的 |
| B-INT | ReAct | 追问内容未知，需动态推理 |
| B8 | Toolformer | 写回逻辑固定，不需要复杂推理 |

## 九、Teresa数据字典对架构的强化作用（V0.2保留）

数据字典V1直接强化三个层面：

**强化A0**：字段校验规则（L3格式正则、枚举值约束）直接作为A0-S02的执行标准。

**强化A1**：字段来源状态（✅/⚠️/❌）直接告诉A1优先修复哪些字段，标注❌的等Teresa确认再处理。

**强化B-GRP**：数据字典定义了FACT_CARD全部37个度量字段（SLA/rework/efficiency_score等），B-GRP的全局报告章节和计算公式直接基于这些字段设计，不需要另起炉灶。
