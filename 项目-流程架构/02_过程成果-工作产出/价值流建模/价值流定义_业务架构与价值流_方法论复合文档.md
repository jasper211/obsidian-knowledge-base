# 价值流与价值链方法论纠偏

> 文档类型: 方法论纠偏 / 强制性执行规范
> 产生日期: 2026-04-11
> 触发原因: L3正向映射过程中发现"价值体系/价值流/价值阶段"层级命名错误与概念混淆
> 权威来源: TOGAF Series Guide - Value Streams / BIZBOK v10 / Michael Porter (1985) / SAFe Framework
> 适用范围: 所有业务架构文档、L1-L5流程规划、价值流CSV、组织方案

## 一、问题陈述

现有架构将"价值体系""价值流""价值阶段"混用，且存在整体命名矮一层、将内部运营能力错标为价值流的系统性错误。这些错误会直接导致：
1. L3流程错归属（基于假的利益相关者）
2. 组织方案错设计（基于错的价值交付逻辑）
3. 人机协作错对齐（AI按错的价值流推导活动）

本文件为**强制执行的纠偏规范**，所有涉及价值流/价值链概念的文档必须遵守。

## 二、权威定义

### 2.1 价值链 Value Chain

**来源**: Michael Porter (1985) / BIZBOK v10

**定义**: 企业将自身分解为战略相关活动的结构化描述，用于理解成本行为和差异化来源。

**核心属性**:
- **数量**: 企业只有 **1条** 价值链（"An organization has ONE and only one value chain" — BIZBOK）
- **视角**: **内部** — "我们怎么运作、怎么竞争"
- **粒度**: 宏观/战略级
- **度量**: 成本结构、利润率、差异化
- **结构**: 主要活动 + 支撑活动

**在本项目中的对应**: L1飞轮模型（L1-01~05）

---

### 2.2 价值流 Value Stream

**来源**: TOGAF Series Guide / BIZBOK v10

**定义**: 一个外部利益相关者从触发到获得完整价值的端到端活动序列。

**核心属性**:
- **数量**: 企业有 **多条** 价值流（每个外部利益相关者一条）
- **视角**: **外部** — "利益相关者怎么获得价值"
- **触发者**: 必须是**外部**利益相关者（**不能是内部团队**）
- **粒度**: 横切式的端到端流动
- **度量**: 时间、质量、体验
- **结构**: 价值流 → 价值阶段(Stage) → 价值活动(Activity)

**判定规则** (3条必须全部满足):
1. **外部利益相关者**：触发者必须是企业外部的角色（客户、合作伙伴、供应商等），内部部门不算
2. **端到端**：从利益相关者的触发事件到获得最终价值，不是中间片段
3. **可独立交付**：有明确的进入条件和退出条件，不依赖其他价值流的并行执行

**在本项目中的对应**: 5条业务线价值流（见第四节）

---

### 2.3 业务能力 Business Capability

**来源**: TOGAF / BIZBOK

**定义**: 企业为实现特定结果而拥有的稳定能力。

**核心属性**:
- 稳定、抽象、去流程化
- 回答"我们能做什么"，不是"我们怎么做"
- 是价值流阶段的**使能器**

**在本项目中的对应**: L2一级业务能力（18个）

---

### 2.4 业务流程 Business Process

**定义**: 实现业务能力的具体、可执行的跨部门流程。

**在本项目中的对应**: L3端到端流程

### 2.5 三者关系 (BIZBOK标准)

```
价值流阶段 Value Stage
     │
     │ enabled by (使能)
     ▼
业务能力 L2 Capability
     │
     │ realized by (实现)
     ▼
业务流程 L3 Process
     │
     │ decomposed into
     ▼
L4模块 → L5经营活动 → L6 SOP
```

## 三、禁止词与纠正词

### 3.1 禁止使用的词

| 禁止词 | 禁止原因 | 替代词 |
|--------|---------|--------|
| **价值体系** | BIZBOK/TOGAF中不存在此概念，是本项目自创的伪构件 | 使用"价值流" |
| **价值流**（指传统18条） | 层级错位，这些实际是价值阶段 | 降级为"价值阶段" |
| **价值阶段**（指传统70个） | 层级错位，这些实际是价值活动 | 降级为"价值活动" |
| **SMPS作为价值流** | SMPS的利益相关者是"支撑组织"=内部，违反外部性原则 | 归入L1-02的内部能力分解 |
| **MDF作为价值流** | MDF的利益相关者是"业务中台"=内部，违反外部性原则 | 归入L1-03的内部能力分解 |

### 3.2 正确的层级命名

| 正确命名 | 定义 | 本项目数量 |
|---------|------|-----------|
| **价值链** Value Chain | 企业唯一的内部战略活动分解 | 1条(L1飞轮) |
| **价值流** Value Stream | 外部利益相关者的端到端旅程 | 5条 |
| **价值阶段** Value Stage | 价值流中的逻辑里程碑 | 每条6~10个 |
| **价值活动** Value Activity | 价值阶段中直接创造价值的原子单元 | 每个阶段3~7个 |

## 四、本项目的正确框架

### 4.1 唯一的价值链 (L1飞轮)

```
L1-01 资源获取与产品整合    (MCV战略与方案赋能)
       ↓
L1-02 市场设计与合作伙伴发展 (销售网络与市场深耕)
       ↓
L1-03 运营反馈与路由决策    (决策中枢)
       ↓(策略优化闭环 → L1-01)
       ↓(能力优化闭环 → L1-04)
L1-04 能力赋能与增长驱动    
       ↓
L1-05 价值增值与生态绑定    
       ↓(体验反馈闭环 → L1-03)
```

**4个正反馈闭环** (来自"价值破局"战略文档):
1. 资源精准反馈闭环: L1-03 → L1-01
2. 市场需求反馈闭环: L1-03 → L1-02
3. 代理人能力提升闭环: L1-03 → L1-04
4. 客户体验反馈闭环: L1-05 → L1-03

**S2B2A商业模式映射**:

```
保司 (Insurer)
    │
    ▼
S = 平台/中台 (本公司)
    │
    ├──► TOB机构 (经代/家办)  ┐
    │                        │
    ├──► KA/TOA (个人IP)     ├──► A = 理财师 ──► C = 终端客户
    │                        │
    └──► 直营代理人          ┘
```

**5条价值流**:

| 编号 | 价值流名称 | 利益相关者 | S2B2A层 | 现有素材 |
|------|-----------|-----------|---------|---------|

| **VS-2** | 机构合作伙伴旅程 | TOB机构（经代/家办） | B层 | 原经代上架价值流 + PACE联合运营 + BMC系列 |

## 五、强制执行规则

### 规则1: 外部性检验 (Stakeholder Externality Test)

创建或修改任何价值流时，必须通过以下检验：

```
问题1: 利益相关者是谁？
  └─ 答案必须是企业外部角色（客户/合作伙伴/供应商/保司）
  └─ 如果答案是"中台""支撑组织""业务部门" → 不是价值流，是内部能力链

问题2: 这条旅程的触发事件是什么？
  └─ 必须由外部利益相关者发起
  └─ 如果由内部战略/KPI驱动 → 不是价值流

问题3: 最终交付物是什么？
  └─ 必须是外部利益相关者"收到"的价值
  └─ 如果交付物是给内部团队 → 不是价值流
```

### 规则2: 端到端完整性检验

```
问题1: 有独立的进入条件吗？
  └─ 必须有明确的触发事件（外部信号/合同/请求）

问题2: 有独立的退出条件吗？
  └─ 必须有明确的终止状态（协议签署/交付完成/周期结束）

问题3: 能独立交付完整价值吗？
  └─ 不能是另一条价值流的中间片段
  └─ 不能依赖与其他价值流的并行执行
```

### 规则3: 唯一性检验 (价值链)

```
问题: 企业描述了几条"价值链"？
  └─ 必须且只能是1条
  └─ 如果出现多条"价值链" → 它们实际是价值链的不同活动（组件），应合并为1条
```

### 规则5: L4唯一物理价值交付物原则 (2026-04-11 M2 G3-5 Mark裁定)

**强制规则**:
> 任何L4切分必须挂一个**唯一的物理价值交付物**(single physical deliverable)。
> 一个L4 = 一个交付物 = 一个A责任人 = 一段可独立完成的流程。

#### 什么是"物理价值交付物"
是一个**可被他人接收、审计、引用**的具体产物,例如:
- 一份文档/报告(《市场洞察报告》/《合规尽调报告》)
- 一个数据表/数据集(《佣金计算结果表》/《机构对接清单》)
- 一个系统记录(合同生效/权限配置/账户开通)
- 一个签字文件(签约合同/决议书)
- 一个正式凭证(税务申报表/到账确认)

**不是物理交付物的**:
- "完成某动作"("完成沟通"、"做好培训") — 没有物
- "状态变化"("就绪"、"已启动") — 没有物的凭证
- "服务动作组合"(营销+销售+培训三件事) — 多个物,应拆分

#### 判定checklist (建立L4时必须回答)
1. [ ] 这个L4完成后,**产出什么物理对象**? (文档/数据/系统记录/签字文件/凭证)
2. [ ] 这个物理对象是**唯一的**还是**多个**? 如果多个,是否应该拆分?
3. [ ] 这个物理对象能否**独立交付给下游**(下游L4/L3或外部利益相关者)?
4. [ ] 这个物理对象是否有**明确的responsible person (A)** 负责产出?
5. [ ] 这个物理对象是否**可度量/可审计**(完成/未完成有客观判据)?

5项全[x]才能建立一个L4。任何一项为[ ],必须拆分或合并。

#### 违反示例

❌ **L4-IBE-MKT 营销执行与品牌支持** (错误)
- 输出: "营销活动执行报告 + 线索数据 + ROI分析" (3个物)
- 问题: 混合了执行、数据、分析三类独立交付
- 修正: 拆分为:
  - L4-IBE-MKT-01 营销方案制定 → 《营销方案书》
  - L4-IBE-MKT-02 营销活动执行 → 《活动执行报告》
  - L4-IBE-MKT-03 营销ROI分析 → 《营销ROI报告》

✅ **L4-BME-01 运营方案框架设计** (正确)
- 输出: 《联合运营框架方案》(唯一)
- 主责: 赵琦/经代联合运营组 (A)
- 独立交付给: L4-BME-02(服务事项设计)

#### 为什么这个规则重要

1. **端到端可度量**: 每个L4有明确产出,可以判断"完成/未完成"
2. **RACI清晰**: 一个交付物一个A责任人,避免多责任方真空
3. **流程可追溯**: 交付物就是流程的物理证据,可审计
4. **符合BIZBOK**: Value Stage → Capability → Process 每层都应有明确产出
5. **AI组织化前提**: AI自动化需要明确的输入/输出边界,"唯一物理交付物"是最好的边界

#### 执行要求

- **M2 G3-5之后建立的所有L4必须100%遵守**
- **M2 G3-5之前建立的L4必须回溯review并修正**(已列入修正清单)
- **validate_kb.py 扩展新检查**: `l4_unique_deliverable` — 每个L4必须有deliverable字段且非空
- **L3-definition-schema.yaml 新增**: L4必填 deliverable (string, 唯一)

## 六点五、横切能力（Cross-cutting Capability）

**概念引入（D-04架构修正补充，2026-04-11）**

### 定义

横切能力 = 由中台统一管理的、**跨多条价值流被消费**的业务能力集合。它不是独立价值流（因为没有独立的外部利益相关者旅程），也不是单一价值流的专属能力（因为多个VS都会调用它）。

### 识别规则

一个能力被识别为"横切能力"需满足：
1. **组织归属中台**：由统一团队管理，不分散在各业务线
2. **跨VS消费**：≥2条价值流的价值阶段会调用该能力
3. **产品线可能多套**：对不同受益方可能有独立产品线（例如权益对机构/理财师/客户有3套）
4. **独立治理**：有自己的L3流程、KPI、RACI

### 本公司的横切能力

**L1-05 权益中台能力层**（权益团队统一管理）

| 能力 | 服务对象 | 代表L3 |
|------|---------|--------|
| 权益产品管理 | 三套产品线(机构/理财师/客户) | L3-RSD-RW, L3-RPD, L3-SSD, L3-SLM, L3-SLCM, L3-EO |
| 权益供应链管理 | 统一8服务商 | L3-SOB, L3-ISD, L3-SPO, L3-SPD, L3-SDS |
| 权益效果评估与迭代 | 跨三套数据跟踪 | L3-DTVA, L3-SSVA, L3-CFRM |
| 权益需求诊断 | 跨通道共性 | L3-SRA |

**分发通道（非L3，只是消费方式）**:
- 机构权益 → VS-2 S4 "权益体系构建"
- 理财师权益 → VS-4 S6 "晋升裂变与权益兑现"
- 客户权益 → VS-5 S3-S7 "服务激活/交付/结算"

### 与价值流的区别

| 维度 | 价值流(VS) | 横切能力(L1-05) |
|------|-----------|----------------|
| 视角 | 外部利益相关者的端到端旅程 | 内部中台能力的集合 |
| 触发者 | 外部 | 各VS的价值阶段 |
| 是否独立 | 是 | 否(被消费) |
| 组织归属 | 对应业务线 | 中台 |
| L3数量 | 5~10条/VS | 10+条/能力层 |

### 常见误区

❌ **错误1**: 把权益命名为"VS-5 客户权益服务旅程" → 锁定客户侧，忽略机构和理财师权益
✅ **正确**: VS-5 = "终端客户服务旅程"，权益是其中**一种价值载体**，还可能有保单/客诉/续约等

❌ **错误2**: 为每套权益产品线建独立VS（机构权益VS / 理财师权益VS / 客户权益VS）
✅ **正确**: 权益是L1-05能力层，不是VS。VS是利益相关者的旅程，机构的旅程是VS-2（包含权益+其他），不单独为权益建VS

❌ **错误3**: 权益L3归属各VS
✅ **正确**: 权益产品管理/供应链/效果评估的L3归L1-05（中台），只有**真正客户侧特有**的L3（如L3-CDA客户需求诊断）归VS-5

## 七、为什么此前会产生错误

追溯历史成因（避免重犯）：

1. **中文翻译不一致**: "Value Stream"有人译"价值流"有人译"价值链"，团队内术语不统一
2. **企业级抽象冲动**: 试图把所有业务归纳为5大"价值体系"，但BIZBOK的价值流本来就应该有多条
3. **内部视角默认化**: 运营团队天然从内部视角写文档，把内部流程误认为价值流
4. **TOGAF读取不完整**: 只读了"Value Stream"章节，没有同时读取"Value Chain"和"Capability"的关系章节
5. **缺少外部性检验**: 没有强制规则要求"利益相关者必须外部"

# L3流程合理性评估 — 基于价值流→价值链方法论

> 评估日期: 2026-04-11
> 方法论: TOGAF价值流→价值链→L3端到端流程映射
> 数据源: 企业整体价值流(5体系/20条价值流/70+价值阶段) + 飞轮模型(5条L1/18个L2) + L3注册表(55条)

## 一、方法论回顾

按照你们的架构设计_01.pdf和流程工作框架V1.0，正确的推导链是：

```
利益相关者 → 价值流(外部视角，客户获取价值的过程)
         → 价值链/L1(内部视角，企业自身经营的核心链条)
         → L2 业务能力(稳定的能力抽象)
         → L3 端到端业务流程(跨部门的完整业务流程)
         → L4 流程模块 → L5 经营活动
```

关键原则：
- **价值流≠L1**：价值流是外部利益相关者获取价值的过程；L1是企业内部的价值链
- **L3必须端到端**：L3是跨部门的完整业务流程，有明确的外部触发端和交付端
- **L3归属L1**：每个L3必须能映射到某个L1价值链环节

## 五、关键判断点（需Mark裁定）

### 判断1：KA线和经代线是否合并L3？
- **合并派**：两条线做的是同一件事（获取→评估→签约→上架→运营），按能力组织而非按渠道组织，CLAUDE_V2的D4-4.2要求32-34个L3，合并后正好落在区间内
- **分离派**：KA是转介模式(BD→产品经理→CSM)，经代是合作伙伴模式(业务线负责人→交付经理→产品经理)，业务逻辑差异大，强行合并会丢失细节
- **建议**：**按能力合并L3，按渠道分L4**。L3定义"做什么"，L4区分"对谁做"

### 判断2：PROC系列8条是否过度拆分？
- 当前8条PROC每条3-5个L5活动，粒度明显偏细
- 端到端分析报告已判定PROC系列中至少3条为"流程片段"(Fragment)
- **建议**：合并为3-4条语义化L3

### 判断3：佣金COM系列归属哪个L1？

# RACI冲突裁定方案

> **编制日期**: 2026-04-11
> **编制人**: Claude (基于validate_kb.py检测结果 + 跨文件交叉分析)
> **裁定人**: Mark (待裁定)
> **状态**: 待Mark评审

---

## 背景

validate_kb.py 检测到 13 处 RACI 冲突，分布于三张矩阵。经逐条交叉比对协同框架、岗位方案(KA管理/RW协同多业务线版)及L3编码注册表，实际可归纳为 **13 处冲突**，按根因分为三类：

| 类型 | 数量 | 根因 |
|------|------|------|
| 多A (R/A合写导致) | 5 | KA矩阵将R与A合并写为"R/A"，导致同一行出现2个含A的角色 |
| 无A/无R (CSV结构性) | 4 | 权益矩阵前3行为多级表头，被误读为数据行；另有1行真实冲突 |
| 跨文件不一致 | 4 | RACI矩阵、协同框架、岗位方案三者对同一流程的主责定义互相矛盾 |

---

## 裁定原则

| 编号 | 原则 | 来源 |
|------|------|------|
| P1 | 每个L3有且仅有1个A (Accountable) | TOGAF RACI规范 |
| P2 | R与A可以是同一人，但必须显式拆分标注 | TOGAF RACI规范 |
| P3 | 路算分离 — 前台负责客户路由与交付，中台负责专业能力与标准 | CLAUDE_V2 L0原则④ |
| P4 | 单点失效消除 — 避免单一角色在全链条上都是A | CLAUDE_V2 L0原则⑧ |
| P5 | 岗位方案(RW协同版)为组织设计权威源，RACI矩阵必须与之对齐 | EA知识库治理规则 |

## 第一部分：KA矩阵 — 5处"多A"冲突

### 冲突 #01 | L3-KAEC 获取KA资源

- **当前状态**:
  - KA RACI矩阵: BD = R/A（含A），其余角色均为"-"
  - 岗位方案(RW版): 主责岗位 = BD
  - 协同框架: BD为全流程主责(R)，无单独A角色定义
- **冲突类型**: 多A (R/A合写，实质为1人同时R和A，技术误报)
- **建议方案**:
  - BD = **R** (执行市场开拓与线索挖掘)
  - BD = **A** (对线索质量和数量负最终责任)
  - 即: BD 同时承担 R 和 A，矩阵中标注为 **R,A** (用逗号分隔，不用斜杠)
- **建议理由**: BD岗位说明书明确"核心使命：开拓市场，精准识别并引入高价值KA客户"。此流程为BD的核心独立职责，R和A归同一人符合业务实际。仅需修正CSV格式写法。(引用: KA岗位方案-BD岗位, 原则P2)

### 冲突 #02 | L3-KAET KA评估定级

  - 协同框架: KN2明确"交付经理（召集与汇报，R）、中台（风控与规则，**A**）"
  - L3编码注册表备注: "RACI冲突:框架→交付经理 vs 矩阵→BD"
- **冲突类型**: 多A + 跨文件不一致 (矩阵说BD是A，协同框架说中台是A)
- **建议方案**:
  - BD = **R** (执行尽职调查、准备评估材料)
  - 交付经理 = **R** (主持跨部门评估会议、深度信息收集)
  - 总部/中台 = **A** (对评估定级决策的合规性和准确性负最终责任)
  - CSM = C
- **建议理由**: 评估定级是"裁定"行为，涉及风控与合规判断。按原则P3(路算分离)，前台(BD/交付)负责信息收集和汇报(R)，中台负责规则裁定(A)。协同框架KN2已明确"中台(风控与规则，A)"，应以此为准。矩阵中BD标注为R/A不正确，A应归中台。(引用: 协同框架KN2, 原则P3路算分离)

## 二、对肉身的负担重新评估

### 原(错误)的human-centric理解
- 253条L4 = 253个人工任务 → **管理灾难**

### 修正后的AI组织化理解
- **253条L4 = 253个专精agent岗位**
  - 80个完全自主agent (Auto)
  - 91个半自主agent (Aug, 人审批关键点)
  - 52个辅助agent (Hybrid, 人主导,agent支持)
  - 30个需要人的L4 (Human)

- **一个人的"肉身负担"**:
  - 必须亲自做: ~30条 (Human)
  - 审批/拍板: ~91条 (Aug 的关键节点)
  - 与agent协同: ~52条 (Hybrid)
  - 完全放心给agent: ~80条 (Auto)
  - **实际肉身介入**: 30 + 91×30% + 52×60% ≈ **88条核心介入点**

**结论**: 一个人实际只需要深度关注**~88条**,不是253条。这在"肉身+agent"模式下**完全可持续**。

# L4 Agent化评估框架

> 产出日期: 2026-04-11 M2收尾
> 触发: Mark指出L4爆炸在AI组织化语境下不是问题,是好事
> 目的: 为每个L4评估其agent化潜力,为M4 AI组织化提供落地清单
> 权威: CLAUDE.md新规则(待写入)

---

## 一、核心假设 (Mark的AI组织化愿景)

1. 未来工作模式 = **肉身 + N个专精Agent**
2. L4颗粒度越细 → Agent专精度越高 → 交付质量越高
3. L4密度不是管理负担,是AI组织化的基础设施
4. 不同L4的agent化潜力不同,需要分级规划

---

## 二、6维评估框架

每个L4按以下6个维度评分(0~3分,满分18):

### 维度1: 输入结构化程度 (Input Structurability)
- **0分**: 完全非结构化(自由文本/口头沟通/无法解析)
- **1分**: 半结构化(需大量NLP解析)
- **2分**: 结构化但复杂(多源异构)
- **3分**: 完全结构化(JSON/API/数据库)

### 维度2: 决策规则清晰度 (Decision Rule Clarity)
- **0分**: 纯主观判断(经验/直觉/创意)
- **1分**: 经验主导+少量规则
- **2分**: 规则为主+边缘case需人工
- **3分**: 完全规则可编码(决策树/公式/算法)

### 维度3: 输出可验证性 (Output Verifiability)
- **0分**: 主观输出(无对错)
- **1分**: 可间接评估(事后观察)
- **2分**: 可直接度量但有误差
- **3分**: 精确可验证(正确/错误二元)

### 维度4: 外部依赖可API化 (External API Accessibility)
- **0分**: 依赖面对面/纸面/人际关系
- **1分**: 部分系统但多数人工
- **2分**: 大部分有API但未打通
- **3分**: 完全API化(含内部系统+外部第三方)

### 维度5: 失败降级可用性 (Fallback Availability)
- **0分**: 无fallback(失败直接卡住)
- **1分**: 有人工fallback但成本高
- **2分**: 有降级方案但需人启动
- **3分**: 有明确的自动降级路径

### 维度6: 合规约束可编码 (Compliance Codability)
- **0分**: 纯人工判断(监管灰区)
- **1分**: 大部分规则需人工
- **2分**: 规则明确但需定期更新
- **3分**: 规则稳定可编码(已有标准化条文)

---

## 三、分级规则

| 总分 | 分级 | 含义 | M4落地优先级 |
|------|------|------|--------------|
| **15~18** | **A-Auto** | 可完全Agent化,人只需监督 | **P0** — M4先建 |
| **10~14** | **A-Aug** | Agent主导+人审批关键节点 | P1 — M4同步建 |
| **5~9** | **A-Hybrid** | 人主导+Agent辅助(数据/提醒) | P2 — M4建辅助 |
| **0~4** | **A-Human** | 必须人工,Agent几乎无能为力 | 保持人工 |

---

## 四、分级特征速查

### 🟢 A-Auto 特征
- 数据流转/规则计算/报告生成
- 输入输出高度结构化
- 规则明确可编码
- 合规约束可嵌入
- **例子**: 佣金计算/异常检测/数据看板/监控报告/元数据录入

### 🟡 A-Aug 特征
- Agent起草/分析,人审批定稿
- 涉及跨部门协调但规则明确
- 数据类决策支撑,但关键处人拍板
- **例子**: 续约方案起草/合同审查/ROI分析/培训设计

### 🟠 A-Hybrid 特征
- 人做判断和创意,Agent提供数据和工具
- 涉及关系/谈判/沟通
- 规则弱,经验强
- **例子**: 保司关系维护/机构诊断/客户陪访/团队管理

### 🔴 A-Human 特征
- 战略决策/情感沟通/创意产出/危机应对
- 高合规风险需人签字
- 无法结构化的判断
- **例子**: Mark裁定/晋升仪式/心理疏导/重大谈判/危机公关

---

## 五、Agent设计原则 (供M4参考)

基于L4评估,每个L4级agent应有以下标准字段:

```yaml
agent_id: L4-编号
name: L4名称
tier: auto/aug/hybrid/human
inputs:
  - name: 输入1
    type: structured/semi/unstructured
    source: API/数据库/人工
outputs:
  - deliverable: 物理交付物名称
    format: 格式
    verification: 验证方式
decision_rules:
  - rule: 规则1
    condition: 条件
    action: 动作
fallback:
  - trigger: 触发条件
    action: 降级动作
compliance:
  - constraint: 约束1
    source: 监管来源
human_handoff:
  - trigger: 何时交给人
    role: 哪个角色
```
