## 问题 1：与标准 L3-L4 审计表不一致（4 行额外数据）

### 1.1 问题描述

交付物表（V5）比审计表多出 **4 行**，均来自 v5 重映射过程中 BMD（非标准 L3）向标准 L3 的迁移：

| L4编码 | 所属L3 | L4名称 | 来源 | 审计表状态 |
|--------|--------|--------|------|------------|
| L4-UCR-03 | L3-UCR | 机构风险偏好综合评估 | 原L3-BMD L4-04 | ❌ 不存在 |
| L4-URD-03 | L3-URD | 初步商机规模预测 | 原L3-BMD L4-05 | ❌ 不存在 |
| L4-URD-04 | L3-URD | 机构战略匹配度评估 | 原L3-BMD L4-02 | ❌ 不存在 |
| L4-URD-05 | L3-URD | 联合运营需求诊断 | 原L3-BMD L4-06 | ❌ 不存在 |

### 1.2 根因分析

**v5 重映射规则导致**：

```
BMD 7 行 → URD/UCR 映射结果：
├─ URD-01 (业务现状调研与分析): 接收 BMD L4-01, L4-02, L4-06 → 3 个源映射到 1 个目标
│   保留: BMD L4-01（相似度最高）
│   冲突新增: BMD L4-02 → URD-04, BMD L4-06 → URD-05
│
├─ URD-02 (需求初筛): 接收 BMD L4-03 → 直接替换，无冲突
│
├─ URD-03 (新增目标): 接收 BMD L4-05 → 审计表无此编码，新增
│
├─ UCR-01 (合同条款深度映射): 接收 BMD L4-04, L4-07 → 2 个源映射到 1 个目标
│   保留: BMD L4-07（相似度最高）
│   冲突新增: BMD L4-04 → UCR-03
│
└─ UCR-02 (设计约束条件生成): 审计表原有，未被 BMD 映射到
```

**审计表现状 vs V5 现状**：

| L3 | 审计表 L4 数 | V5 L4 数 | 差异 |
|----|-------------|----------|------|
| L3-URD | 2 (URD-01/02) | 5 (URD-01/02/03/04/05) | +3 |
| L3-UCR | 2 (UCR-01/02) | 3 (UCR-01/02/03) | +1 |

### 1.3 影响评估

| 维度 | 影响 |
|------|------|
| **数据一致性** | 交付物表与审计表不一致， downstream 依赖审计表的系统（如 DIM_PROCESS 数据库）可能出现编码缺失错误 |
| **业务完整性** | 这 4 个 L4 对应的交付物（风险偏好评估、商机规模预测、战略匹配度、需求诊断）均为 BMD 原始数据，业务上可能是真实需要的活动 |
| **编码连续性** | URD-03/04/05、UCR-03 的编码顺延规则符合标准，不会导致编码冲突 |

### 1.4 修正方案（三选一）

#### 方案 A：同步更新审计表（推荐）

**前提**：业务确认这 4 个 L4 是真实需要的活动。

**操作**：
1. 将 URD-03/04/05、UCR-03 追加到 `L3_L4完整性审计表_v4.csv`
2. 同步更新 `DIM_PROCESS` 数据库中的 L3-L4 维度表
3. 在审计表中补充这 4 个 L4 的完整属性（L4名称、L4定义、上下游关系等）

**优点**：保持交付物表与审计表完全一致，数据链路完整。

#### 方案 B：V5 表中标记为"待确认"

**前提**：暂不确定业务是否需要这 4 个 L4。

**操作**：
1. 在 V5 表的 `migration_note` 中追加标记：`[待确认：审计表未收录]`
2. 保留数据但不做 downstream 同步
3. 待业务确认后再决定是否更新审计表

**优点**：保守策略，不破坏现有审计表结构。

#### 方案 C：从 V5 中删除这 4 行

**前提**：业务确认这 4 个 L4 不需要。

**操作**：
1. 删除 V5 中 URD-03/04/05、UCR-03 共 4 行
2. 将 BMD L4-02/04/05/06 的 4 行数据标记为"未映射"或在日志中记录为"丢弃"
3. V5 行数从 400 降至 396

**风险**：可能丢失 Mark 原始 Agent 评分数据（BMD L4-02/04/05/06 共 4 行），影响数据完整性。

### 1.5 建议

> **推荐方案 A**，理由：
> 1. BMD 数据来自 Mark 的 Agent 评分文档，具有业务权威性，不应随意丢弃
> 2. 重映射时这 4 个 L4 的命名和编码规则均符合标准，不存在规范性问题
> 3. 保持交付物表与审计表一致是数据治理的基本原则

## 问题 2：MD 文档数据溯源统计错误

### 2.1 问题描述

MD 文档的"数据来源构成"表与用户实际统计存在差异：

| 来源 | MD 声称 | 用户实际统计 | 差异 |
|------|---------|-------------|------|
| Agent评分(Mark) | 250 (62.5%) | **223 (55.8%)** | ❌ 少 27 行 |
| 语义推导 | 109 (27.3%) | **177 (44.3%)** | ❌ 多 68 行 |
| 价值节点(Phase2) | 35 (8.8%) | 35 | ✅ 一致 |
| 迁移 | 3 (0.8%) | 3 | ✅ 一致 |
| 价值节点(手动映射) | 2 (0.5%) | 2 | ✅ 一致 |
| 迁移+修正 | 1 (0.3%) | 1 | ✅ 一致 |

### 2.2 根因分析

**MD 文档混用了两个不同的"来源"字段**：

| 字段名 | 含义 | 实际数据 |
|--------|------|----------|
| `交付物来源` | 核心**交付物名称**的来源 | Agent评分 250 / 语义推导 109 / ... |
| `Agent评分来源` | **Tier/D1-D6 评分**的来源 | Agent评分 223 / 语义推导 177 |

MD 文档声称的"数据来源"实际引用的是 `交付物来源` 列，但用户核对的是 `Agent评分来源` 列，两者统计口径不同。

**两个维度的交叉关系**：

```
                    Agent评分来源
                    Agent评分    语义推导
交付物来源
Agent评分           223          27
价值节点(Phase2)      0          35
价值节点(手动映射)      0           2
语义推导              0         109
迁移                  0           3
迁移+修正             0           1
```

**关键发现**：
- 有 **27 行**的交付物来自 Mark（`交付物来源=Agent评分`），但评分是后来语义推导补的（`Agent评分来源=语义推导`）
- 这意味着 Mark 的原始文档中有 27 个 L4 只提供了交付物名称，没有提供完整的 6 维度评分

### 2.3 修正状态

MD 文档已修正，将原来的单表拆分为**双维度说明**：

1. **维度 A：交付物来源**（核心交付物本身的来源）— 250/109/35/3/2/1
2. **维度 B：Agent 评分来源**（Tier/D1-D6 评分的来源）— 223/177

并补充了交叉关系说明和待确认项。

### 2.4 附加发现：27 行"交付物有但评分无"的数据

这 27 行的特征是：
- 核心交付物来自 Mark 的 Agent 评分文档
- 但 6 维度评分（D1-D6）是后来基于 L4 名称语义推导的
- 这些行的 `M2_Tier` 与 `推导 Tier` 可能存在偏差，建议重点复核

**定位方法**：
```python
df[(df['交付物来源'] == 'Agent评分') & (df['Agent评分来源'] == '语义推导')]
```
