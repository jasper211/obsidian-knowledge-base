## 板块2：数据链全景

VN-PAY-01覆盖从保司发来的PDF/Excel，到最终市场佣金表外发给合作伙伴的完整数据流。

**本次分析覆盖的1个价值节点**

【VN-PAY-01 · 市场佣金制作产出包】🟡P0规范化
  Gate状态：Gate①挂数=PASS　Gate②落地=PASS　Gate③追溯=PARTIAL
  起点A：保司源头佣金PDF/Excel（季度）　终点Z：《市场佣金表(月)》v.final
  生产方：Lillian / Joanne / 刘敏然（COM-01录入）/ MOMO（COM-02制作）　消费方：对账/应派/产品复盘　频次：季×1 + 月×1
  涉及数据表：
    佣金准入表（过程表）← 原为手工录入的"收料口"，现已被数据表替代，但切换规则没写下来
    fact_commission_rate（事实表）← 存放各产品的佣金率，由ETL脚本自动计算，但计算公式没书面确认 ← ★P0：Owner挂名，ETL算错了Owner可能不知道怎么排查
    config_product_commission_formula（参数表）← 产品佣金计算公式配置表，公式冲突时谁说了算没定
    config_license_carrier_mapping（参数表）← 牌照和保司的对应关系
    agg_source_commission_wide（聚合表）← 把源头佣金按维度汇总，但聚合逻辑业务方没确认过 ← ★P1：Owner和Steward都为空，没人对聚合结果负责
    config_commission_table_type（参数表）← 决定市场佣金表怎么拆分的参数
    config_product_exclusion_range（参数表）← 哪些产品不算佣金
    product_risk_override（参数表）← 特殊情况下覆写产品属性，但覆写规则设了不会自动过期
    partner_tier_rules（参数表）← 合作伙伴档位和佣金系数，三权合一（一人配、一人审、一人批都是同一个人）← ★P0：配错了直接影响渠道激励金额
    config_partner_routing（参数表）← 合作伙伴出单走哪个牌照，三权合一 ← ★P0：指错牌照就是无照经营
    agg_market_commission_tier_rate（聚合表）← 全档位佣金表，档位怎么评没书面确认 ← ★P1：Owner和Steward为空
    市场佣金表（终态聚合表）← 最终外发给合作伙伴的表，手工调整后不留痕 ← ★P0：改了什么、为什么改、谁批的，都没有记录

## 板块3：集群风险

**本次发现1类集群风险：MOMO同时掌控COM-02制表链的多个关键环节，且均无独立复核机制**

MOMO同时负责以下4个环节，且均无独立复核机制：

| 环节 | 操作内容 | 涉及表 |
|---|---|---|
| 市场佣金表终态调整 | 手工调整市场佣金表后外发，不留痕 | 市场佣金表 |
| 合作伙伴牌照路由配置 | 配置config_partner_routing，决定出单走哪个牌照 | config_partner_routing |
| 合作伙伴档位规则配置 | 配置partner_tier_rules，决定渠道佣金系数 | partner_tier_rules |
| 制表参数配置 | 配置config_commission_table_type，决定佣金表输出格式 | config_commission_table_type |

**通俗比喻**：这就像一家工厂的质检员、生产主管、设备管理员都是同一个人。设备参数怎么调、产品出厂前改什么、出厂后发给谁，全都是他一个人说了算。如果某天他请假了，或者某个参数配错了，没有人能在第一道关卡拦住错误。

## 板块4：P0规则空白（4条，立即处理）

### P0-001：佣金准入表→数据表切换规则缺失
**技术描述**：佣金准入表（过程表）→ fact_commission_rate，切换规则未定义
**调研状态**：✅ 已确认（L4-COM-01："nobody updates source commission Excel anymore, now taken from data tables"）
**关联节点**：VN-PAY-01 · 市场佣金制作产出包
**访谈岗位**：刘敏然、Carrie
**通俗说法**：原来收保司佣金表是手工敲Excel的，现在已经改成系统自动从数据表里取了。但"什么时候改的、哪些保司改了、改之前的数据怎么查、改错了怎么回退"——这些都没写下来。如果系统出问题了，大家想回到原来的Excel，可能连原来的文件在哪都不知道。
**期望做到**：明确切换时间节点、切换范围、历史数据追溯路径和回滚方案，形成书面文档。

---

### P0-002：市场佣金表手工调整留痕/审批/回滚机制缺失
**技术描述**：市场佣金表（终态聚合表），MOMO "edits"后外发，调整不留痕
**调研状态**：✅ 已确认（L4-COM-02："momo edits market commission table using routing rules doc"）
**关联节点**：VN-PAY-01 · 市场佣金制作产出包
**访谈岗位**：MOMO、Carrie
**通俗说法**：市场佣金表生成后，MOMO会根据路由规则文档做一些手工调整，然后直接外发给合作伙伴。但"改了什么、为什么改、改之前长什么样、谁批准的"——这些都没有记录。如果改错了，外发给合作伙伴之后，对方按错的费率对账，后面很难发现。
**期望做到**：建立调整留痕机制（改前/改后差异记录）、审批链和回滚方案。

---

### P0-003：config_partner_routing三权合一+无复核
**技术描述**：config_partner_routing（参数表），priority和assigned_license_code，Owner=Steward=填写人=momo
**调研状态**：✅ 已确认（L4-COM-02：MOMO"edits market commission table using routing rules doc"）
**关联节点**：VN-PAY-01 · 市场佣金制作产出包
**访谈岗位**：MOMO、Carrie
**通俗说法**：合作伙伴出单走哪个牌照，这个路由规则由MOMO一个人配置、一个人复核、一个人审批。如果配错了，把某类产品指到了已经失效的牌照上，那就是无照经营。而且如果MOMO请假了，没人能接替这项工作。
**期望做到**：建立三权分离机制（发起/配置/复核/审批分人），明确紧急情况的替补方案。

---

### P0-004：源头PDF→标准化录入无OCR/验收标准
**技术描述**：保司源头PDF/Excel → 佣金准入表，无OCR/无验收标准
**调研状态**：❓ 部分填充（L4-COM-01提及"源头佣金里"从数据表取，但未提及PDF→录入环节）
**关联节点**：VN-PAY-01 · 市场佣金制作产出包
**访谈岗位**：刘敏然、Carrie
**通俗说法**：保司发来的PDF格式各家都不一样——有的列名叫"首期佣金"，有的叫"First Year Commission"；有的日期是"2024/01/01"，有的是"01-Jan-2024"。现在靠人工录入后肉眼检查对错，但没有统一的检查清单。录错了传递到下游，所有人的佣金都会算错。
**期望做到**：建立OCR或结构化提取机制，定义录入准确率阈值和人工校验清单，原始PDF归档至OneDrive。

## 板块5：P1规则空白（8条，尽快补全）

**关于费率管理（4条）**

**P1-001**（刘敏然）：fact_commission_rate ETL责任边界不清
→ 这张表的佣金率（fyc_rate/ryc_rate）是ETL脚本自动算出来的，但表上写的Owner是刘敏然。如果ETL算错了，刘敏然能排查出问题在哪吗？计算公式有没有书面确认过？
▸ VN-PAY-01

**P1-003**（刘敏然）：fact_commission_rate有效期重叠冲突解决
→ 同一个产品有两条费率记录的有效期重叠了，系统怎么处理？取最新的还是报错？这个规则目前没写下来。
▸ VN-PAY-01

**P1-004**（刘敏然）：config_product_commission_formula冲突解决
→ 同一个产品在不同时间段有两条不同的计算公式，生效期重叠了用哪个公式？首年和续期的公式会不会冲突？
▸ VN-PAY-01

**P1-005**（刘敏然、Carrie）：agg_source_commission_wide聚合逻辑未确认
→ 源头佣金宽表是按什么维度汇总、用什么聚合函数？这个逻辑业务方确认过吗？Owner和Steward都是空的。
▸ VN-PAY-01

**关于市场佣金制作（3条）**

**P1-002**（MOMO、Carrie）：市场佣金表外发版本一致性校验缺失
→ MOMO调整后外发，外发前有没有人审核？外发的版本和内部留底的版本怎么确保一致？有没有版本号？
▸ VN-PAY-01

**P1-006**（MOMO、Carrie）：agg_market_commission_tier_rate聚合口径缺失
→ 档位评定是按自然月、滚动季度还是保单年度？业绩门槛是多少？门槛调整了历史业绩重算吗？
▸ VN-PAY-01

**P1-007**（MOMO、Carrie）：config_partner_routing匹配优先级仲裁缺失
→ 路由规则有6个条件字段（合作伙伴/分类/佣金模式/保司/业务线/产品），多个条件同时命中时，优先级怎么排？
▸ VN-PAY-01

**关于产品映射（1条）**

**P1-008**（Carrie）：源头PDF产品命名→内部编码映射缺失
→ 保司PDF里的产品名称和我们内部的产品编码不一样，这个对应关系有没有标准映射表？映射错了费率就配错了。
▸ VN-PAY-01
