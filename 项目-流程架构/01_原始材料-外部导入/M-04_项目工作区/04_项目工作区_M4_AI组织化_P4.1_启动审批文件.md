## 1. 一页纸决策书

### 做什么
建 3 个基础设施层, 为未来 80 个 Auto agent 提供运行环境:
1. **数据管道** — 从保司/机构/理财师系统采集数据, 入仓, 出看板
2. **规则引擎** — 佣金/分级/权益等业务规则可配置化 (不再硬编码)
3. **告警系统** — 异常检测 + 自动通知 + 路由到对应负责人

### 为什么现在做
- P4.1 **零 P3 依赖** — 纯技术搭建, 跟组织/人无关
- P3 hold 期间 P4.1 并行 = **项目总时间缩短 3~4 个月**
- 没有基础设施, 后续业务 agent 每个都要自建数据管道, 重复造轮子

### 花多少钱

| 方案 | 预算 (HKD) | 人力 | 时长 | 风险 |
|-----|----------|-----|-----|-----|
| **A 内部为主** | **100~150 万** | Carrie + 1~2 开发 | 4~5 月 | 低预算但可能慢 |
| B 外包为主 | 200~300 万 | 外包团队 3~5 人 | 3~4 月 | 快但成本高 |
| C 混合 | 150~200 万 | Carrie + 1 内部 + 2 外包 | 3~4 月 | 平衡 |

**推荐**: **方案 A 内部为主** — 理由:
- MGA 不需要 Netflix 级基础设施, 用开源工具足够
- Carrie 已经是数据底座负责人, 有基础
- 省下来的钱留给 M4.2 业务 agent (更需要预算)
- 如果 Carrie 团队能力不足, 4 周后 escalate 切换到方案 C

### Mark 只需做 1 件事

**签字批准 方案 A**: Carrie 负责, 预算 ≤ 150 万 HKD, 3~4 个月完成。

## 2. P4.1 做什么 (技术层面, Carrie 看)

### 2.1 数据管道层

**目标**: 公司所有业务数据 T+1 入仓, 关键数据实时可查。

**当前状态** (基于 HR xlsx 观察):
- 数据分散在多个 Excel / 各系统中
- 无统一数据仓库
- 报表靠手工

**目标状态**:
```
数据源 (保司/CRM/佣金/HR)
    ↓ (ETL 采集, 每日/实时)
数据仓库 (PostgreSQL)
    ↓ (查询层)
BI 看板 (Metabase/Superset)
    ↓ (API 层)
未来 agent 调用
```

**技术选型建议** (开源优先, 低成本):
| 组件 | 推荐 | 备选 | 理由 |
|-----|-----|-----|-----|
| ETL 编排 | **Apache Airflow** | n8n / Prefect | 成熟 + 社区大 |
| 数据仓库 | **PostgreSQL** | MySQL | 功能强 + 免费 |
| BI 看板 | **Metabase** | Superset | 非技术人员友好 |
| 数据质量 | **Great Expectations** | 自研 | 自动数据校验 |

**覆盖的 Auto L4** (9 条):
- L3-IMF L4-01 数据采集与质量校验
- L3-IMF L4-06 实时数据接入看板
- L3-IRR L4-01 合作周期数据汇总
- L3-CPM L4-02 数据采集与实时监控
- L3-EFB L4-03 执行反馈收集
- L3-FLM L4-08 转化漏斗分析
- L3-FTR L4-08 学习数据追踪
- L3-IPI L4-12 业绩数据反馈
- L3-IMF L4-09 预测分析 (基础数据部分)

### 2.2 规则引擎层

**目标**: 佣金/分级/权益等业务规则从"代码硬编码"变为"JSON 配置 + Python 执行"。

**当前状态**:
- 规则在人脑里 (Mark/BD/财务各记一部分)
- 无标准化的规则文档
- 规则变更靠口头传达

**目标状态**:
```
规则配置文件 (JSON/YAML)
    ↓ (规则引擎加载)
Python 规则执行器
    ↓ (输入数据)
计算结果 + 审计日志
    ↓
下游系统 / 看板 / 通知
```

**技术选型建议**:
| 组件 | 推荐 | 备选 | 理由 |
|-----|-----|-----|-----|
| 规则存储 | **JSON 文件 + Git 版本管理** | 数据库 | 简单 + 可追溯 |
| 规则执行 | **Python 函数** | Drools / OpenRules | 灵活 + 团队会 Python |
| 规则编辑 | **YAML 模板 + 验证脚本** | 低代码平台 | 与 EA 知识库 validate_kb.py 一致 |
| 审计日志 | **PostgreSQL 表** | ELK | 简单够用 |

**覆盖的 Auto L4** (18 条):
佣金全链路 (COM L4-03/05/06/09) + 理财师分级 (EO L4-01~03/06~08) + 基本法 (FBA L4-04/05) + 产品配置 (IPI L4-01/02/06) + 合同触发 (IAC L4-05/10/11) + 晋升评估 (FPG L4-01/03) + 佣金结算 (IBE SAL-03)

**关键**: 规则引擎建好后, **M3.3 Mark 规则化会议的产出 (10 套规则) 可以直接灌入** — P3 和 P4.1 在这里汇合。

### 2.3 告警系统层

**目标**: 异常事件自动检测 + 按规则路由到对应负责人。

**当前状态**:
- 无统一告警
- 异常靠人发现
- 响应靠口头通知

**目标状态**:
```
数据管道 (实时/定时)
    ↓ (异常检测规则)
告警引擎
    ↓ (路由规则: 谁管什么)
通知渠道 (企业微信/邮件/短信)
    ↓
负责人收到 → 处理 → 闭环
```

**技术选型建议**:
| 组件 | 推荐 | 备选 | 理由 |
|-----|-----|-----|-----|
| 异常检测 | **Python 脚本 + 阈值规则** | ML 异常检测 | 先简单后复杂 |
| 告警路由 | **Python + 配置文件** | PagerDuty | 免费 + 灵活 |
| 通知渠道 | **企业微信 Webhook** | 钉钉 / 邮件 | 公司已用企业微信 |
| 闭环追踪 | **PostgreSQL 工单表** | Jira | 轻量 |

**覆盖的 Auto L4** (7 条):
- L3-SLCM L4-01 运营期健康度监控
- L3-SLCM L4-06 上市初期密集监控
- L3-IRR L4-06 续约前流失预警
- L3-FBA L4-08 客户流失预警召回
- L3-IMF L4-10 异常事件紧急通报
- L3-IPI L4-13 产品客户体验监控
- L3-FLM L4-10 候选人黑名单筛查

## 6. 与 P3 的汇合点

P4.1 和 P3 虽然并行, 但有 1 个关键汇合点:

```
P3 (Mark 规则化会议)          P4.1 (Carrie 规则引擎)
    │                              │
    │ 产出: 10 套规则文档            │ 产出: 规则引擎 V1
    │ (JSON/YAML 格式)             │ (可加载 JSON/YAML)
    │                              │
    └──────────┬───────────────────┘
               │
               ▼
        规则灌入: Mark 的规则 → 规则引擎
        (P3 + P4.1 汇合, ~W8~12)
```

**这意味着**: 当 Mark 决定恢复 P3 开规则化会议时, 产出的规则文档**可以直接灌入 P4.1 已建好的规则引擎**。两条路径在 Week 8~12 自然汇合。
