# Mark任务协同规则
> 版本：v0.1 | 建立日期：2026-05-27
> 适用范围：任何Jasper主导的、以Mark下发任务MD为起点的协同项目
> 与F2关系：本文件是F2（AI协作规范_多终端_v0.5）的上游规范，F2在本文件Phase D阶段开始激活
> 归档路径：01_上下文文件（AI协作）/Mark任务协同规则_v0.1.md
> 归档类型：AI协同规则类 → 本地第二大脑（R9规则）
> 状态：v0.1草稿，待Jasper确认后由Qoder归档

## 一、文档定位

### 1.1 这份文件解决什么问题

Mark下发任务MD之后，到任务真正可以执行之间，存在一段"分析→评估→规划→授权"的前置工作。这段工作没有标准化，每次都要重新想。

本文件把这段工作固化为可复用的协同闭环，覆盖从**收到任务MD → 分析解读 → 前置评估 → 规划 → 执行 → 回执Mark → 等待下一轮**的完整路径。

### 1.2 与现有规范的关系

```
本文件（Mark任务协同规则）
  ↓ Phase D阶段开始调用
F2（AI协作规范_多终端_v0.5）
  ↓ 执行层任务包下发
OpenCode / Kimi / Qoder 执行
```

| 规范文件 | 解决什么 | 激活时机 |
|---|---|---|
| 本文件 | Mark任务如何变成可执行任务 | 收到任何Mark任务MD时 |
| F2 AI协作规范v0.5 | 任务包如何设计和下发给执行终端 | Phase D规划阶段 |
| F3 教训库 | 历史教训防止重蹈覆辙 | Phase B前置分析时参考 |

### 1.3 Claude在本规范中的职责边界

**做**：
- 任务MD解读与结构化分析
- 依赖链与阻塞项识别
- 可执行性评估
- 规划图设计（含跨文件夹路径标注）
- 任务包设计与下发（调用F2）
- 回执报告初审
- 目录树维护建议

**不做**：
- 文件执行（交OpenCode/Qoder）
- 内容扫描（交Kimi）
- 代替Jasper作业务判断
- 代替Jasper向Mark回执
- 代替Jasper授权任务包

## 二、完整协同闭环（六阶段）

```
Mark下发任务MD
      ↓
[Phase A] 任务接收与解读
      ↓
[Phase B] 前置分析
      ↓
[Phase C] 可执行性评估（三档判定）
      ↓
[Phase D] 规划与任务包 ← 调用F2 R1-R9
      ↓
[Phase E] 执行与回执质检
      ↓
[Phase F] Mark回执与闭环判定
      ↓
  ┌───────────────────────┐
  │ 闭环：等待新任务       │  Mark无回复 = 任务完成
  │ 继续：基于回复再执行   │  Mark有问题 = 进入新轮次
  │ 关闭：收到新任务       │  Mark下发新MD = 开启新周期
  └───────────────────────┘
```

---

### Phase A · 任务接收与解读

**触发条件**：Jasper收到Mark下发的任务MD（或等效形式的任务指令）

**动作主体**：Jasper（带入Claude对话）+ Claude（结构化解读）

**Claude执行动作**：

1. 读取任务MD全文
2. 输出结构化解读摘要，格式如下：

```
【任务解读摘要】
任务名称：[简短命名，便于台账记录]
任务来源：Mark下发 / 日期：[日期]
核心要求：[一句话，Mark希望得到什么]
涉及范围：[哪些L3/流程/文件/人员]
明确截止：[有/无，如有列出]
隐含期望：[Claude识别到的但未明说的意图，标注"【Claude判断】"]
初步复杂度：[简单（1-2步可完成）/ 中等（需多步规划）/ 复杂（跨线依赖）]
```

**卡点**：解读摘要需Jasper口头确认"理解正确"后进入Phase B，不得自行跳过。

---

### Phase B · 前置分析

**触发条件**：Phase A解读摘要经Jasper确认

**动作主体**：Claude（分析）+ Jasper（裁定阻塞项）

**Claude执行动作**：

1. **依赖链梳理**：这个任务依赖哪些前置条件？哪些线/角色需要先完成什么？
2. **阻塞项识别**：发现不确定/未确认的问题，编号为QX（延续现有Q1-Q3序列）
3. **参考F3教训库**：有没有历史教训与本任务相关？
4. **跨文件夹路径确认**：任务是否涉及EA项目文件夹与本项目文件夹双路径？如是，明确标注：

```
输入来源路径：[EA项目绝对路径]
输出归档路径：[Mark任务专项协同绝对路径]
```

**产出物**：前置分析清单，格式：

```
【前置分析清单】
依赖项：
  - [依赖1]：状态（已就绪/待确认/阻塞）
  - [依赖2]：...

阻塞问题：
  - QX：[问题描述] → 需要：[Mark确认/Jasper裁定/Terresa提供]
  - QY：...

教训库参考：[有/无相关教训，如有列出编号]

跨文件夹路径：
  - 输入：[路径或"无跨文件夹"]
  - 输出：[路径]
```

**卡点**：有阻塞问题（QX）时，必须先推动Mark/相关人确认，不得强行进入Phase C"可执行"结论。

---

### Phase C · 可执行性评估

**触发条件**：Phase B前置分析清单完成

**动作主体**：Claude（评估）+ Jasper（最终裁定）

**三档判定**：

| 档位 | 条件 | 后续动作 |
|---|---|---|
| ✅ 可直接执行 | 无阻塞项，依赖全部就绪 | 直接进入Phase D |
| 🟡 部分可执行 | 有阻塞但可拆分，无阻塞部分先行 | 拆分任务，可执行部分进Phase D，阻塞部分挂起 |
| 🔴 不可执行 | 核心阻塞未解除 | 整理Q清单推送Mark，挂起等待 |

**产出物**：可执行性结论（一句话+档位标记）

**卡点**：Jasper对档位有异议时，以Jasper裁定为准。

---

### Phase D · 规划与任务包

**触发条件**：Phase C评估结论为✅或🟡（可执行部分）

**动作主体**：Claude（规划+出包）+ Jasper（确认+授权）

**调用F2规范**：本阶段全面激活F2 R1-R9，特别是：
- R1：先出规划图，Jasper确认后才出任务包
- R2：Jasper明确授权后执行终端才启动
- R8：出包前执行R8检查声明

**执行终端选择**（Jasper指定）：

```
文件执行类   → Qoder（归档/格式/命名）
代码执行类   → OpenCode（脚本/数据库/自动化）
内容扫描类   → Kimi（长文档摘要/多文件对比）
```

**跨文件夹任务包的路径规范**（新增强制规则）：

凡任务涉及EA项目文件夹与本项目文件夹双路径，任务包必须同时写明绝对路径，不得只写相对路径或"当前目录"。格式：

```
【路径说明】
输入文件：[EA项目完整绝对路径]/[文件名]
输出文件：[Mark任务专项协同完整绝对路径]/[目标目录]/[文件名]
```

**产出物**：规划图（Jasper确认）+ 任务包（F2格式，含R8检查声明）

---

### Phase E · 执行与回执质检

**触发条件**：Jasper完成授权，执行终端启动

**动作主体**：执行终端（执行）+ Claude（初审）+ Jasper（验收）

**执行终端义务**：
- 按任务包步骤执行，不超出范围
- 完成后逐项对照Done Criteria自检
- 回传产出时注明"已自检，结论：[通过/X项不符]"

**Claude初审义务**（来自F2 + LE-C-006）：
- 全量检查，不抽查
- 发现问题扩大范围，不缩小
- 执行终端自检不替代Claude独立核验
- 初审结论格式：

```
【Claude初审结论】
Done Criteria逐项核验：□通过 □部分通过 □不通过
发现问题：[如有，具体描述]
建议处置：[修订重做 / 附加观察记录 / 可提交验收]
```

**Jasper验收**：最终验收权在Jasper，Claude初审结论仅供参考。

---

### Phase F · Mark回执与闭环判定

**触发条件**：Jasper完成验收，准备向Mark提交

**动作主体**：Jasper（整理+提交）+ Claude（协助起草回执）

**Mark回执格式模板**：

```
【Mark回执 · 任务名称 · 日期】

完成情况：[完成/部分完成/未完成，一句话说明]

产出摘要：
  - [产出1]：[路径或描述]
  - [产出2]：...

遗留问题（如有）：
  - [问题1]：[简述+建议处置]

等待回复：[是/否]
```

**闭环判定逻辑**：

```
提交后等待Mark回复
    │
    ├─ Mark无回复（默认任务满足要求）
    │     → 台账标注"完成-等待新任务"
    │     → 任务挂起，不关闭（等新MD触发新周期）
    │
    ├─ Mark回复有问题
    │     → 基于回复内容，重新进入Phase A解读
    │     → 开启新轮次（任务编号加R2, R3...）
    │     → 直到Mark无回复或明确说"OK"
    │
    └─ Mark下发新任务MD
          → 旧任务台账标注"已关闭-新任务触发"
          → 新MD触发新周期，从Phase A开始
```

**注意**：任务关闭的唯一方式是Mark明确说OK，或Mark下发新任务（隐含旧任务已验收）。Jasper不单方面关闭任务。

## 三、目录树规则（本项目适用）

### 3.1 三层上限原则

```
项目根目录/
  └─ 一级目录（最多8个）/
       └─ 二级目录（按周期或域）/
            └─ 文件（不再有三级目录）
```

任何时候不得超过三层。随任务增多，通过**归档**（而非新建子目录）来控制层级。

### 3.2 归档规则

文件超过一个周期（CP已关闭）后，移入当前目录下的`_归档`文件夹（不计入三层限制），不新建子目录。

### 3.3 Claude的目录树维护职责

- 每个里程碑（CP）完成后，主动提示是否需要归档旧文件
- 发现目录层级即将突破三层时，提前提示Jasper做归档或合并
- 不自行创建目录，只出建议 → Qoder执行

## 四、任务执行台账

### 4.1 定位说明

| 文件 | 目的 | 受众 | 更新频率 |
|---|---|---|---|
| §5每日巡检表 | 向Mark汇报当日进展 | Mark | 每日23:00 |
| **任务执行台账** | 记录完整周期内任务推动过程 | Jasper自用 | 每个任务完成后 |

台账不替代巡检，也不向Mark提交。它是Jasper在一个周期结束后复盘"我们是怎么推动这些任务的"的内部记录。

### 4.2 台账格式（轻量化时间线）

```markdown
# 任务执行台账 · M4-W10周期（2026-05-26 → 2026-06-12）

---

## 时间线

| 日期 | 任务主题 | 做了什么 | 状态 | 备注 |
|---|---|---|---|---|
| 5-26 | 协同规则建立 | 建立目录树+Mark任务协同规则v0.1 | ✅完成 | |
| 5-27 | Q1-Q3确认 | 向Mark提交阻塞问题确认单 | ⏳等待回复 | |
| ... | ... | ... | ... | |

---

## 状态图例
✅ 完成（Mark无回复或已OK）
⏳ 等待回复（已提交，等Mark）
🔄 进行中（执行终端运行中）
🔴 阻塞（等前置条件）
❌ 关闭（新任务触发，旧任务自然关闭）
```

**原则**：
- "做了什么"一列保持简洁，5-10字描述核心动作，不罗列细节
- 细节在任务包和回执报告里，台账只记时间线和状态
- 每个CP节点（5-29/6-05/6-12）后，在台账底部加一段50字内的周期小结
