## 问题一：数据字典与我们工作的融合关系

### 结论先行：完全融合，是我们SQLite的升级蓝图

数据字典V1定义了Teresa的PostgreSQL架构的字段级规范。
与我们SQLite的关系是**演进关系，不是替代关系**：

```
我们的SQLite（现在）         Teresa的PostgreSQL（目标）
────────────────────         ──────────────────────────
fact_activity          →     FACT_CARD + DIM_PROCESS
dim_value_stream       →     DIM_VS
dim_job_family         →     DIM_ORG
bridge_l4_job          →     DIM_PROCESS.l4_accountable_family
dim_agent_capability   →     DIM_AGENT
（无）                 →     DIM_TIME（纯脚本生成）
（无）                 →     DIM_M_STRATEGY（M0-M8，9行静态）
（无）                 →     DIM_KPI（Week 6后）
（无）                 →     DIM_DELIVERABLE
```

### 数据字典给我们的三个直接行动点

**行动点1：L3/L4编码格式标准已明确**
数据字典明确规定了格式校验规则：
- L3格式：`^L3-[A-Z]{2,6}$`（如 L3-IAO，L3-COM）
- L4格式：`^L4-[A-Z]{2,6}-\d{2}[a-z]?$`（如 L4-COM-03，L4-BME-05a）

这直接是问题三（L3/L4编码统一）的标准答案。
**我们现在数据库里的编码凡是不符合这两个格式的，都是需要修正的。**

**行动点2：confirmation_status字段有了官方对应**
数据字典里DIM_PROCESS有`l3_status`字段（枚举：active/draft/retired/merged），
我们设计的confirmation_status与之对应，迁移时合并处理。

**行动点3：A0 Agent的验证规则有了标准来源**
数据字典里每个字段都有明确的校验规则（CHECK约束+枚举值），
这些规则就是A0-S02（源文件对比验证）的执行标准，不需要我们自己定义。

## 问题二：Agent设计模式选择

### 图中五种模式分析

| 模式 | 核心逻辑 | 优势 | 局限 |
|------|---------|------|------|
| ReAct | 思考→行动→观察 循环 | 动态适应，适合未知问题 | 单Agent，无法并行 |
| Plan-and-Solve | 先规划全局路线，再执行 | 路径清晰，适合已知复杂任务 | 计划刚性，遇变化需重规划 |
| Reflexion | 执行→得结果→LLM自我反思→迭代 | 质量自我优化，适合有对错标准的任务 | 迭代成本高，需要明确评判标准 |
| Toolformer | 严格JSON Schema输出，程序调用工具，结果喂回LLM | 结构化输出稳定，适合工具调用密集的任务 | 工具调用失败会阻断整链 |
| Multi-Agent | 任务分配→多Agent互相调用→协商决策 | 并行处理，适合多模块独立任务 | 协调复杂，需要编排层 |

### 我们项目的特点

```
特点1：有明确的数据标准（数据字典）→ 对错有标准，适合Reflexion
特点2：多个独立Agent（A0-A4，B1-B8）→ 适合Multi-Agent
特点3：每个Agent有明确工具调用（SQL查询/文件解析/CSV输出）→ 适合Toolformer
特点4：任务有依赖顺序（A0先验证，A1再修复，A2再生成报告）→ 适合Plan-and-Solve
特点5：数据不完整，过程中会有意外（如编号格式不一致）→ 需要ReAct的动态适应
```

### 建议：混合模式，分层使用

**不是选一个，是不同层级用不同模式：**

```
编排层（顶层）：Plan-and-Solve
    ↓ 制定全局任务序列（A0→A1→A2→报告）
    
单Agent执行层：Toolformer
    ↓ 每个Agent严格按JSON Schema调用工具
    ↓（SQL查询/文件读取/数据库写入）
    
质量验证层：Reflexion
    ↓ A0执行后自我检查：数据是否符合字典标准？
    ↓ 不达标→重新执行→直到达标
    
多Agent协作层：Multi-Agent
    ↓ A0+A1+A2在数据底座准备阶段并行运行
    ↓ B3+B4+B5在报告生成阶段串行调用
```

### 对当前各Agent的模式建议（V0.2更新）

| Agent | 推荐模式 | 理由 |
|-------|---------|------|
| A0 数据溯源验证 | Reflexion + Toolformer | 有明确字典标准可自我检查，工具调用密集（SQL查询+格式校验）|
| A1 数据修复补全 | ReAct + Toolformer | 遇到意外编号格式需动态推理，同时需要稳定的工具输出 |
| A2 缺口感知报告 | Plan-and-Solve + Toolformer | 查询路径固定（先查哪张表，再查哪张表），工具调用稳定 |
| A3 增量更新感知 | ReAct | 新文件内容未知，需要动态推理变更影响范围 |
| A4 版本管理 | Toolformer | 逻辑固定（旧版归档→新版写入），不需要复杂推理 |
| B3-B5 报告链路 | Plan-and-Solve + Multi-Agent | B3→B4→B5串行，每步计划明确，可并行处理多个岗位查询 |
| B8 反馈回写 | Reflexion | 写回前需验证：写入的内容是否与Mark决策一致？ |

### 对实现步骤的优化建议

基于混合模式，调整Agent建设顺序：

**阶段1（现在）：先建Toolformer基础**
每个Agent先实现"稳定工具调用"——给输入，出固定格式的输出。
这是所有模式的基础，VS Code现在做的Phase任务就是在建这一层。

**阶段2（A族报告跑通后）：加Reflexion验证层**
A0加上自我检查循环：执行完验证是否符合数据字典标准，不符合重跑。
先从A0开始，因为它的验证标准最清晰（就是数据字典的CHECK规则）。

**阶段3（Teresa架构上线后）：Multi-Agent编排**
B3+B4+B5上线后，加一个编排层（Orchestrator），
统一接收用户输入，分发给各Agent，汇总输出报告。
这一层用Plan-and-Solve：根据输入的岗位名称，规划调用哪些Agent、按什么顺序。

### 给其他AI平台的全量提取任务说明

**需要扫描的文件类型**：csv / md / txt（全部文件）


- "不一致"的情况全部保留，不要自动选择哪个对
- 来源文件写文件名即可，不需要路径

### 我设计的L3映射标准（供你拿到全量表后使用）

**映射标准的目标**：
当从任意源文件读取到一个L3编码或名称时，能够唯一确定它对应的"标准L3编码"是什么。

**标准L3编码的定义原则**（基于数据字典）：
```
标准格式：L3-[A-Z]{2,6}
示例：L3-IAO / L3-COM / L3-BMD
不带序号后缀：L3-BMC-01 不是标准格式，标准是 L3-BMC
```

**映射标准五条规则**：

**规则1：格式标准化**
凡是带序号后缀的（如 L3-BMC-01），去掉后缀，取 L3-BMC 作为标准编码。
凡是全大写字母组合（2-6位）的，直接作为标准编码。

**规则2：代码相同名称不同 → 以Mark确认版本的名称为准**
判断依据：
- 02 EA包A知识库的文件来源于Mark的决策输出 → 优先级高
- 01 企业架构知识库的文件是流程小组V0草稿 → 优先级低
- 有"Mark确认/锁定"标注的版本 → 最高优先级

**规则3：名称相同代码不同 → 以数据字典格式为准，选符合 `^L3-[A-Z]{2,6}$` 的那个**
如果两个都符合格式，选更短的（字母越少越接近标准缩写）。
如果都不符合格式，标记为"待人工裁定"，不自动映射。

**规则4：完全陌生的编码（既不在标准格式也无法推导）→ 标记为"待裁定"**
不强行映射，避免错误对齐。

**规则5：映射关系表结构**
```
标准L3编码 | 标准L3名称 | 等价编码列表 | 等价名称列表 | 来源文件 | 确认状态 | 备注
L3-IAO    | 保司接洽    | [L3-IAO-01] | [保司初始接洽] | 文件A,文件B | 待确认 | 代码有序号后缀变体
```

**映射关系表的使用方式**：
当Agent读取任意源文件时，遇到L3编码/名称，查这张映射表：
- 在"等价编码列表"或"等价名称列表"中找到匹配 → 返回对应的"标准L3编码"
- 找不到匹配 → 标记为"未知L3，需人工确认"，不报错，不跳过

**L4映射标准（基于L3映射的延伸）**：
L4编码 = L4-{L3字母部分}-{序号}
一旦L3标准编码确定，对应的L4标准格式自动推导：
```
例：L3-IAO 对应的 L4 标准格式为 L4-IAO-01, L4-IAO-02...
如果源文件里有 L4-01（无L3前缀），需要结合上下文的L3编码推导完整标准编码
```
