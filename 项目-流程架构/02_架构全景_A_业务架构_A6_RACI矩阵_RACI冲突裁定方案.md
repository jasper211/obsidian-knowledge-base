# RACI冲突裁定方案

## 背景

validate_kb.py 检测到 13 处 RACI 冲突，分布于三张矩阵。经逐条交叉比对协同框架、岗位方案(KA管理/RW协同多业务线版)及L3编码注册表，实际可归纳为 **13 处冲突**，按根因分为三类：

| 类型 | 数量 | 根因 |
|------|------|------|
| 多A (R/A合写导致) | 5 | KA矩阵将R与A合并写为"R/A"，导致同一行出现2个含A的角色 |
| 无A/无R (CSV结构性) | 4 | 权益矩阵前3行为多级表头，被误读为数据行；另有1行真实冲突 |
| 跨文件不一致 | 4 | RACI矩阵、协同框架、岗位方案三者对同一流程的主责定义互相矛盾 |

---

## 裁定原则

| 编号 | 原则 | 来源 |
|------|------|------|
| P1 | 每个L3有且仅有1个A (Accountable) | TOGAF RACI规范 |
| P2 | R与A可以是同一人，但必须显式拆分标注 | TOGAF RACI规范 |
| P3 | 路算分离 — 前台负责客户路由与交付，中台负责专业能力与标准 | CLAUDE_V2 L0原则④ |
| P4 | 单点失效消除 — 避免单一角色在全链条上都是A | CLAUDE_V2 L0原则⑧ |
| P5 | 岗位方案(RW协同版)为组织设计权威源，RACI矩阵必须与之对齐 | EA知识库治理规则 |

## 第一部分：KA矩阵 — 5处"多A"冲突

### 冲突 #01 | L3-KAEC 获取KA资源

- **当前状态**:
  - KA RACI矩阵: BD = R/A（含A），其余角色均为"-"
  - 岗位方案(RW版): 主责岗位 = BD
  - 协同框架: BD为全流程主责(R)，无单独A角色定义
- **冲突类型**: 多A (R/A合写，实质为1人同时R和A，技术误报)
- **建议方案**:
  - BD = **R** (执行市场开拓与线索挖掘)
  - BD = **A** (对线索质量和数量负最终责任)
  - 即: BD 同时承担 R 和 A，矩阵中标注为 **R,A** (用逗号分隔，不用斜杠)
- **建议理由**: BD岗位说明书明确"核心使命：开拓市场，精准识别并引入高价值KA客户"。此流程为BD的核心独立职责，R和A归同一人符合业务实际。仅需修正CSV格式写法。(引用: KA岗位方案-BD岗位, 原则P2)

---

### 冲突 #02 | L3-KAET KA评估定级

- **当前状态**:
  - KA RACI矩阵: BD = R/A，总部/中台 = C
  - 岗位方案(RW版): 主责岗位 = BD
  - 协同框架: KN2明确"交付经理（召集与汇报，R）、中台（风控与规则，**A**）"
  - L3编码注册表备注: "RACI冲突:框架→交付经理 vs 矩阵→BD"
- **冲突类型**: 多A + 跨文件不一致 (矩阵说BD是A，协同框架说中台是A)
- **建议方案**:
  - BD = **R** (执行尽职调查、准备评估材料)
  - 交付经理 = **R** (主持跨部门评估会议、深度信息收集)
  - 总部/中台 = **A** (对评估定级决策的合规性和准确性负最终责任)
  - CSM = C
- **建议理由**: 评估定级是"裁定"行为，涉及风控与合规判断。按原则P3(路算分离)，前台(BD/交付)负责信息收集和汇报(R)，中台负责规则裁定(A)。协同框架KN2已明确"中台(风控与规则，A)"，应以此为准。矩阵中BD标注为R/A不正确，A应归中台。(引用: 协同框架KN2, 原则P3路算分离)

### 冲突 #03 | L3-KAOP KA上架准备

- **当前状态**:
  - KA RACI矩阵: 交付经理 = R/A，产品经理 = C，CSM = I，总部/中台 = R
  - 岗位方案(RW版): 主责岗位 = KA交付经理
  - 协同框架: KN2明确"交付经理（主持检核，R/A）、中台（提供配置完成证明，R）、权益交付经理（提供权益开通证明，R）"
- **冲突类型**: 多A (R/A合写，加上总部/中台也标R，实质为分工合理但格式问题)
- **建议方案**:
  - 交付经理 = **R,A** (项目总负责人，对KA达到"Ready to Sell"状态负最终责任)
  - 总部/中台 = **R** (执行系统配置、账号开通等后台操作)
  - 产品经理 = C
  - CSM = I
- **建议理由**: 协同框架和岗位方案一致认定交付经理为"唯一客户接口和项目总负责人"。中台执行具体配置任务(R)但不承担最终交付责任。此处仅需修正CSV格式。(引用: 岗位方案-KA交付经理, 协同框架KN2, 原则P5)

### 冲突 #04 | L3-KAEM KA赋能

- **当前状态**:
  - KA RACI矩阵: 交付经理 = R/A，产品经理 = C
  - 岗位方案(RW版): 主责岗位 = **KA产品经理**
  - 岗位方案(KA管理版): KA产品经理"核心使命：作为权益产品包的落地执行者，专注赋能执行"
  - 协同框架: "交付经理主导与产品经理专业支持的平衡"
- **冲突类型**: 多A + 跨文件不一致 (矩阵说交付经理R/A，岗位方案说产品经理主责)
- **建议方案**:
  - 产品经理 = **R** (执行赋能培训、素材交付、效果验证)
  - 交付经理 = **A** (对赋能计划的整体效果负最终责任，派单与验收)
  - CSM = C (陪跑需求对接)
- **建议理由**: KA管理岗位方案明确产品经理"核心使命：专注赋能执行"，RW版也标注"L3-KAEM主责=KA产品经理"。但交付经理作为"KA客户的唯一战术对接窗口与交付总负责人"，应保留A权。R归产品经理执行，A归交付经理验收，实现专业分工。(引用: KA岗位方案-产品经理, RW版三-1, 原则P3)

### 冲突 #05 | L3-KAGA KA业绩跟踪与运维

- **当前状态**:

  - 岗位方案(RW版): 主责岗位 = KA交付经理
  - 协同框架: "决策与行动由交付经理（R）主导"，"确保决策者（A）基于完整信息做出判断"
- **冲突类型**: 多A (R/A合写，实质为1人同时R和A，技术误报)

## 第二部分：权益矩阵 — 4处结构性冲突 + 4处实质冲突

### 冲突 #06 | 权益矩阵 Row2 — CSV结构性问题 (无A/无R)

- **当前状态**: Row2实际内容为"权益业务价值链,L3代码与名称,业务,中台,机构,职能,核心说明"，这是表头行而非数据行
- **冲突类型**: CSV结构性误报 (多级表头被误读为数据行)
- **建议方案**: **修正CSV格式** — 将Row1-3的多级表头合并为1行标准表头，或在validate_kb.py中对权益矩阵增加skip_rows=2的特殊处理
- **建议理由**: 非业务冲突，纯技术问题。修正CSV结构即可消除。

- **当前状态**: Row3实际内容为",,,,交付经理,,"，这是角色标注的子表头行
- **冲突类型**: CSV结构性误报 (同#06)
- **建议方案**: 同#06，**合并为标准表头格式**
- **建议理由**: 同#06

### 冲突 #08 | 权益矩阵 Row4 — L3-CDA 权益客户需求诊断与分析 (多A误报)

- **当前状态**:
  - 权益RACI矩阵: 业务=R, 中台=A, 机构=-, 职能=C
  - 但validate_kb.py将"L3-CDA"列的文字中含字母A也计入了A角色(误报)
  - 协同框架: 权益规划经理(中台)为全流程主责
  - 岗位方案(RW版): 主责=权益规划经理(RW中台-规划)
- **冲突类型**: 技术误报 (L3编码列含字母A被误计)
- **建议方案**: 实际RACI分配正确(业务=R, 中台=A)，**仅需修正validate脚本**，将L3编码/名称列排除出RACI计数范围
- **建议理由**: 数据本身无冲突，是验证脚本的列偏移bug。

### 冲突 #09 | L3-OBC 权益方案目标确认与共识达成

- **当前状态**:
  - 权益RACI矩阵: 业务=R, 中台=A, 机构=-, 职能=**R**
  - 岗位方案(RW版): 主责=权益规划经理(中台)
  - 协同框架: 权益规划经理主导目标对齐
- **冲突类型**: 无直接冲突 (R可以有多个)，但**职能列标注R需确认**
- **建议方案**:
  - 业务(前台) = **R** (收集客户需求、推动共识达成)
  - 中台(权益规划经理) = **A** (对目标合理性和可行性负最终责任)
  - 职能 = **C** (提供支持意见，不应为R)
  - 机构 = -
- **建议理由**: 职能部门在目标确认阶段的角色应为咨询(C)而非执行(R)。若职能也是R，则R角色过多，责任边界模糊。按原则P3，中台A、前台R、职能C。(引用: RW版L3-OBC主责=权益规划经理, 原则P3)

  - 职能 = **C** (提供数据分析支持，降级为C)
- **建议理由**: 核心说明明确"中台负责"，职能部门在持续监控中的角色应为咨询支持(C)。中台同时R和A符合其作为规划板块的定位。(引用: 权益矩阵核心说明, RW版, 原则P5)
