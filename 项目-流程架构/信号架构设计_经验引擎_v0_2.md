## 二、文件在本项目中的角色

### 2.1 定位确认

**这份文件在「企业流程架构 & 经验引擎」项目中的角色：**

| 角色 | 说明 |
|------|------|
| ❌ 不是信号源 | 它不是触发洞察的外部信号 |
| ❌ 不是 Mark 任务指令 | 它是 experience-engine 的内部产出物 |
| ✅ 是经验参照层的数据来源 | 洞察七模块中「经验参照」模块的素材库 |
| ✅ 是阶段2的正式接入对象 | 对应上下文文件「阶段1.2：加入 experience-engine」 |

**一句话定位：它是引擎的燃料（经验参照），不是引擎的输入信号。**

### 2.2 三个项目的关系图（更新版）

```
项目A：EA数据底座（标准侧，已完成）
  → 提供「应该怎么做」的标准参照
  → 4张核心表：dim_l3 / dim_l4_activity / dim_value_stream / dim_agent_capability

  → 提供「历史上怎么做的 / 背后原则是什么」

  → 信号×架构匹配系统，动态洞察层
  → 外部信号 × 项目A × 项目B → 结构化洞察
```

## 三、整体架构的对话确认

### 3.1 Jasper 提出的架构理解

> 从任务指令到信号A，再将信号A与EA流程架构匹配，然后出信号B。信号B是洞察的输入源之一，其他输入源可能包括 experience-engine 这些文档的匹配，最终出有价值的洞察。

**Claude 评估：方向完全正确。**

### 3.2 准确的三个点

**① 信号A→信号B是核心链路**：先跑通这条是正确的阶段0策略。

**② 信号B是洞察的输入源之一，而非唯一**：experience-engine 是并行输入，不是替代关系。

**③ 阶段0暂不纳入 experience-engine**：节奏合理，保持验证焦点。

### 3.3 需要补充的一处

**信号B不只是「匹配到了什么」，还必须包含缺口分析（gap_analysis）。**

缺口信息 = 信号指向的业务行为与EA底座定义的标准之间的差距。这个缺口才是洞察真正有价值的地方，是七模块中「洞察结论」和「建议行动」的来源。

### 3.4 完整架构图

```
Mark任务指令（及未来多元输入）
        ↓
   [节点1] 任务内容解析
        ↓
   [节点2] 形成信号A（结构化信号）
        ↓
   [节点3] 信号A × EA数据底座（L3/L4/KPI匹配）
        ↓
   [节点4] 形成信号B（匹配结果 + 缺口判断）
        ↓
   [节点5] 信号B × experience-engine（阶段2启动）
        ↓
   [节点6] 洞察推理程序
        ↓
   [节点7] 输出七模块洞察结论
```

## 四、七节点信号架构详细设计

### 节点1：任务内容解析

**功能**：将多元格式的输入内容转化为可处理的文本。

**输入格式支持与优先级**：

| 格式 | 阶段0 | 阶段1 | 阶段2+ |
|------|-------|-------|--------|
| Markdown / 纯文字 | ✅ 直接处理 | ✅ | ✅ |
| PPT | ❌ 暂不支持 | ⏳ 转文字后处理 | ✅ |
| 图片 | ❌ 暂不支持 | ⏳ OCR后处理 | ✅ |
| 录音 | ❌ 暂不支持 | ❌ | ✅ Phase 3信号源 |

**阶段0原则**：格式解析不是阶段0的阻断项，先用纯文字信号跑通链路。

**节点输出**：清洁文本（可供节点2进行实体提取）

---

### 节点2：形成信号A（结构化信号）

**功能**：从清洁文本中提取关键实体，形成标准化的结构化信号。

**核心设计原则**：信号A的质量直接决定节点3匹配的准确度，是整条链路的质量基础。

**信号A标准结构**（详见第五章）

**阶段0处理方式**：手工提取，Claude执行，不依赖代码。

---

### 节点3：信号A × EA数据底座匹配

**功能**：将结构化信号与EA数据底座的四张核心表进行多路并行匹配，锁定相关的L3/L4/KPI节点。

**匹配路径（三路并行）**：

```
信号A的实体
    ├─ business_scenario  → 语义匹配  → L3（最主要路径）
    ├─ job_family         → 精确匹配  → 岗位KPI → 企业KPI → L3
    ├─ objective          → 规则匹配  → KPI编码 → L3
    └─ trigger_event      → 规则匹配  → 价值流阶段 → L3
                                              ↓
                                      confirmed L3
                                              ↓
                                      L4 + 核心交付物
                                      Agent Tier（Auto/Aug/Hybrid/Human）
                                      标准KPI关联
```

**三路并行的意义**：多路结果互相印证，提升匹配置信度。三路结果收敛到同一L3 → 高置信度；结果分散 → 低置信度，需人工裁定。

**依赖的EA底座表**：

| 表名 | 用途 |
|------|------|
| dim_l3 | 82个标准L3编码，语义匹配的目标库 |
| dim_l4_activity | L3→L4映射，含交付物+Agent Tier |
| dim_value_stream | 价值流阶段，触发事件匹配 |
| dim_agent_capability | Agent能力维度，判断自动化程度 |
| KPI穿透表（235行） | 企业KPI↔L3映射，规则匹配路径 |
| 岗位KPI表（302行） | 岗位KPI→企业KPI→L3，精确匹配路径 |

**治理规范参照**（匹配时的判断标准）：

- 价值流-L3映射：3问检验法（Q1利益相关者→Q2触发事件→Q3交付接收方）
- L1-L3映射：6类典型归属模式
- L3编码映射标准V1.1

---

### 节点4：形成信号B（匹配结果 + 缺口判断）

**功能**：整合节点3的匹配结果，并生成缺口分析，形成洞察推理的原材料。

**核心区别**：信号B ≠ 信号A + 匹配编码。信号B的核心价值在于 `gap_analysis`——将「发生了什么」转化为「和标准相比差在哪里」。

**信号B标准结构**（详见第六章）

---

### 节点5：信号B × experience-engine 匹配

**功能**：用信号B的业务场景和缺口信息，从 experience-engine 中找到相关的历史经验参照。

**启动时间**：阶段2（阶段0概念验证通过后）

**与节点3的核心差异**：

| 维度 | 节点3（×EA底座） | 节点5（×experience-engine） |
|------|----------------|---------------------------|
| 匹配对象 | 结构化编码（L3/L4/KPI） | 自然语言原则和判断 |
| 匹配方式 | 语义+规则+精确（三路并行） | 语义匹配为主 |
| 准确度 | 较高（结构化数据） | 相对较低（自然语言） |
| 提升路径 | 扩展编码覆盖率 | 建立跨系统编号对照表 |

**阶段2前置条件**：需建立「EA底座L3编码 ↔ experience-engine entry_id」对照表（见第七章待解决问题）。

---

### 节点6：洞察推理程序

**功能**：基于信号B（+经验参照）进行三步推理，生成有行动意义的洞察内容。

**这不是模板填充，而是推理程序。**

**三步推理逻辑**：

```
Step A：现象归因
  输入：gap_analysis.gap_desc
  推理：识别缺口的高概率原因（2-3个假设）
  输出：「洞察结论」模块的高概率原因

Step B：影响穿透
  输入：matched_kpi + 权重
  推理：计算缺口对企业KPI的影响范围和量级
  输出：「影响范围」模块的关联KPI和预计影响

Step C：输出 audit 锚点（v0.2调整，来源：§28业务实战主导锁定）
  ⚠️ v0.1设计是输出"建议行动选项A/B/C"，已调整
  输入：信号B缺口 + experience-engine相关do_and_dont/risks_and_mitigations段（阶段2）
  推理：识别信号触发了experience-engine哪些问题点
  输出：audit锚点（"这条信号涉及 [entry_id] 的 do_and_dont/risks" + 引用原文）
         让 Mark 看 audit 锚点 + 经验原文后自己拍 A/B/C

  §28调整原因：经验类内容的行动选项语言由Mark业务实战主导，
  不接受agent推断扩展。Claude输出锚点供Mark决策，不替代Mark决策。
```

> **兼容性说明**：阶段0不涉及experience-engine，Step C在阶段0输出「基于EA底座标准的行动建议」（不引用经验库），此处调整在阶段2正式接入后生效。

**三步对应七模块结构的位置**：

| 推理步骤 | 对应七模块 | v0.2变化 |
|---------|----------|---------|
| Step A 现象归因 | 模块4：洞察结论 | 无变化 |
| Step B 影响穿透 | 模块6：影响范围 | 无变化 |
| Step C audit锚点 | 模块5：建议行动 | ⚠️ 从"选项A/B/C"改为"audit锚点+经验原文" |

**trigger_event 字段说明**：

## 六、信号B标准结构定义

```
─────────────────────────────────────────
信号B · 标准结构 v0.1
（基于信号A + EA底座匹配结果）
─────────────────────────────────────────
signal_id:              [继承自信号A的signal_id]
source_signal_a:        [关联的信号A编号]

match_confidence:       高 / 中 / 低

match_notes:            [匹配过程中的异常或多路径冲突说明]

─────── 缺口分析（核心） ───────

gap_analysis:
  gap_type:     缺口 / 偏差 / 优化机会 / 正常 / 待确认
  gap_desc:     [具体描述：信号行为 vs EA底座标准定义的差距]
  agent_tier:   Auto / Aug / Hybrid / Human
                [当前L4的Agent化程度，判断是否/如何介入]
  severity:     高 / 中 / 低
                [缺口对业务运行的影响程度]

─────── 经验参照（阶段2填充） ───────
⚠️ v0.2更新：引用粒度升级为a+c+f三段，增加轨道和元数据字段

experience_ref:
  matched_entry_id:   [experience-engine entry编号，阶段2填入]
  entry_name:         [entry名称]
  entry_type:         [A/B/C/D类]
  source_track:       [V3.1（推荐）/ V3（需核查fallback_marker）]
  target_audience:    [B2B / B2A / B2B+B2A（用于过滤洞察消费者）]
  confidence_level:   [HIGH / MEDIUM / LOW]
  relevance_note:     [为什么相关，一句话]
  a_business_framework: [原文引用，约100-200字]
  c_root_cause:         [原文引用，约100-200字]
  f_do_and_dont:        [原文引用，约100-200字]

─────────────────────────────────────────
```

**gap_analysis 字段是信号B的核心价值所在**：

它将节点3的「找到了什么」转化为节点6推理需要的「差在哪里」。没有缺口分析，洞察只是「信号发生了什么」的描述，不是「需要关注什么」的判断。

**match_confidence 的判断标准**：

| 等级 | 判断标准 |
|------|---------|
| 高 | 三路匹配路径收敛到同一L3，无歧义 |
| 中 | 两路匹配路径一致，一路不确定 |
| 低 | 三路匹配路径分散，或只有一路有结果 |

### 问题1（原）：两套编号系统的映射（对应前置1）

**问题描述**：EA底座使用结构化编码（如 `L3-IRR`），experience-engine 使用内部 entry_id（如 `decision_framework_004`）。两套系统之间没有映射关系。

**v0.2补充**：映射时需用 layer_hint 元数据作为关键过滤字段，映射粒度应精确到「L3编码 ↔ A/B/C/D中具体某条entry」，而不是「L3 ↔ 任意entry_id」。

**举例**：

```
信号B匹配到：L3-IRR（合作周期管理）
节点5想找相关entry，需要：
  1. 通过layer_hint过滤出业务域匹配的entry
  2. 在过滤结果中找decision_framework_004（跨保司迁移决策框架）
  3. 确认entry来源是V3.1（可信）而非V3（含fallback）
```

**Owner**：Jasper主导 / Mark agent辅助
**时间节点**：阶段1结束前完成
