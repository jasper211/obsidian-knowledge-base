## 一、V0漏洞说明（V0.1记录，保留）

### 发现时机
Teresa的流程小组任务计划V2揭示：我们bridge_l4_job表的80条数据来源于"规划态/承诺态"映射，不是业务确认版。数据结构完整，但内容可信度存疑。

### 漏洞本质
V0的A2（数据质量巡检）只做**结构性检查**：
- ✅ 字段是否为空
- ✅ JOIN是否成功
- ✅ 版本是否冲突

但缺少**内容准确性验证**：
- ❌ 数据内容与源文件是否一致
- ❌ 数据的确认状态（规划态/推导态/业务确认/锁定）
- ❌ 哪些数据可以直接用于报告，哪些需要标注存疑

### 已踩过的坑
| 时间 | 问题 | 性质 |
|------|------|------|
| Phase 3 | 发现3个数据Fix（l3_name为NULL等） | 结构性问题，A2可发现 |
| Phase 4-1 | 两套编号体系完全不匹配 | 结构性问题，A2可发现 |
| Teresa文档评估 | bridge_l4_job基于规划态数据 | **内容准确性问题，A2无法发现** |
| VS-1补录 | 推导数据需标注来源 | **内容准确性问题，A2无法发现** |

## 二、新增Agent：A0 数据溯源与准确性验证（V0.1新增，保留）

### 定位
**所有Agent的前置守门人。** 在数据入库之前验证来源可信度，在入库之后持续监控内容准确性，输出每条数据的可信度评级。

### 与A1/A2的区别

| | A0 数据溯源验证 | A1 数据修复补全 | A2 数据质量巡检 |
|--|--|--|--|
| 问的问题 | "这条数据是真的吗？" | "这条数据缺了什么？" | "这条数据结构完整吗？" |
| 检查维度 | 内容准确性+确认状态 | 缺失字段+断裂链路 | 空值+格式+版本冲突 |
| 触发时机 | 数据入库前+源文件更新后 | 发现缺口时 | 定期+数据库更新后 |
| 输出 | 可信度评级+存疑清单 | 补全数据+推导标注 | 质量报告+异常推送 |
| 人工介入 | 高（存疑项必须人工确认） | 高（推导内容确认） | 低（仅异常才介入） |

### 核心能力

**能力1：确认状态标注**
每条数据入库时打上状态标签：

| 状态 | 含义 | 报告中的处理 |
|------|------|------------|
| 🔴 规划态 | 来源于未经业务确认的规划文档 | 必须标注"待确认"，不可直接引用 |
| 🟡 推导态 | 从JD或其他文档推导，非原始数据 | 标注推导来源，建议确认 |
| 🟠 草稿态 | 源文件标注为V0/草稿 | 标注版本，提示可能变更 |
| 🟢 业务确认 | 经过业务方评审确认 | 可直接用于报告 |
| ✅ Mark锁定 | Mark审批通过，版本锁定 | 最高可信度，可直接引用 |

**能力2：源文件对比验证**
定期将数据库内容与源文件对比，发现：
- 字段值与源文件不一致（如岗位名被修改但数据库未更新）
- 源文件版本升级但数据库仍是旧版内容
- 推导数据与后续正式文档产生矛盾

**能力3：可信度传导**
下游数据继承上游的可信度：
- 如果VS-1某阶段是推导态 → 基于VS-1生成的报告该板块自动标注推导来源
- 如果bridge_l4_job是规划态 → A族报告的L3协同板块自动标注"待Teresa V1版本确认"

**能力4：可信度报告**
每次执行输出：
- 各表的确认状态分布（多少条规划态/推导态/确认态/锁定态）
- 存疑清单（需要人工确认的具体条目）
- 报告可用性评估（基于当前数据，哪些报告板块可以生成，哪些需要标注）

### Skill规划

| Skill编号 | Skill名称 | 状态 |
|----------|---------|------|
| A0-S01 | 数据确认状态标注 | ⏳ 待设计 |
| A0-S02 | 源文件对比验证（执行规则来自数据字典V1校验规则）| ⏳ 待设计 |
| A0-S03 | 可信度传导计算 | ⏳ 待设计 |
| A0-S04 | 可信度报告生成 | ⏳ 待设计 |

### 达标标准
- 数据库每张表每条记录都有confirmation_status字段
- 报告生成前可以查询"哪些数据可直接用，哪些需标注"
- 源文件更新后24小时内识别出数据库的过期内容

### 启动时机
**现在立即需要**——在Phase 5报告原型之前，bridge_l4_job和dim_job_family里的数据需要先打上确认状态标签，否则报告里无法区分哪些内容是可信的，哪些是待确认的。

## 八、Agent协作模式分析（V0.2新增）

### 背景
基于AI Agent常见五种设计模式（ReAct / Plan-and-Solve / Reflexion / Toolformer / Multi-Agent），结合本项目特点，分析Agent之间最适合的协作关系。

### 五种模式与本项目的适配分析

| 模式 | 核心逻辑 | 本项目适配度 | 原因 |
|------|---------|-----------|------|
| ReAct | 思考→行动→观察循环，动态适应 | ⭐⭐ 低 | 我们的任务路径已知，不需要动态探索；且"对错"标准需要你或Mark判断，不适合Agent自主循环 |
| Plan-and-Solve | 先规划全局路线，再执行 | ⭐⭐⭐⭐⭐ 高 | 任务链路明确（A0→A1→A2→报告），适合先规划调用哪些Agent、按什么顺序，再逐步执行 |
| Reflexion | 执行→自我反思→迭代直到合格 | ⭐⭐ 低 | 迭代的"合格标准"在我们项目中需要人来判断，不适合纯Agent自我迭代 |
| Toolformer | 严格按JSON Schema调用工具，结果喂回LLM | ⭐⭐⭐⭐ 中高 | 每个Agent内部调用SQL/文件工具时适用，但这是**单Agent内部逻辑**，不是协作模式 |
| Multi-Agent | 多Agent任务分配、互相调用、协商决策 | ⭐⭐⭐⭐⭐ 高 | Teresa架构上线后，B3/B4/B5串行调用；多个岗位族报告可以并行生成，天然适合Multi-Agent |

### 建议：Plan-and-Solve + Multi-Agent 混合协作

**整体用Plan-and-Solve**

每次执行前有一个规划层，决定：
- 这次查询需要调用哪些Agent
- Agent的调用顺序是什么
- 哪些Agent可以并行，哪些必须串行

目前这个规划层由我（Claude.ai）承担——我分析输出任务包，你决策，VS Code执行。Teresa架构上线后，规划层可以由一个Orchestrator Agent承接，自动根据用户输入规划调用链路。

**局部用Multi-Agent**

当多个岗位族报告同时生成时：
```
用户输入："给我A族和B族的报告"
         ↓
    Orchestrator（Plan-and-Solve规划）
    ↙              ↘
B3→B4→B5           B3→B4→B5
（A族报告线）       （B族报告线）
    ↘              ↙
      汇总输出给用户
```

数据层的维护也可以并行：
```
Teresa文件更新
      ↓
A3感知变更
  ↙      ↘
A0验证   A1修复
（并行执行，互不依赖）
      ↓
  A2重新生成报告
```

## 九、Teresa数据字典对架构的强化作用（V0.2新增）

Teresa的数据字典V1是我们整个Agent架构的**权威输入标准**，直接强化了三个关键层面：

### 强化层面1：A0的验证规则有了完整执行清单

数据字典里每个字段的校验规则，就是A0执行内容准确性验证的标准来源：

| 数据字典规则 | 对A0的强化 |
|------------|---------|
| L3格式：`^L3-[A-Z]{2,6}$` | A0-S02直接用此正则校验所有入库L3编码 |
| L4格式：`^L4-[A-Z]{2,6}-\d{2}[a-z]?$` | 同上，校验L4编码 |
| agentifiability枚举：Auto/Aug/Hybrid/Human | A0校验Agent评分字段的合法值 |
| vs_code枚举：VS-1~VS-5/L1-05 | A0校验价值流字段的合法值 |
| 每个L4只能有一个A责任人 | A0校验bridge_l4_job不出现重复A责任人 |

A0不再需要自己定义验证规则——数据字典就是规则集，直接执行。

### 强化层面2：confirmation_status与数据字典字段天然对齐

我们设计的可信度标签，与数据字典的字段直接对应：

| 我们的confirmation_status | 数据字典对应字段 | 对齐方式 |
|--------------------------|--------------|---------|
| 🔴 规划态 | DIM_PROCESS.l3_status = 'draft' | 迁移时直接映射 |
| 🟠 草稿态 | DIM_PROCESS.l3_status = 'draft' + version=1 | 合并处理 |
| 🟢 业务确认 | DIM_PROCESS.l3_status = 'active' | 直接映射 |
| ✅ Mark锁定 | DIM_PROCESS.is_current = TRUE + valid_to = NULL | 组合映射 |

SQLite阶段先用我们的标签，迁移PostgreSQL时零成本转换。

### 强化层面3：数据字典明确了各表数据来源，直接指导A1的修复优先级

数据字典每个字段都标注了取值来源状态（✅已有/⚠️部分有/❌需新建），这直接告诉A1应该优先修复哪些字段：

| 数据字典标注 | A1的处理方式 |
|------------|-----------|
| ✅已有数据 | A1不需要处理，直接入库 |
| ⚠️部分有数据 | A1补全缺失部分，标注来源 |
| ❌需新建采集 | A1标记缺口，推送给你决策是否手工录入 |

特别关键的：`DP-016 l4_accountable_role`（A责任人）标注为❌，原因是GAP-01未完成。A1看到这个标注就知道不需要尝试自动补全，等Teresa的V1文件来了再处理。

### 总结

```
数据字典V1的作用
      ↓
┌─────────────────────────────────────────┐
│  给A0：提供完整的字段校验规则和枚举约束    │
│  给A1：明确哪些字段可自动补全，哪些等人工  │
│  给A0：confirmation_status的迁移映射关系  │
│  给整个架构：L3/L4编码的SSOT标准格式     │
└─────────────────────────────────────────┘
```
