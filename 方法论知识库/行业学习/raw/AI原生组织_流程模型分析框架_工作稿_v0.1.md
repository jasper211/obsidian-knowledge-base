## 5. Agent编排层 ★正在搭建★（已用 VNW 真实代码校准）

**架构原则**：VNW 不采用"每层拆一个独立子 Agent"的架构。[Agent搭建SOP_v1.2.md](../../../../../Jasper AI协同经验引擎/AI工程能力整改项目/05_Agent库/草稿/Agent搭建SOP_v1.2.md) 第四节明确记录：早期"子Agent"命名法（`{AgentID}-S{序号}`）已被 PTA 实操验证后废弃，改用"一个 Agent + skills/tools 模块"——PTA 当年是把散落的独立小脚本**合并**回一个 Agent 下的模块，不是往更细拆。所以本层的各项能力，默认应留在对应业务 Agent（如 VNW）内部当 skills，不要因为框架图上占了一层就默认要拆成独立 Agent 进程。

**真正值得独立成 Agent 的判断标准**：本质上跨多个业务 Agent 复用、有独立触发/生命周期的能力——例如"治理"（方法论转正Agent，要审计的是 VNW/PTA/AIT 所有 agent，不只一个）、"背景记忆"（OB巡检Agent，服务所有业务 agent）。这两个的独立性来自"服务对象不止一个业务 Agent"，不是来自框架图的层级划分。

**VNW 真实具备/未具备对照**（2026-08-03 核实代码得出，不是推测）：

| 框架层 | 图里设想的Agent | VNW 真实现状 |
|---|---|---|
| 1.战略与规划 | 战略规划Agent（半自动，生成草案） | **不具备**。需求定义、路线图全是 Jasper 手写。 |
| 2.流程模型层 | 流程挖掘Agent+建模Agent（自动，从日志发现） | **具备，但机制不是"挖掘"**。`skills/l3_model_builder.py` 自动建模，输入是 Postgres 权威库+人工维护的流程蓝图文件+D1-D6评估表，是"从已有文档结构化重建"，不是"从原始执行日志反推流程"（process mining）。VNW 目前完全没有事件日志挖掘能力。 |
| 3.分析模型层 | 分析引擎Agent（自动，加载模型分析） | **具备，是真LLM调用**。`skills/l3_analysis_runner.py` 的 `run()` 真的调 DeepSeek API 生成分析产出（另留 `--import-analysis-output` 手动导入口子）。 |
| 4.数据底座层 | 数据工程Agent（自动，ETL清洗） | **具备，但脚本不是Agent**。`sync_data_foundation.py` 自动做 ETL，没有LLM参与，是确定性脚本，触发靠 Jasper 手动跑命令。 |
| 5.Agent编排层 | Orchestrator（自动，任务规划调度） | **基本不具备，只有一个真实的小例外**。全流程靠 Jasper 逐条手敲 CLI 命令。唯一自动调度是一个真实存在的 launchd 定时任务（`com.jasper.vnw-source-check.plist`，每30分钟跑一次），但只做只读扫描，不自动应用变更/不自动重跑分析/不自动发布——11层监控README原话："尚未建设...大模型自动重跑；未校验分析不得自动发布"。 |
| 6.输出与治理 | 报告Agent+治理Agent（半自动，生成报告+人工审批） | **报告侧具备但不是Agent写的，治理侧是代码规则不是独立Agent**。前端是固定模板读JSON渲染；模型输出固定标`MODEL_DRAFT`，不经Jasper确认不能转正；治理规则硬编码在建模/分析脚本的校验逻辑里，"方法论转正Agent"（本该填这个位置）目前还没建成。 |

**一句话总结落差在哪**：VNW 已经有一条真实自动化的分析产线（ETL自动、建模自动、LLM分析自动），但产线的"启动开关"和"步骤衔接"全靠人；治理是写死的代码规则，不是能审计别的 Agent 的独立 Agent；"从日志挖掘流程"这条能力完全没有，现在做的是"从文档重建流程"。

**未覆盖范围**：PTA/AIT/OB/HKIA/PDA 的真实代码状态本轮未核实，上表仅覆盖 VNW；这几个 Agent 如果要同样过一遍真实代码再填表，需要单独安排。
