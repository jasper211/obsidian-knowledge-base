## 问题诊断：为什么AI会"推翻重写"

### 三大常见陷阱

#### 问题1：不知道整体结构
- AI看不到项目全貌，只能凭对话猜测
- 无法判断核心逻辑，容易大范围重写
- 所有代码混在一起，分不清主次

#### 问题2：不知道边界
- 没有标注受保护文件
- 没有明确要求"只改这个文件"
- AI随意修改核心逻辑

#### 问题3：上下文失控
- 已有功能没有文档说明
- AI重复实现或覆盖功能
- 对话太长后，AI忘记前面的关键限制

### 解决思路

**结构化目录 + 版本管理 + 上下文工程**

## AI 开发的三条底线

### 底线1：可回退
```
为什么：AI会犯错
如何做：
  ✅ 每次稳定修改后提交一次版本
  ✅ 每个功能完成都有可恢复节点
  ✅ 没有"后悔能力"的AI开发风险很高
```

**工具**：Git + GitHub（项目的时间机器）

### 底线2：可理解
```
为什么：AI理解项目的质量决定生成质量
如何做：
  ✅ 文件命名要清晰
  ✅ 功能边界要清晰
  ✅ 文档、代码、提示词、配置分层管理
```

**工具**：清晰的项目结构 + 完整的README和Spec

### 底线3：可迭代
```
为什么：产品上线后一定会继续修改
如何做：
  ✅ 第一版不是终点，而是起点
  ✅ 支持加功能、修Bug、改UI
  ✅ 不能迭代的AI项目只是一次性Demo
```

**工具**：良好的代码架构 + 版本管理

## Git：项目的"后悔药"

### 核心功能

| 功能 | 作用 | 对非技术人的意义 |
|------|------|-----------------|
| **版本管理** | 每次修改都可保存成快照 | 完整的修改历史记录 |
| **回退** | 改错了可回到任意历史版本 | "时间机器"功能 |

| **分支** | 同时开发多个功能互不影响 | 平行工作能力 |
| **对比** | 对比两个版本的差异 | 快速定位变化 |

### Git的本质
> **Git = 项目的时间机器**

## Git vs GitHub：本地 vs 云端

| 工具 | Git | GitHub |
|------|-----|--------|
| **定位** | 本地版本管理工具 | 远程代码托管平台 |
| **功能** | 记录版本、分支、合并 | 备份、协作、展示、部署 |
| **需要网络** | ❌ 不需要 | ✅ 需要 |
| **类比** | 办公桌上的档案柜 | 云端共享仓库 |

### 完整的工作流

**Git + GitHub = 本地管理 + 云端协作 + 自动部署**

两者配合才能支持长期开发和持续迭代

## Git 核心概念：三个区域

### 工作区
- 你正在修改的文件
- 代码编辑器里看到的内容
- 操作：编写和修改代码

### 暂存区
- 修改后尚未标记为"准备保存"
- 准备提交的修改集合
- 操作：`git add`（选择性添加文件）

### 版本库
- 已经保存的历史版本
- 通过 `git commit` 从暂存区保存为版本
- 通过 `git push` 上传到GitHub
- 操作：完整的版本快照

### 理解这三个区域 = 理解Git的核心逻辑

## Git 基础命令：四个就够

### 命令1：git status
```bash
查看当前改了什么
- 哪些文件被修改
- 哪些未提交
- 提交前先看状态，确认修改范围
```

### 命令2：git add .
```bash
添加所有修改到暂存区
- 点号代表当前目录所有变更
- 也可指定单个文件名
- 灵活选择要提交的内容
```

### 命令3：git commit -m "message"
```bash
上传到版本库
- 保存一个版本快照
- 描述要写清楚做了什么
- 这是项目历史记录的核心
```

### 命令4：git push
```bash
上传到GitHub远程仓库
- 推送到main分支触发自动部署
- 团队成员和部署平台可获取
```

**非技术人先掌握这四个命令，即可完成日常版本管理**

## 首次提交到GitHub的完整步骤

### 6步走通

```bash
Step 1: git init
  └─ 在项目根目录初始化本地仓库
  └─ 生成隐藏的.git目录

Step 2: git add .
  └─ 添加所有初始代码到暂存区

Step 3: git commit -m "init project"
  └─ 提交初始版本
  └─ 写清楚"初始化项目"

Step 4: git branch -M main
  └─ 设置主分支名称为main

Step 5: git remote add origin <仓库地址>
  └─ 绑定GitHub远程仓库地址

Step 6: git push -u origin main
  └─ 第一次上传代码到GitHub
```

### 后续日常流程
```bash
git status        # 查看改了什么
git add .         # 添加所有改动
git commit -m ""  # 提交版本
git push          # 上传到GitHub
```

## 上下文优化：让AI更好地理解项目

### 问题
每次对话都要重新解释项目结构，AI无法积累对项目的理解

### 解决方案

#### 1. 项目结构清晰
```
ai-content-assistant/
├── src/
│   ├── components/    # 可复用组件
│   ├── pages/         # 页面
│   ├── utils/         # 工具函数
│   └── styles/        # 样式
├── public/            # 静态资源
├── README.md          # 项目说明
├── .cursor/rules      # Cursor规范
└── .env.example       # 环境变量示例
```

#### 2. 清晰的文件命名
- ✅ `useContentGeneration.js` - 清晰的功能
- ❌ `utils.js` - 太模糊

#### 3. 完整的README
```markdown
# AI内容创作助手

## 快速开始
## 文件结构说明
## 核心功能模块
## 开发指南
## 如何修改
```

#### 4. .cursorrules 文件
```
# AI代理行为准则
- 只修改 src/ 目录下的代码
- 不要修改部署配置文件
- 新增功能要先提问
- 修改前必须读README.md
```
