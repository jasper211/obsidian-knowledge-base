# Skill 工程化与 Harness 体系

## 课程定位

**课程**：AI编程与产品开发系列·模块八（工程化深化）
**主题**：从 Vibe Coding 升级到可复用、可控制、可迭代的工程化实践
**核心**：Skill能力体系 + Harness Engineer新角色
**目标**：让 AI 开发从临时发挥升级为标准化流程

## 核心问题：为什么 AI 开发必须工程化

### AI 开发失控的根源

**五大常见场景**：
1. 一次性要求 AI 做完整系统 → 各模块耦合严重、无法单独修改
2. 没有 Spec 就直接生成代码 → AI 按自己理解实现、偏离需求
3. 页面、接口、Prompt 混在一起 → 改一个地方影响其他功能
4. AI 修 Bug 时重写整个项目 → 旧功能丢失、新 Bug 产生
5. 项目变复杂后无法理解全貌 → 代码混乱、迭代困难

**失控的根源**：缺少流程、缺少规范、缺少边界

| 维度 | Vibe Coding | Skill工程化 |

**行业数据**（2026年）：

- 45% 的开发者生成代码含安全漏洞

## AI 开发三条底线

这三条底线是非技术人控制 AI 的核心方法：

### 底线 1：先 Spec 后开发
```
为什么：不写 Spec 就开工 = 让 AI 猜你的需求
做法：先写清楚做什么、输入是什么、输出是什么，再让 AI 动手
本质：用结构化需求替代模糊描述
```

### 底线 2：一次只做一个功能
```
为什么：一次修改只影响少量文件，避免牵一发动全身
做法：一个任务只改一个模块；一个功能只对应一个 Spec
本质：降低修改的影响范围
```

### 底线 3：每次修改必须可测试、可回退
```
为什么：AI 会犯错，需要后悔的机制
做法：修改后立即测试；Git 版本管理；稳定后再提交下一个功能
本质：建立风险隔离机制
```

### 小步迭代原则

**三个选项**：
1. **一个任务只改一个模块** → 修改后立即运行测试
2. **一个功能只对应一个 Spec** → 测试运行 → 稳定后再提交 Git 版本
3. **一次修改只影响少量文件** → Git 版本 → 验证通过后再做下一个功能

**意义**：小步迭代是非技术人控制 AI 的核心方法

## 新角色：Harness Engineer（AI 工程导演）

### 什么是 Harness

Harness = 驾驭 + 连接 + 控制

| 能力 | 含义 | 作用 |
|------|------|------|
| **驾驭** | 掌控 AI 工具的执行方向，不让 AI 自由发挥 | 确定开发方向 |
| **连接** | 把工具、模型、Prompt、Spec、Skill 串联成完整流程 | 组织工作流 |
| **控制** | 通过规范和流程确保 AI 输出符合预期 | 保证质量 |

**本质**：Harness Engineer 不是传统程序员，而是 **AI 工程系统的导演**

### 角色演变

| 时代 | 角色 | 特点 |
|------|------|------|
| **过去** | 程序员 | 写代码；经验藏在脑子里 |
| **现在** | Harness Engineer | 人定义目标，AI 完成执行；经验沉淀为 Skill |
| **未来** | 多 AI 协调者 | 会组织 AI 的人比单点使用 AI 的人更有优势 |

**关键洞察**（2026）：最稀缺的不是会写代码的人，而是**会驾驭 AI 的人**

### Harness Engineer 的六项能力结构

```
1. 产品理解能力
   ↓ 知道要解决什么问题，定义产品方向

2. Spec能力
   ↓ 把需求写成 AI 可执行的规范，越标准越好

3. Skill能力
   ↓ 把流程固化成可复用能力，一次沉淀多次使用

4. Context能力
   ↓ 让 AI 持续理解项目上下文，不丢失历史信息

5. 审核能力
   ↓ 判断 AI 输出是否可靠、是否满足验收标准

6. 工具编排能力
   ↓ 选择 Cursor、Trae、Codex 等合适工具，组合使用

六项能力 = 从 AI 使用者升级为 AI 工程导演
```

## Skill：AI 能力体系的核心

### 什么是 Skill

**定义**：Skill 是 AI 能力模板，是可复用的开发流程

**与 Prompt 的根本区别**：
- **Prompt** = 灵感（一次任务、无标准结构、无法沉淀）
- **Skill** = 资产（一类任务、标准结构、可持续迭代）

| 对比维度 | Prompt | Skill |
|---------|--------|-------|
| **解决范围** | 一次任务 | 一类任务 |
| **存储方式** | 散落在聊天记录里 | 进入项目目录长期复用 |
| **寿命** | 偏临时，用完即丢 | 偏资产，持续迭代 |
| **结构** | 没有标准结构 | 有标准结构（7 要素） |
| **复用能力** | 无法沉淀和复用 | 可以沉淀到 Skill 库 |

### Skill 的五个核心特征

```
特征一：包含输入定义
  ↓ 明确需要什么材料才能开始

特征二：包含执行步骤
  ↓ AI 按什么顺序完成任务（1-2-3-4）

特征三：包含约束条件
  ↓ AI 不能做什么、边界在哪里

特征四：包含输出结果
  ↓ 最终交付什么产物

特征五：包含验收标准
  ↓ 如何判断任务完成、什么算合格

Skill 让 AI 开发从临时发挥变成按流程执行
```

### Skill 的标准结构（7 要素）

```
1. Skill名称 - 解决哪类问题，一目了然
2. 适用场景 - 什么时候使用这个 Skill
3. 输入材料 - 需要 PRD、Spec、文件、日志还是截图
4. 执行步骤 - 分解成可复制的步骤序列（1-2-3-4）
5. 约束条件 - 不能做什么，边界和禁区
6. 输出结果 - 修改文件列表、测试方法、变更说明
7. 验收标准 - 如何判断完成、什么算合格

结构完整 = AI 可以稳定执行
```

### 从 Prompt 到 Skill 的转化路径

```
第一步：用 Prompt 成功完成一次任务
  ↓ 先跑通一次，证明思路可行

第二步：复盘成功原因，提炼输入材料
  ↓ 分析这次为什么成功，哪些条件是关键的
  ↓ 总结需要什么输入才能复现成功

第三步：拆出执行步骤，写入约束和验收标准
  ↓ 把成功路径拆成可复制的步骤序列
  ↓ 明确边界和完成判断条件

第四步：保存到 Skill 库
  ↓ 以标准格式保存，方便下次直接调用

核心原则：
  • 每次成功都值得沉淀
  • 每次失败都可以变成 Skill 约束条件
```

## 实战 Skill 类型案例

### 1. UI Skill：页面生成与优化

```
输入：页面目标、风格要求、组件列表、交互说明
输出：页面结构、组件代码、样式文件
适用场景：工具站、落地页、后台页面、小程序页面

约束条件：
  • 不加入无关业务逻辑
  • 不引入未要求的外部依赖
  • 不修改非当前页面的文件

验收标准：
  • 页面可正常渲染
  • 交互功能符合 Spec
  • 移动端布局基本适配
```

### 2. API Skill：接口接入与安全

```
输入：接口文档、请求参数、返回格式、错误码说明、测试方法
输出：API 调用函数、错误处理逻辑

约束条件：
  • 密钥不能写死在前端代码
  • 必须加入错误处理和超时机制
  • 返回格式必须做校验

验收标准：
  • API 调用成功返回预期数据
  • 异常情况有友好提示
  • 密钥不存在于前端源码

核心：安全是 API Skill 的第一优先级
```

### 3. 数据库 Skill：表设计与读写

```
输入：业务对象、字段定义、权限需求、查询场景
输出：表结构设计、读写函数、权限建议

约束条件：
  • 不同用户数据必须隔离
  • 敏感字段必须加密存储
  • 删除操作必须软删除

验收标准：
  • 数据读写正常
  • 用户只能访问自己的数据
  • 异常情况不丢失数据

适用场景：历史记录、用户偏好、订单数据、会员次数

核心：数据隔离 + 加密 + 软删除
```

### 4. 部署 Skill：上线检查与平台部署

```
输入：项目类型、部署平台、构建日志、环境变量清单
输出：部署步骤、环境变量配置、排错建议

适用场景：Vercel、EdgeOne Pages、云服务器部署

约束条件：
  • 上线前必须检查环境变量
  • 密钥必须通过环境变量注入
  • 构建失败不允许部署

验收标准：
  • 公网可访问
  • 页面样式正常
  • API 调用正常
  • 密钥不暴露

意义：确保每次上线都有检查清单
```

### 5. Bug Skill：修复受控流程

```
输入：报错日志、复现步骤、相关文件
执行步骤：
  1. 先解释原因
  2. 再定位文件
  3. 再最小修改

输出：修复方案、修改文件、测试方法

约束条件：
  • 禁止直接重写整个项目
  • 禁止修改与 Bug 无关的文件
  • 必须保留原有功能

验收标准：
  • 报错消失
  • 原功能不受影响
  • 修改范围最小化

铁律：只改该改的，不多改一行
```

### 6. Prompt Skill：优化让 AI 输出更可控

```
输入：原始 Prompt、当前生成结果、目标效果
执行步骤：
  1. 分析问题出在哪里
  2. 重构角色定义
  3. 约束输出格式

输出：新版 Prompt、测试案例、对比效果

适用场景：内容生成、结构化输出、多平台模板

验收标准：
  • 输出更稳定，多次执行结果一致
  • 输出更短更精炼
  • 输出格式可控，不出现多余解释
```

## Spec 标准化：从模糊需求到可执行规范

### 为什么 Spec 要标准化

**AI 的视角**：Spec 越标准，AI 输出越可控
- 没有标准 Spec，AI 每次理解都不同
- 标准化 Spec 让 AI 输出有据可依

**人的视角**：Spec 定义了完成标准
- Spec 越标准，Skill 越容易复用
- 标准化 Spec 可以直接映射到 Skill 输入

**项目的视角**：
- 降低 Skill 编写和复用门槛
- 标准化是非技术人掌控复杂项目的关键

### PRD 结构化写法（结构化产品需求）

```
1. 用户是谁
   ↓ 明确目标用户画像和使用场景

2. 解决什么问题
   ↓ 核心痛点和价值关系

3. 核心功能有哪些
   ↓ 列出 MVP 必须包含的功能清单

4. 页面结构是什么
   ↓ 主要页面面和导航主张

5. 使用场景是什么
   ↓ 什么时候用、在哪用、怎么用

6. 输入输出是什么
   ↓ 每个功能的输入字段和输出结果

7. 边界是什么
   ↓ 哪些做、哪些不做，明确范围

结构化 PRD = AI 可理解的需求说明书
```

### AI 可执行 Spec 模板

```
feature: 小红书发布包生成

inputs:
  - topic: 用户输入的主题
  - style: 内容风格
  - audience: 目标人群
  - keywords: 关键词

outputs:
  - titles: 标题建议
  - body: 正文内容
  - hashtags: 话题标签
  - coverTexts: 封面文案

constraints:
  - 不生成夸大宣传
  - 返回 JSON 格式

acceptance_criteria:
  - 输入主题后能生成内容
  - 结果可复制
  - 格式正确可解析

AI 可执行 Spec = AI 能直接理解并执行的任务说明书
```

## AI 开发的五大风险

### 1. AI 生成代码的五类风险

```
风险一：逻辑看似正确但实际错误
  ↓ 边界情况处理不当

风险二：正常流程没问题，异常情况直接崩溃
  ↓ 缺少异常处理和测试

风险三：修新 Bug 引入旧 Bug，牵一发动全身
  ↓ 缺少影响范围控制

风险四：编造 API 名称或使用已废弃的方法
  ↓ AI 幻觉问题

风险五：每次生成后必须运行测试
  ↓ 不能只看代码就通过

结论：对 AI 生成的代码保持健康的怀疑态度
```

### 2. 上下文污染问题

**症状**：长对话中混入过多历史需求，旧需求和新需求相互冲突

**解决方案**：
```
方案一：重新整理 Spec
  ↓ 把当前有效的需求整理成独立文档
  ↓ 让 AI 基于最新 Spec 工作

方案二：不同功能不同对话
  ↓ 避免历史上下文干扰新任务
  ↓ 每个功能单独开启任务

方案三：把项目规范写入配置文件
  ↓ 使用 CLAUDE.md 或 .cursorrules
  ↓ 每次会话自动加载，不依赖对话历史

结论：对话越短，AI 越准；上下文越干净，输出越稳
```

### 3. AI 幻觉问题

| 幻觉类型 | 表现 | 应对方法 |
|---------|------|--------|
| **幻觉一** | 编造 API 字段（不存在的参数、虚构的返回格式） | 关键技术点要查官方文档（不轻信 AI） |
| **幻觉二** | 编造平台能力（假设平台支持实际上没有的功能） | 涉及支付、备案、平台发布必须人工核实 |
| **幻觉三** | 假设不存在的文件（引用项目中根本不存在的代码文件） | 用 Spec 约束输出格式（限定 AI 只能在已知范围内操作） |

**原则**：AI 很自信，但自信不等于正确

### 4. 不适合 AI 直接开发的场景

```
❌ 高风险支付系统
   ↓ 涉及资金流转，必须人工设计和审核

❌ 医疗法律金融核心决策
   ↓ 影响人身安全和重大财产，不能依赖 AI

❌ 大规模复杂重构
   ↓ 影响范围太广，AI 可能引入不可控变更

❌ 高安全要求系统
   ↓ 涉及用户隐私和敏感数据，必须严格把控

❌ 没有测试和审核的生产系统
   ↓ AI 生成的代码必须经过测试才能上线

❌ 合规要求严格的领域
   ↓ 涉及法规和行业标准，需要人工确认

结论：AI 可以辅助，但不能无审核上线
```

## AI 项目级配置最佳实践

### 三个配置文件的作用

```
1. .cursorrules 文件
   ↓ Cursor 自动读取的项目规范
   ↓ 定义技术栈、编码规范、架构约束
   ↓ 每次会话自动加载

2. CLAUDE.md 文件
   ↓ Claude Code 自动读取的配置文件
   ↓ 定义核心原则、禁止行为、项目结构
```

## AI 编程安全清单

### 六大检查项

```
✅ 检查一：密钥管理
   条件：密钥不在代码中硬编码
   做法：API Key 只通过环境变量注入

✅ 检查二：代码审核
   条件：AI 生成代码经过人工审核
   做法：关键逻辑必须人工确认

✅ 检查三：依赖安全
   条件：第三方 Skill 和依赖经过审查
   做法：不安装来源不明的扩展

✅ 检查四：对话安全
   条件：上下文不包含敏感信息
   做法：对话中不输入密码和密钥

✅ 检查五：版本管理
   条件：每次修改前 Git 提交
   做法：确保可以回退到稳定版本

✅ 检查六：上线安全
   条件：生产系统不直接部署 AI 代码
   做法：必须经过测试和审核流程

结论：安全不是可选项，是 AI 开发的底线
```

## Harness Engineer 成长路径

### 四阶段进化

```
第一阶段：Vibe Coder
  ├─ 能用 AI 做出东西
  ├─ 但 Prompt 散落各处
  ├─ 结果不稳定，不可复现
  └─ 没有沉淀

      ↓ 能力升级

第二阶段：Prompt Engineer
  ├─ 能写出好 Prompt
  ├─ 理解 AI 工作原理
  ├─ 把提示词优化到极致
  └─ 但还是离散的能力

      ↓ 系统化升级

第三阶段：Skill Builder
  ├─ 能把经验沉淀为 Skill
  ├─ 能复用已有能力
  ├─ 不重复造轮子
  └─ Skill 有标准流程

      ↓ 系统协调升级

第四阶段：Harness Engineer
  ├─ 能编排多个 Skill 形成完整链路
  ├─ 能驾驭多种 AI 工具协同
  ├─ 工作流程稳定产出
  └─ 控制 AI 工程系统

每个阶段都是一次能力升级，目标是从被动使用到主动驾驭
```

### 成长建议

```
1. 从最小 Skill 开始
   ↓ 不要一次写复杂 Skill
   ↓ 先写最简单的版本

2. 每次失败都是 Skill 约束条件
   ↓ 记录什么不能做，比记录什么能做更重要
   ↓ 把失败经验沉淀成约束

3. 定期清理和更新 Skill
   ↓ 过时的 Skill 及时归档
   ↓ 避免误导

4. 团队共享统一 Skill 库
   ↓ 个人 Skill 逐步上升为团队标准
   ↓ 把 CLAUDE.md 和 Skill 结合
   ↓ 项目规范写配置文件，流程写 Skill

核心：Skill 化是一个持续积累的过程，不是一次性的工程
```
