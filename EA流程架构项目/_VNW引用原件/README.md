# _VNW引用原件/

VNW需要引用、但性质上不该走OB白名单原子提炼的EA项目源文件——L3流程蓝图、
D1-D6打分方法论定义、D1-D6全量打分表、岗位L4映射材料。这些是项目组成员
产出的工作材料，不是"成型的方法论文档和结果文档"，跟`EA流程架构项目/`
其余文件（全部是LLM提炼出的concept_atom/entity_hub）性质不同，不要把
这个文件夹里的文件当成知识原子处理（没有`type: concept_atom`
frontmatter，不参与聚类/枢纽机制）。

## 同步机制

由`sync_vnw_reference_files.py`原样镜像，**不做任何提炼、不改内容**，只做
"存在性+最新版本"同步：
- 每天跟`ob-daily-extract`同一个定时任务一起跑（launchd
  `com.jasper.ob-daily-extract`，凌晨2点+开机补跑，已验证真实在跑，日志
  见`/tmp/ob-vnw-reference-sync.log`），增量同步（按内容哈希，没变化的
  文件不重复写入）
- L3流程蓝图、以及2026-07-29新增的VN/KPI/L4两阶段复核材料，只要版本号是
  紧贴扩展名的写法（如`..._V3.44.xlsx`），都会自动识别同名前缀下版本号
  最大的文件，同事更新到新版本号（哪怕换了文件名）**不需要人工干预**
  ——`_prune_stale()`还会顺手把vault里的旧版本文件清掉，不会永久堆积。
- DICT数据字典、68L3岗位族归属设计、dim_kpi权威层这3份**版本号不在文件名
  末尾**（后面还跟着日期/状态后缀，自动识别容易误判），只能整份镜像，
  这3份出新版本时，新文件名需要有人(维护这些文件的同事，或Jasper)手动
  加进`VNW_REFERENCE_SOURCES`——这是本机制唯一还需要人盯着的触点。
- 源文件路径+同步时间记录在`_manifest.json`（溯源用，不是给人读的）
- **`.xlsx`源文件会额外多一份同名`.md`**（2026-07-29新增）：vault检索用的
  `obsidian-mcp-server`索引器只认纯文本（.md/.csv/.txt），.xlsx是二进制
  格式，原样镜像了也搜不到——所以.xlsx除了保留原件（可以在Obsidian里直接
  打开/下载），还会自动生成一份逐sheet转成markdown表格的纯文本版供检索，
  转换是机械的（openpyxl读单元格值，不筛选不总结），两份都会随源文件更新
  自动同步。**看到`.md`版本时，格式/公式以`.xlsx`原件为准，不要把转换版
  当成权威格式。**

    结论。同目录下另有"最终版"/"理想化版"/"确认最终版"（无版本号）三份

    这一支）

**5、6、8、9、10会自动跟上新版本**（按文件名前缀+末尾版本号匹配，同目录下
多个历史版本/不同标签文件平铺存放也没关系，只要目标文件名末尾是
`_v数字.扩展名`这个格式）。**7（dim_kpi）连同2、4**版本号不在文件名末尾，
自动匹配不安全，仍需人工更新文件名。

新增引用源：在`sync_vnw_reference_files.py`的`VNW_REFERENCE_SOURCES`列表
里加一条即可，不需要改同步逻辑。
