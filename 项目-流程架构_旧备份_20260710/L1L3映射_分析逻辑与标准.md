# L1-L3 映射分析逻辑与标准

> 文档类型：架构治理规范

## 一、架构层级体系

本项目采用 L1→L5 五层架构，各层含义如下：

| 层级 | 名称 | 定义 | 数量 |
|------|------|------|------|
| **L1** | 价值链节点 | 企业唯一价值链的战略活动分解（BIZBOK：一条价值链） | 5个 |
| **L2** | 业务能力 | 使能 L1 的稳定能力集合（"我们能做什么"） | 18个 |
| **L3** | 端到端流程 | 实现业务能力的跨部门可执行流程 | 82个 |
| **L4** | 流程模块 | L3 内的原子工作单元，必须对应唯一物理交付物 | 若干 |
| **L5** | 经营活动 | L4 内的具体执行步骤序列 | 若干 |

**层级关系**（BIZBOK 标准）：
```
L1 价值链节点
  └── L2 业务能力（enabled by）
        └── L3 端到端流程（realized by）
              └── L4 流程模块（decomposed into）
                    └── L5 经营活动
```

## 二、L1 权威定义

权威来源：价值流与价值链方法论纠偏.md 第四节 4.1（Mark 裁定）

| 编码 | 名称 | 核心职能 | 内部简称 |
|------|------|----------|----------|
| **L1-01** | 资源获取与产品整合 | 战略制定、市场洞察、风险识别、价值主张设计、保司资源整合 | MCV战略 |
| **L1-02** | 市场设计与合作伙伴发展 | 渠道拓展、合作伙伴引入与上架、市场进入设计 | 合作网络 |
| **L1-03** | 运营反馈与路由决策 | 运营执行监控、佣金路由、流程决策、反馈闭环 | 决策中枢 |
| **L1-04** | 能力赋能与增长驱动 | 能力建设、工具开发、赋能体系、联合运营设计 | 能力引擎 |
| **L1-05** | 价值增值与生态绑定 | 权益管理、客户留存、续约、价值交付与核算、生态合作执行 | 权益中台 |

**4个正反馈闭环**（来自"价值破局"战略文档）：
```
L1-01 ←── 资源精准反馈  ──── L1-03
L1-02 ←── 市场需求反馈  ──── L1-03
L1-04 ←── 代理人能力提升 ─── L1-03
L1-03 ←── 客户体验反馈  ──── L1-05
```

## 三、L3 归属 L1 的判断逻辑

### 3.1 核心判断问题

对任意一个 L3 流程，依次回答以下三个问题：

```
Q1：这个流程的主要目的是什么？
  ├── 制定战略 / 分析市场 / 整合保司资源    → 候选 L1-01
  ├── 引入合作伙伴 / 渠道拓展 / 机构上架    → 候选 L1-02
  ├── 运营执行 / 路由决策 / 合规管控        → 候选 L1-03
  ├── 建设能力 / 赋能工具 / 联合运营方案    → 候选 L1-04
  └── 权益交付 / 客户绑定 / 结算续约        → 候选 L1-05

Q2：这个流程的主要受益方是谁？
  ├── 平台本身（战略决策支持）              → 偏 L1-01
  ├── 外部合作伙伴（机构/保司）入驻前       → 偏 L1-02
  ├── 内部运营团队（执行、决策、合规）      → 偏 L1-03
  ├── 内部能力建设团队 / 被赋能的渠道方     → 偏 L1-04
  └── 已入驻客户 / 合作伙伴（价值持续交付）→ 偏 L1-05

Q3：这个流程在客户/合作伙伴生命周期的哪个阶段？
  ├── 尚未进入（洞察/设计/整合期）          → L1-01
  ├── 正在引入（谈判/签约/上架期）          → L1-02
  ├── 运营中（执行/监控/路由期）            → L1-03
  ├── 成长中（赋能/培训/工具建设期）        → L1-04
  └── 深化中（权益/续约/价值沉淀期）        → L1-05
```

### 3.2 六类典型归属模式

**模式一：战略分析 → L1-01**

包含"洞察""战略""市场进入""风险评价""价值主张""可行性"等关键词的流程，无论其名称中是否含有"市场"，均归 L1-01。

> 典型案例：L3-MIO（市场洞察与机会识别）、L3-SRE（战略风险评价）、L3-CAS（竞争与获客策略）
> 易混淆点：含"市场"不等于归 L1-02；L1-02 的"市场"是渠道拓展，L1-01 的"市场"是洞察与策略。

---

**模式二：合作伙伴引入 → L1-02**

专注于合作伙伴（保司、机构、KA）的**进入前**阶段：接触、评估、谈判、授权、上架准备。一旦合作伙伴已进入平台，后续运营和赋能分别归 L1-03/L1-04。

> 典型案例：L3-IAC（保司授权与合作框架）、L3-KAOP（KA上架准备）、L3-THBOB（同行经代入驻准备）
> 易混淆点：L3-COM（佣金管理）看似与合作伙伴相关，但属于"入驻后的结算路由"，归 L1-03。

---

**模式三：执行路由与合规 → L1-03**

流程核心是**执行、监控、路由、合规判断**，而非建设能力或交付价值。输出物是决策结果、合规记录、执行反馈，而非产品或权益。

> 典型案例：L3-COM（佣金全链路管理）、L3-EFB（任务管控与执行反馈）、L3-UCR（合规风险评估）
> 易混淆点：L3-USV（运营服务事项设计与内部验证）虽含"设计"，但其产出是内部验证结论，归 L1-03 而非 L1-04。

---

**模式四：能力建设与赋能 → L1-04**

流程产出是**可复用的能力资产**：培训体系、合同模板、知识库、联合运营方案框架、技术工具。区别于 L1-03 的执行，L1-04 是在"建工具"而非"用工具"。

> 典型案例：L3-SKM（知识资产与内容管理）、L3-UCT（定制化合同模板开发）、L3-URF（联合运营资源规整与框架方案设计）
> 易混淆点：L3-RSJD（经代机构销售业务执行）表面是"执行"，但其本质是生态合作伙伴的价值绑定，归 L1-05。

---

**模式五：权益交付与价值绑定 → L1-05**

**权益产品全生命周期**（设计→上架→推广→交付→评估→续约）及**客户深化**（入驻后的服务启动、关系深化、合同签订、续约决策）均归 L1-05。L1-05 是"横切能力层"，服务于多条价值流，但在价值链上是独立的。

> 典型案例：L3-RPD（权益包设计与发布）、L3-CRR（客户关系深化与续约决策）、L3-SSVA（服务结算与价值核算）
> 易混淆点：含"合同"的流程不自动归 L1-03。权益合同（L3-CDS）归 L1-05，因为合同是价值绑定的法律载体；运营合同（L3-SDS）归 L1-03，因为合同是运营路由的执行凭证。

---

**模式六：横切能力（L1-05 特殊子集）**

L1-05 中存在一类**横切能力**：由中台统一管理、被多条价值流消费的流程。这类流程不属于任何单一价值流（VS），但在价值链上归 L1-05。

| 横切能力 L3 | 名称 | 跨哪些 VS 被消费 |
|------------|------|----------------|
| L3-CFRM | 客户反馈与权益需求再挖掘 | VS-2、VS-4、VS-5 |
| L3-SRA | 服务需求诊断与分析流程 | VS-2、VS-3、VS-5 |
| L3-SPD | 服务流程配置与培训 | VS-2、VS-3、VS-4、VS-5 |

| 易混淆场景 | 错误归属 | 正确归属 | 判断依据 |
|-----------|---------|---------|---------|

## 四、强制规则

### 规则 1：L3 单属一 L1

> 每个 L3 编码在 `fact_activity` 表中必须且只能归属一个 L1 编码。
> 同一 L3 的所有行（无论 L4/L5 如何切分）的 `l1_code` 和 `l1_name` 必须完全一致。

**违规检测 SQL**：
```sql
SELECT l3_code, COUNT(DISTINCT l1_code) as l1数量
FROM fact_activity
GROUP BY l3_code
HAVING COUNT(DISTINCT l1_code) > 1;
-- 应返回空结果
```

**当存在跨 L1 分裂时**，以多数行所在的 L1 为候选，同时参考 L3 名称语义裁定，不得两者各取一半。

---

### 规则 2：L1 名称必须使用权威定义

不得使用括号内的内部简称（如"MCV战略""决策中枢"）作为 `l1_name` 字段值。

| 字段值（强制） | 禁止使用的别名 |
|--------------|--------------|
| 资源获取与产品整合 | 战略与方案赋能、MCV战略、L1-01 MCV战略 |
| 市场设计与合作伙伴发展 | 销售网络与市场深耕、保司资源整合 |
| 运营反馈与路由决策 | 决策中枢、合作伙伴赋能 |
| 能力赋能与增长驱动 | （无已知别名） |
| 价值增值与生态绑定 | 价值增值与客户绑定、L1-05权益中台 |

---

### 规则 3：L4 唯一物理交付物原则

（来源：Mark 裁定，2026-04-11 M2 G3-5）

每个 L4 必须对应**唯一**的物理交付物（文档/数据表/系统记录/签字文件/凭证）。`physical_deliverable` 字段不得为空，不得填写动作描述（"完成沟通"）或状态变化（"已就绪"）。

---

### 规则 4：L3 归属变更必须留有裁定记录

任何对 `l1_code` 的修改必须记录：

- 修改前后的 L1 编码
- 变更依据（逻辑清晰 / 人工裁定）
- 裁定类别（A类：无需讨论直接更新 / B类：需人工确认）
- 影响行数

## 五、裁定流程

### 5.1 A 类异常（逻辑清晰，直接 UPDATE）

满足以下**全部**条件时，无需人工讨论：

1. L3 名称与当前 L1 定义**明显不符**（用第三节判断逻辑可快速定位）
2. 目标 L1 唯一且无歧义
3. L3 名称与目标 L1 的核心职能**高度吻合**

> 示例：L3-SDSA（市场数据分析与决策支持）原归 L1-04，但属于战略分析型流程，唯一候选 L1-01，直接 UPDATE。

### 5.2 B 类异常（需人工裁定）

满足以下**任一**条件时，需生成裁定方案文档供人工确认：

1. 目标 L1 存在两个合理候选（语义有交叉）
2. L3 名称本身有歧义，需结合 L4/L5 内容判断
3. 修改会影响已有报告或下游关联分析
4. 当前归属与历史裁定记录冲突

**B 类裁定文档格式**：
```markdown
### L3-XXX | [L3名称]
**当前归属：** L1-XX [名称]
**建议归属：** L1-XX [名称]
**背景：** [1-2句描述该流程的业务场景]
**理由：** [与目标L1核心职能的对应关系]
**裁定：** ✅ 更新为 L1-XX / ⚠️ 维持不变
```
