## 一、定位与核心原则

### 1.1 两份核心交付物的区别

| 交付物 | 格式 | 定位 | 消费方 |
|--------|------|------|--------|
| **D1_价值节点清单_V3.0.xlsx** | Excel（6 Sheets） | **业务视角**：价值节点的完整属性卡、评估矩阵、行动清单 | Mark（裁定）、Carrie（数据库回写） |
| **D2_价值节点_L3映射表_V1.0.csv** | CSV（GBK 编码） | **权威数据**：价值节点 ↔ L3 一对一/多对一映射、评分快照、熔断状态 | 数据底座层、下游脚本、流程监控表 |

> **核心原则**：D2 是 D1 的**结构化导出视图**，不是独立产物。任何 D2 的变更必须先在 D1 中完成评估，再通过 `D3_L3调整记录` 登记。

### 1.2 价值节点的定义（Mark V3.0）

价值节点（Value Node, VN）是**L3 流程闭环内凝结成的物理资产**，不是 L4 动作的简单罗列，而是多个 L4 咬合后产生的、可被审计和度量的交付物单元。

```
判断标准：一个价值节点必须同时满足
├─ 有明确的物理形态（文件/表单/系统记录）
├─ 有数据字段可与数据库表关联
├─ 有业务锚点（保单/客户/月份/主体）
├─ 有明确的责任主体（A/R/C/I）
└─ 有 KPI 可度量其产出质量
```

## 二、方法论框架：4属性 + 3Gate + 双锚定

### 2.1 四大硬性属性（Hard Attributes, HA）

| 属性编码 | 属性名 | 判定标准 | D2 字段 |
|----------|--------|----------|---------|
| HA-1 | **物理载体** | 有可触摸、可传递、可审计的物理形态 | `vn_physical_form` |
| HA-2 | **数据属性** | 包含可被系统识别的数据字段，能与数据库表关联 | `attr2_value_property` |
| HA-3 | **业务锚点** | 能锚定到具体业务场景（保单/客户/月份/主体） | `attr1_business_position` |
| HA-4 | **责任人** | 有明确的责任主体（A accountable） | `attr4_data_validation` |

**评分规则**：
- `PASS`：属性完整满足，有明确证据
- `PARTIAL`：部分满足，存在缺口但可补强
- `FAIL`：关键缺失，无法补救或成本过高
- `WARN`：待确认，缺乏足够信息判定

### 2.2 三重验证 Gate

| Gate 编码 | Gate 名 | 核心问题 | D2 字段 |
|-----------|---------|----------|---------|
| G-1 | **凭证性 Gate** | 是否有可追溯的凭证链（审批记录/系统日志/邮件确认）？ | `gate1_data_linked` |
| G-2 | **数据闭环 Gate** | 数据能否在数据库中形成闭环（输入→处理→输出可追溯）？ | `gate2_grounded` |
| G-3 | **权责清晰 Gate** | 制作/审核/使用三权是否物理分离？ | `gate3_traceable` |

**Gate 评分规则**：
- `PASS`：Gate 完全通过，有完整证据链
- `PARTIAL`：部分通过，存在弱环节但不致命
- `FAIL`：Gate 未通过，存在结构性缺口

**熔断规则**：
```
IF (G-1 == FAIL AND G-2 == FAIL AND G-3 == FAIL)
    → P0 强熔断（最高优先级，如 VN-PAY-04 IA合规生命线）
ELSE IF (任意 2 个 Gate == FAIL)
    → P0 熔断（如 VN-PAY-09 BP V2 缺失）
ELSE IF (任意 1 个 Gate == FAIL)
    → P0 规范化（需补强）
ELSE IF (任意 Gate == PARTIAL)
    → P1（次优先级规范）
ELSE
    → 通过
```

### 2.3 M 锚定与 KPI 锚定

| 锚定类型 | 说明 | D2 字段 | 示例 |
|----------|------|---------|------|
| **M 锚定** | 价值节点在 M0-M8 战略闭环中的位置 | `m_anchor` | `M0触发→M6产出→M8归档` |
| **KPI 锚定** | 可度量的业务指标 | `kpi_anchor` | `佣金产出包准确率 ≥ 99.5%` |

**M0-M8 框架定义**：
- M0：业务触发点
- M1：需求输入
- M2：业务处理
- M3：审核校验
- M4：授权决策
- M5：执行动作
- M6：结果输出（物理交付物产出）
- M7：确认闭环
- M8：归档追溯

### 3.2 Phase 2 核心步骤详解：价值节点识别与收敛

#### 步骤 2.3.1：读取历史基线

**输入**：
- `D2_价值节点_L3映射表_V1.0.csv`（历史版本，GBK 编码）
- `L1_L3映射表_最终版.csv`（82 条标准 L3）
- `dim_process` 数据库当前状态

**规则**：
- 若调研涉及的 L3 在 D2 历史基线中**已存在**，沿用其 VN 编码，更新评分
- 若 L3 在 D2 历史基线中**不存在**，进入新增价值节点流程
- 若 L3 被标记为**废弃**，在 D3 中登记，D2 中保留记录但标记 `is_fused=FALSE`

#### 步骤 2.3.2：L4 → 价值节点收敛（关键）

**收敛原则**：多个 L4 在 L3 闭环里咬合后，凝结成一个物理资产 = 一个价值节点。

**致命反例检测**（Mark 强制规则）：

| 反例编号 | 问题描述 | 检测规则 | 收敛动作 |
|----------|----------|----------|----------|
| 反例① | 服务类 L3 被拦腰斩断为三件套 | 7 个服务商 L3 的 L4 数 > 14 | 收敛到单一 VN（如 VN-PAY-05） |
| 反例② | 付款执行被切碎为独立交付物 | COM-14~18 + STLM 重复 > 5 | 收敛到单一 VN（如 VN-PAY-04） |
| 反例③ | FPG 全空但立为交付物 | FPG 交付物空率 > 70% | 归并到邻近 VN 并熔断 |

**收敛后的价值节点编码规则**：
```
VN-{板块}-{序号}
  ├── VN-PAY-01~09  财务支付板块
  ├── VN-MGA-01~03  MGA 板块
  ├── VN-EQ-01      权益板块
  └── VN-{新增板块}-{序号}  新增板块（需 Mark 确认）
```

#### 步骤 2.3.3：4属性 + 3Gate 人工评分

**评分者**：Terresa（初评） → Mark（复核）

**评分流程**：
1. **HA 评分**：基于调研 Excel 中的 `L4交付物明细` 和 `痛点` 字段，逐条判定
2. **Gate 评分**：基于 HA 评分结果和 dim_process 数据关联状态，逐 Gate 判定
3. **综合判定**：按熔断规则计算 `overall_judgment`
4. **优先级标记**：
   - P0：涉及合规/审计/资金安全，必须立即处理
   - P1：涉及效率/体验/成本，次优先级规范
   - P2：建议性优化，可排期处理

#### 步骤 2.3.4：产出 D1_价值节点清单（Excel）

**6 Sheets 标准结构**：

| Sheet | 内容 | 来源 |
|-------|------|------|
| 0_方法论与说明 | V2.0 vs V3.0 对比、4属性定义、3Gate定义、M0-M8定义、熔断规则 | 方法论模板 |
| 1_价值节点总览 | 节点ID、L3闭环、物理资产、构成、形态、M锚定、KPI、裁定结论 | 映射表 + dim_process |
| 2_节点详情卡 | 每张 VN 的完整属性卡（4属性+3Gate+M锚定+KPI+Next动作） | 自动填充模板 |
| 3_四属性三重验证矩阵 | Gate 着色 + 综合判定公式 | 评分结果 |
| 4_M0-M8锚定矩阵 | 节点在 M0-M8 中的位置 | 映射表固定字段 |
| 5_熔断与行动清单 | 熔断原因、致命缺口、裁定责任人、行动事项、里程碑 | 根据差异项推导 |

### 4.2 关键字段生成规则详解

#### `is_fused`（融合标记）

```
IF 该 VN 由多个 L3 的 L4 收敛而成
    → is_fused = TRUE
    → notes 必须注明收敛原因（如"付款执行被切碎，收敛到VN-PAY-04"）
ELSE IF 该 VN 为单一 L3 的原生产物
    → is_fused = FALSE
```

**示例**：
- VN-PAY-04（转介费派发确认台账）：`is_fused=TRUE`，由 L3-COM 的 L4-COM-14~18 + L3-STLM 的 L4-STLM-04/05 收敛
- VN-PAY-01（市场佣金制作产出包）：`is_fused=FALSE`，为 L3-COM 的原生产物

#### `overall_judgment`（综合判定）

综合判定由 **4属性评分 + 3Gate 评分 + 业务优先级** 共同决定：

| 条件 | 结果 | 颜色标记 |
|------|------|----------|
| 任意 Gate == FAIL 且 attr3/attr4 == FAIL | **P0强熔断** | 🔴 |
| 任意 2 个 Gate == FAIL | **P0熔断** | 🟠 |
| 任意 1 个 Gate == FAIL | **P0规范化** | 🟡 |
| 无 FAIL 但存在 PARTIAL | **P1** | 🔵 |
| 全部 PASS | **通过** | 🟢 |

#### `vn_composition`（组成描述）

必须按以下模板填写：
```
{L4-A名称} + {L4-B名称} + ... + {咬合点描述}
```

**示例**：
- VN-PAY-05：`服务值台账入口 + 服务值汇总表（含成本+服务费+供应商）`
- VN-PAY-04：`转介费申请审批 + 转介费银行执行 + 转介费归档与对账`

## 七、脚本工具与操作步骤

### 7.1 半自动化脚本清单

| 脚本 | 功能 | 输入 | 输出 | 阶段 |

## 九、附录：典型价值节点生成示例

### 示例：VN-PAY-04（转介费派发确认台账）

**背景**：佣金付款执行被切碎为 10 条独立 L4（申请→审核→授权→支付→归档），违反"不能拦腰斩断 L3"原则。

**收敛动作**：
1. 识别所有涉及付款执行的 L4：`L4-COM-14~18`、`L4-STLM-04~05`
2. 判定这些 L4 咬合后凝结的物理资产：`支付审批单 + 银行回执 + 台账记录`
3. 填写 `vn_composition`：`转介费申请审批 + 转介费银行执行 + 转介费归档与对账`
4. 评估 4属性：
   - HA-1（物理载体）：PASS（有支付审批单+银行回执）
   - HA-2（数据属性）：FAIL（与 FACT_PAID_LEDGER 未匹配）
   - HA-3（业务锚点）：PASS（牌照+月份+拨出率）
   - HA-4（责任人）：PARTIAL（JorJor/Chaya/NANA/SOSO 混用）
5. 评估 3Gate：
   - G-1（凭证性）：FAIL（审批链不完整）
   - G-2（数据闭环）：FAIL（与 FACT_PAID_LEDGER 未匹配）
   - G-3（权责清晰）：FAIL（申请/审核/支付三权未分离）
6. 综合判定：**P0强熔断**（3 Gate 全失，IA合规生命线）
7. 标记 `is_fused=TRUE`，`priority=P0强熔断`
8. 备注：`IA合规硬指标未达标，需Mark+Carrie联合裁定`

---

> **结语**：本方法论的核心是 **"L4 咬合凝结为物理资产 → 价值节点 → 4属性3Gate评估 → 综合判定 → D2 映射表冻结"**。任何调研工作若偏离此原则，需在 D3 调整记录中登记偏差原因。
