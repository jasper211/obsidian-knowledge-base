## 〇、先看懂这张大图（最重要的一句话）

这 27 个问题，**不是 27 个都还没做**。按平台真实进度分三档：

| 档位 | 是什么 | 涉及问题 | 访谈时该聊什么 |
|---|---|---|---|
| **🟢 已实现** | 平台里早就跑着的逻辑，问题问的其实是"它是怎么做的" | EFA 线绝大多数（佣金链=母项目，Carrie 已建 60~70%） | 把现有逻辑讲清楚，确认口径对不对，补"留痕/审批"这层治理皮 |
| **🟡 部分实现** | 核心算出来了，但有个别字段/校验还缺源或没编码 | FIN 应收链、收款人映射、拨出率红线 | 确认缺的那一块由谁补、什么时候补 |
| **🔴 仅规划** | 只有设计文档，一行代码都还没写 | FIN 应付链、权益 hold、协议参数中心化、体系外资金 | 这才是真正要"裁定方向 + 排期 + 给资源"的硬骨头 |

**一句话总结**：
- **EFA 线（市场佣金链）= 母项目，大部分🟢已实现**，访谈重点是"把已有逻辑讲明白 + 补治理留痕"。
- **FIN 线（财务结算）= 子项目沙箱期**，应收🟡跑通了，**应付/权益/体系外🔴还只是设计**，这是真缺口。

## 一、EFA 线（市场佣金链 = 母项目，多数已实现）

> 这条线对应的 `config_partner_routing`、`partner_tier_rules`、`fact_commission_rate`、`agg_*` 等表，**都是平台正在跑的真实表**，不是空白。下面逐条说"它现在是怎么做的"。

### 🟢 EFA-P0-003｜config_partner_routing 三权分离（路由规则谁配谁审）

- **【事实】平台现状**：表存在（`config/CONFIG_PARTNER_ROUTING_*.xlsx`），跑在 `agg2_commission_tier_rate.py` 里。规则按 `priority` **升序**匹配（数字越小越优先），用 `is_active=1` 筛有效规则，6 个条件字段（合作伙伴/分类/佣金模式/保司/业务线/产品）任一为 `ALL` 即通配。**匹配不到 → 回退用 `main_license_code`**（不会乱分、不会报错）。
- **【判定】**：技术机制完整。问题不在"系统能不能做"，而在**治理**——目前配置/复核/审批是同一个人（MOMO）。
- **访谈口径建议**：技术上完全支持"谁配、谁审"拆开，因为规则表有 `is_active` 和 `priority`，可以做"草稿态→复核→生效"。**真正要业务/Mark 定的是**：复核交给谁、紧急上线走不走绿色通道。【需业务定】

### 🟢 EFA-P1-007｜路由表多条件命中时的优先级

- **【事实】**：已经是 `priority` 升序、命中即返回（first-match-wins）。**priority 越小越优先**。匹配不上回退 `main_license_code` 就是现成的 fallback。
- **访谈口径**：这条其实"已实现"，访谈只需让业务确认"`priority` 数值是不是按业务意图排的"，以及"回退到 main_license_code 是否可接受"。

### 🟢 EFA-P1-006｜全档位表聚合口径（partner_tier / fyc_tier 从哪来）

- **【事实】**：`partner_tier` 来自 `Config_Commission_Table_Type` 里的 partner_code，再去 `DIM_PARTNER` 递归展开层级（tier=1 是当前伙伴，越大越顶层）；`fyc_tier` 来自 `Partner_Tier_Rules` 匹配出的 `FYC_Tier`。聚合逻辑是确定的，不是多义的。
- **【需业务定】**：文档问的"按自然月/滚动季度/保单年度评定档位"——**平台目前没有"周期评定"这个概念**，档位是按规则表当下的配置直接套，不随时间滚动。要不要做"周期+追溯"是业务规则问题（见下 EFA-P2-002）。

### 🟢 EFA-P0-001｜佣金准入表 Excel → 数据表切换

- **【事实】**：确实已切换。佣金率现在由 `fact1_commission_rate.py`（FACT1）从数据表算，逻辑是"`Total_Y1~Y10` 有值优先直接用，否则按公式 `Basic/Extra/SMPA` 兜底算"。整链由 Airflow `commission_pipeline` DAG 编排（FACT1→Agg1→Agg2→Agg3→入库）。
- **【判定】回滚问题**：每次跑都有时间戳产物（`Fact_Commission_Rate_*.xlsx`）留档，旧 Excel 也在 git/历史里，**可追溯可回退**。但"出错自动回滚"这种机制【未实现】，目前是重跑 DAG。
- **访谈口径**：切换已完成且可追溯；要不要做"自动回滚/双跑校验"是后续治理项。

### 🟢 EFA-P0-002 / EFA-P1-002｜市场佣金表手工调整留痕 + 外发版本一致

- **【事实】**：Agg2→Agg3 拆表是脚本自动产出（按制表类型拆，带时间戳）。但 **MOMO 在产出后用路由规则文档做的手工微调，平台没有"调整留痕/审批/外发版本锁定"这层**——这部分目前在脚本之外，是人工 Excel 操作。
- **【判定】**：这是**真缺口**，但属于"治理/系统功能"缺口，不是计算逻辑缺口。
- **访谈口径**：建议方向——手工调整收进平台（或至少加一张"调整日志表"+ 外发版本号/时间戳锁定）。【需业务定排期】

### 🟢 EFA-P1-001 / EFA-P2-004｜fact_commission_rate ETL 责任边界 + 公式错误检测

- **【事实】公式逻辑**：FACT1 算 `fyc_rate`/`ryc_rate` 的规则在 `fact1_commission_rate.py`，公式用 AST 安全求值（已不用 eval），参数是 Basic/Extra/SMPA。
- **【事实】检测机制**：有一个**弱校验**——`agents/commission_agents.py` 里对费率值有范围检查（落在 `[-0.1, 2.0]` 之间）。但**"续期不应高于首期""某类产品费率不应超过 X%"这种业务合理性校验，目前没有**。
- **【判定】**：这是真缺口里"性价比最高"的一个——加几条业务规则断言（续期≤首期、费率上下限）就能挡住"3% 算成 30%"这类错误。
- **访谈口径**：值得做，需业务方给出"哪些是不可能的值"的清单。【需业务定阈值】

### 🟢 EFA-P1-005｜agg_source_commission_wide 聚合逻辑

- **【事实】**：Agg1 宽表按 **12 个维度 GROUP BY**（commission_plan_code、tier_code、is_prepaid、融资、Commission_Type、customer_type、product_id、Rate_Option_Code、Age_from、Currency、最低保费门槛、Issue_Cutoff_Date），聚合函数是 `first`（取首条，因为同组本应唯一）。
- **【事实】防重**：**有冲突护栏**——同一组合下如果 `fyc_rate`/`Fyc_Deferred` 不唯一，脚本直接 `raise` 报错，不会"双倍计算"。文档担心的"同保单被聚合两次"在代码层已被拦。
- **访谈口径**：逻辑已实现且有护栏，访谈只需业务确认"GROUP BY 这 12 个维度对不对、取 first 是否符合业务"。

### 🟡 EFA-P1-003 / EFA-P1-004 / FIN P1-007｜费率/公式版本有效期重叠冲突（三条同一问题）

- **【事实】**：`fact_commission_rate` 有 `effective_start_date` / `effective_end_date` / `Issue_Cutoff_Date`。下游 Agg2 查宽表时**按 `commission_date` 落在 `[start, end]` 区间过滤**——所以正常情况下一笔只命中一个版本。
- **【判定】**：**有"按日期取版本"机制，但没有"重叠仲裁"机制**。如果业务录入时两条记录区间真的重叠了，平台不会自动判"以哪条为准"，可能两条都命中。
- **访谈口径**：这是真缺口，但很轻——补一条入库校验"同 key 的有效期不许重叠"即可。**真正要业务定的是空档期**（保司通知调费但内部还没更新，这期间按新还是旧）。【需业务定】

### 🟢 EFA-P2-001｜制表参数变更后下游是否自动重算

- **【事实】**：`Config_Commission_Table_Type` / `config_product_commission_formula` 改了之后，**不会自动重算**，需要在 Airflow 手动触发 `commission_pipeline` DAG（DAG 是 `schedule_interval=None`）。一旦触发，整链 FACT1→Agg3 全部按新参数重算。
- **访谈口径**：现状是"手动触发、全链重算"。要不要做"参数改了自动触发"是自动化增强项。【需业务定优先级】

### 🟡 EFA-P2-002｜partner_tier_rules 档位评定周期与历史追溯

- **【事实】**：`Partner_Tier_Rules` 表**没有 `effective_date_type` / 评定周期字段**。档位是按规则表当下配置直接套，不按月/季滚动，也没有"业绩达标后补差"机制。
- **【判定】**：这是真的业务规则空白——平台没做"周期评定+追溯"是因为没收到这个需求。
- **访谈口径**：【需业务定】要不要按周期评档、跨档保单按哪个档算、历史是否补差。

### 🟢 EFA-P2-003｜product_risk_override 覆写规则自动过期

- **【事实】**：覆写表（`config/Product_Risk_Override_*.xlsx`）匹配顺序是"精确(sku+id+rate_option) → 通配(product_id=ALL) → 回退 DIM_PRODUCT_SKU 原值"。**没有有效期、没有自动过期**，规则设了就长期生效。
- **访谈口径**：现状是"长期生效+精确优先通配"。要不要加过期/清理是治理增强。【需业务定】

### 🟡 EFA-P1-008 / FIN P1-006｜源头 PDF 产品命名 → 内部编码映射（两条同一问题）

- **【事实】**：平台**已经有三级产品名匹配机制**（计划书链 `_match_product_id`）：① `DIM_PRODUCT_ID` 精确/最长前缀匹配 → ② ETL 规则里的"产品映射表" sheet → ③ 外挂映射表 `product_name_mapping.xlsx`。还做了字符规范化（NFKC + 去括号/引号/间隔点/脚注）。匹配失败会**阻断并报错**，不会静默错配。
- **【判定】**：佣金链侧（`DIM_COMMISSION_RATE`）的产品名→编码映射，复用的是同一套思路。不是"没有映射"，而是**映射表需要持续维护**（保司出新品名要补录）。
- **访谈口径**：机制已有，访谈确认"谁负责在出现新品名时补映射表"。【需业务定 owner】

## 二、FIN 线（财务结算子项目 = 沙箱期，应收跑通、其余设计中）

> ⚠️ FIN 子项目当前在**沙箱阶段**（未合并母项目），按门禁规则推进。下面如实区分"已跑通 / 仅设计"。

### 🟡 P0-002 + VN-PAY-04｜拨出率≤50% / 同行支付≤88% 的 IA 硬指标校验

- **【事实】规则**：业务规则 SSOT 已明确（编号 ST-03）——持牌经纪拨出率 ≤88%、其他 ≤50%，公式 = 成本实派 ÷ 牌照实收，且需跨期汇总。
- **【事实】校验**：设计里有视图 `v_payout_ratio`，但**还没编码实现**。**目前是手工校验，应派环节没有系统自动拦截**。
- **【判定】**：规则清楚，差"把校验写成代码"这一步。是真缺口但落地不难（应付链建好后加一张校验视图/断言）。
- **访谈口径**：诚实说"现在靠人工，规则已定，自动拦截待应付链编码时一起做"。边界值（49.9% 怎么算、四舍五入还是严格大于）【需业务定】。

### 🔴 A-2 P2-001｜首年折扣% 适用条件与审批链

- **【事实】**：佣金链里**有折扣机制**——`rate_option_code` 体系（STD=标准、DISC_X=折扣、DISC_SQ=首年0保费），FACT1/Agg 全链透传。
- **【判定】**：**"哪些产品适用折扣、折扣比例怎么定、谁审批"这是纯业务规则**，平台只负责按录入的 rate_option 算钱，不决定折扣政策。
- **访谈口径**：【需业务定】这条平台答不了，是业务方要回答的（适用条件、审批人、差异化折扣怎么管）。

### 🟡 B-1 P0-004｜汇率选取时点规则

- **【事实】**：应收表 `fact_receivable` **已有 `exchange_rate` 字段**，但**源头 `fact_policy` 没有这一列，所以现在应收输出里汇率是空的**。
- **【判定】**：字段位置留好了，缺的是"汇率从哪来、按哪天"——应收设计文档里这是 Q17 待确认项。
- **访谈口径**：【需业务定】汇率来源（保单录入时/汇率表/实收时确定）和时点规则（进账日/批核日/月度固定）。这是访谈必须拿到的答案，否则应收金额无法换算港币。

### 🔴 B-2 P1-003｜权益激励 hold 解除是手工还是自动

- **【事实】**：`DIM_EQUITY_TIER` 有 Excel 样本配置；hold 状态表（设计名 `fact_hold`，含权益/续保两类）**设计完整但未编码**。
- **【事实】现状流程**：权益部每半月更新服务价值 → 通知可派金额 → **蔡依娜手工解 hold + 派发**。目前靠 Excel 公式，没有系统自动触发。
- **访谈口径**：如实确认"现在是半月更新后手工解 hold"。要不要做"达标自动解 hold"是 FIN 后续编码任务，需先把 `fact_hold` + 服务价值表建起来。【需业务定是否自动化】

### 🟡 B-3 P1-004｜DIM_PAYEE_MAPPING 收款人映射约定

- **【事实】**：旧设计的 `DIM_PAYEE_MAPPING` 已**收敛到母项目既有表 `map_partner_payee`**。默认按人名合并；已确认链式映射"吴竞 → 白博文 → 雨泽家族办公室"。映射分 6 类（个人→公司、业务约定、同音字、利润分成、分行→总行、机构简称→全称）。
- **【判定】**：机制有了，但**完整名单不全**——号称 23 人映射到雨泽家办，文档只显式列了 7~8 人，剩下待补。
- **访谈口径**：【需业务定】把 23 人完整名单、利润分成主体、分行映射补齐——名单不全会直接影响应派单准确度。

### 🔴 B-4 P1-006｜（产品编码映射）→ 见上 EFA-P1-008，同一问题，机制已有

### 🔴 B-6 P1-011 + VN-PAY-06 C-2｜银行权益活动费建表 / 理财师综合应派 dim_agreement_param

- **【事实】**：`dim_agreement_param`（理财师协议参数表）、银行活动费专用表（设计名 L3-BANK）**都还没建，仅在规划文档里**。当前银行活动费是 Excel 手工管理。
- **【判定】**：这是 Carrie 的核心职责区（建表/建模），属🔴仅规划。
- **访谈口径**：Carrie 需输出**表结构草案**（理财师ID×协议类型×参数字段 + FK + 生效期）。访谈要拿到字段清单和数据来源，才能动手建模。【需业务定字段口径】

### 🔴 B-7 P2-002｜record_type "额外费用" 内部细分（MPF/RIB）

- **【事实】**：`fact_receivable`（应收侧）**不涉及这个细分**；费用细分（BASIC/OR/权益费/管理费）是在**应付侧设计**里，而应付链还没编码。
- **访谈口径**：【需业务定】"额外费用"里 MPF / RIB 是否要拆成子类、各自怎么处理——拿到答案后在应付链建模时落地。

## 三、Mark 裁定三个熔断节点（C 组 = 都还没建表，要先定方向）

> 这三个的共同点：**平台目前零覆盖，Carrie 要输出的是"建表方案草案"，再由 Mark 拍板归口/排期/资源**。访谈不是问"现在怎么做"，而是"定方向 + 给资源"。

| 节点 | 缺什么（事实） | Carrie 待输出 | 卡点 |
|---|---|---|---|
| **C-1 VN-PAY-04** 转介费派发台账 | IA 合规规则未代码化（依赖 P0-002 拨出率方案）；银行回执无统一归档 | 阈值配置表结构 + 实时校验触发 + 告警规则 | 依赖应付链 + 拨出率校验先落地 |
| **C-2 VN-PAY-06** 理财师综合应派 | 四类协议参数未中心化（`dim_agreement_param` 未建）；人工合并易错 | `dim_agreement_param` 表结构草案（理财师×协议类型×参数 + FK + 生效期） | FPG-05 归哪个部门要 Mark 定 |
