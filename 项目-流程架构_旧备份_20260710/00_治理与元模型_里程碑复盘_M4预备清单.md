## 四、M4 风险登记

### R1: 技术栈POC失败

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#1: M4.1技术栈需POC, Drools/数据管道/告警是概念级 |
| **具体场景** | Carrie团队没有Airflow/PostgreSQL生产级运维经验, POC跑通≠生产可用 |
| **影响** | M4.1延迟3~4周, 或被迫切换到方案C(混合外包), 预算+50% |
| **概率** | 中 (Carrie有数据基础但无DevOps经验) |
| **缓解** | W2 POC设硬门槛: 不通过则W3立即切方案C, 不等; P4.1审批文件已预留方案C切换路径 |
| **监控** | W2结束Carrie提交POC报告, Mark/Teresa review |

### R2: Agent无主人 — L4与岗位映射断裂

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#2: 80条Auto L4的"主人"需从JD反查精确映射 |
| **具体场景** | Agent上线后产出异常, 无人知道该谁review/修正; 或多个岗位争夺同一Agent的管辖权 |
| **影响** | Agent运行无监督 = 错误积累 = 业务事故; 或责任推诿导致Agent被弃用 |
| **概率** | 高 (7族JD是按组织逻辑设计, 80条L4是按流程逻辑切分, 两套逻辑不一定1:1) |
| **缓解** | W0-2强制完成映射表; 允许1个L4映射到多个岗位但必须标注"A责任人"唯一; 映射表纳入RACI矩阵 |
| **监控** | Teresa每月review映射表, 新增L4必须同步更新 |

### R3: 预算失控

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#3: P4.1的≤100万HKD预算需Carrie验证 |
| **具体场景** | 保司数据源对接费用超预期(无API, 需定制开发); 或方案C切换导致外包成本翻倍 |
| **影响** | M4.2~M4.4预算被挤压, 或Mark叫停项目 |
| **概率** | 低~中 (方案A本身有15万应急预留) |
| **缓解** | W4/W8/W12三个里程碑检查点, 偏离预算20%立即escalate Mark; Carrie月度预算报告 |
| **监控** | Carrie月报含预算执行vs计划对比 |

### R4: M3.3规则化会议延迟 → 规则引擎空转

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#4: M3.3规则化会议是规则引擎输入, 延迟影响P4.1 W8~12 |
| **具体场景** | Mark日程排不出4次×2.5h; 或会议质量不够, 规则产出不可执行 |
| **影响** | 规则引擎V1有引擎无规则, 18条Auto L4无法上线, M4.1延期 |
| **概率** | 中~高 (Mark日程紧张是已知瓶颈) |
| **缓解** | W1-5排死日历, 4次会议间隔≤2周; 赵琦提前准备规则草稿, Mark只做裁定不做起草; 即使会议延迟, 规则引擎可先用佣金历史规则做测试 |
| **监控** | Teresa追踪会议完成率, 每次会议后24h内产出规则文档JSON |

### R5: 过渡路径阻断 → M4.2人员不到位

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#5: 过渡路径(M3.5)是人员到位的前置 |
| **具体场景** | Ivan的HR模板持续未回传; 或过渡路径涉及法律/劳动合同问题需外部律师 |
| **影响** | M4.2启动时核心业务岗位未到位, Agent的肉身监督人缺位 |

| **缓解** | W0-4设催办截止日: 2周内无回传则Teresa直接用M3组织图+JD产出替代方案; M4.1(纯技术)不依赖人员到位, 仅M4.2开始需要 |
| **监控** | Teresa周报标注过渡路径状态 |

### R6: M4北极星漂移

| 维度 | 内容 |
|------|------|
| **来源** | M3复盘警告#6: M4必须先锁定北极星 |
| **具体场景** | M4执行过程中被技术细节吸引(如Airflow调优), 偏离"80条Agent上线"的核心目标 |

## 五、M4 阶段里程碑

### M4.1 基础设施 (34条Auto, 3~4个月)

| 维度 | 内容 |
|------|------|
| **覆盖** | 数据管道9条 + 规则引擎18条 + 告警7条 |
| **进入标准** | (1) Mark签字P4.1 ✅ (2) Carrie岗位到位 ✅ (3) POC W2通过 ✅ |
| **退出标准** | (1) 34条Auto Agent全部上线运行≥30天 (2) 每条Agent有且仅有1个JD岗位作为A责任人 (3) 数据管道≥5个数据源T+1入仓 (4) 规则引擎≥3类核心规则(佣金/分级/权益)可配置 (5) 告警系统7条告警触发+企业微信通知到人 |
| **关键检查点** | W2 POC / W4 数据管道V1 / W8 规则引擎V1 / W12 告警V1 / W16 联调完成 |
| **核心风险** | R1(POC失败) + R4(规则会议延迟) |

### M4.2 核心业务 (25条Auto, 2~3个月)

| 维度 | 内容 |
|------|------|
| **覆盖** | 保司交付/合同管理/产品上架等核心业务流程的Auto L4 |
| **进入标准** | (1) M4.1退出标准全部达成 (2) 80条L4→JD映射表100%完成 (3) 过渡路径V0已产出, 核心业务岗位人员到位≥80% (4) M3.3规则化会议至少完成2/4次 |
| **退出标准** | (1) 25条Auto Agent上线运行≥30天 (2) 核心业务岗位人员实际使用Agent≥2周 (3) 无因Agent错误导致的业务事故(保司投诉/佣金错算/合同延误) |
| **关键检查点** | 每2周review Agent上线数 + 业务方反馈 |
| **核心风险** | R2(Agent无主人) + R5(人员不到位) |

### M4.3 智能分析 (15条Auto, 2~3个月)

| 维度 | 内容 |
|------|------|
| **覆盖** | 预测分析/趋势报告/客户画像等分析型Auto L4 |
| **进入标准** | (1) M4.2退出标准全部达成 (2) 数据管道已稳定运行≥2个月(分析Agent依赖数据质量) (3) 分析型岗位人员到位(F族权益中台有分析需求) |
| **退出标准** | (1) 15条Auto Agent上线运行≥30天 (2) 分析产出被至少1个业务决策引用(证明有用, 不是摆设) (3) 数据质量异常率<5% |
| **关键检查点** | 月度review: 分析Agent产出 → 业务决策 的转化链路 |
| **核心风险** | 数据质量不足导致分析Agent产出垃圾 |

### M4.4 长尾优化 (6条Auto, 1~2个月)

| 维度 | 内容 |
|------|------|
| **覆盖** | 低频/低优先级但仍可自动化的L4 |
| **进入标准** | (1) M4.3退出标准全部达成 (2) 组织已适应"人+Agent"工作模式≥3个月 |
| **退出标准** | (1) 80条Auto Agent全部上线 (2) 全员人均管理Agent数≥2 (3) 人效指标有可测量的提升(不要求达到800万, 但必须有正向数据) (4) M4复盘文档完成 |
| **关键检查点** | M4结束前1周: 全量Agent健康度检查 + 人效数据采集 |
| **核心风险** | R6(北极星漂移 — 长尾阶段容易松懈) |

### 阶段转换规则

1. **前一阶段退出标准未达成, 不进入下一阶段** — 宁可延期不可跳过
2. **每阶段之间留1周缓冲** — 用于复盘+调整+下阶段准备
3. **M4.1→M4.2是最关键转换** — 从"技术搭建"到"业务使用", 需要组织变革管理(不是技术问题)

## 六、Mark 需要的决策

**以下问题需要Mark在M4启动前以"是/否"裁定, 每题附推荐答案和不裁定的后果。**

### 决策1: P4.1预算

> **是否批准P4.1方案A(内部为主, 预算≤100万HKD, Carrie负责)?**

- 推荐: **是**
- 不裁定后果: 基础设施无法开工, M4整体延迟3~4个月, 且人员空转成本>100万

### 决策2: Carrie升级

> **是否将Carrie从"数据底座"升级为"Agent节点负责人"正式实体岗, M4期间直接向Mark汇报?**

- 推荐: **是**
- 不裁定后果: Carrie以兼职/模糊职责执行M4核心工作, 责任不清, 出问题无人担责

### 决策3: POC硬门槛

> **W2 POC不通过时, 是否自动切换到方案C(混合外包, 预算≤200万HKD)?**

- 推荐: **是**, 且授权Teresa/Carrie直接切换, 不再回Mark审批(节省2~3周)
- 不裁定后果: POC失败后陷入"再试一次"循环, 反复延期

### 决策4: 规则化会议排期

> **是否在M4启动后4周内完成至少2次规则化会议(每次2.5h)?**

- 推荐: **是**, Mark日历锁定4个半天
- 不裁定后果: 规则引擎空转, 18条规则类Auto L4无法上线, M4.1从16周膨胀到20+周

### 决策5: 过渡路径替代方案

> **若Ivan的HR模板2周内未回传, 是否授权Teresa用M3组织图+JD直接产出过渡路径V0(不等HR标准模板)?**

- 推荐: **是** — 完美的HR模板不如及时的工作版本
- 不裁定后果: 过渡路径持续阻断, M4.2启动时人员不到位

### 决策6: M4成功的第一KPI

> **M4的月度review, 第一个KPI是否定为"Agent上线数"(而非技术完成度/代码行数/系统稳定性)?**

- 推荐: **是** — 技术完成度是过程指标, Agent上线数是结果指标
- 不裁定后果: 团队优化技术架构但不上线Agent, 10个月后有精美系统但零业务价值
