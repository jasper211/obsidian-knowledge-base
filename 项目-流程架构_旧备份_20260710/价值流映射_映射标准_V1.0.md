## 一、数据结构标准（SSOT）

### 层级定义
```
价值流（VS）         → 外部利益相关者视角的端到端旅程（5条）
  └── 价值阶段（S）  → 旅程中的关键里程碑阶段
        └── 价值活动 → 该阶段内的具体业务活动
              └── L3 → 对应的内部端到端跨部门流程编码
```

### 字段命名标准

| 字段名 | 说明 | 格式 |
|--------|------|------|
| `vs_id` | 价值流编号 | VS-1 ~ VS-5 |
| `stage_id` | 价值阶段编号 | VS{n}-S{m}，如VS1-S1 |
| `stage_name` | 价值阶段名称 | 文字描述 |
| `activity` | 价值活动描述 | 文字描述 |
| `l3_code` | L3流程编码 | 符合`^L3-[A-Z]{2,6}$` |
| `l3_note` | L3映射备注 | 横切/共享/等 |
| `confirmation_status` | 数据可信度 | 见第三节 |
| `data_source` | 数据来源 | 见第三节 |

**历史错误命名（禁止使用）**：
- ❌ 把"价值阶段"列命名为"价值流" → 应为`stage_name`
- ❌ 把"价值活动组"列命名为"价值阶段" → 应为`activity_group`（如有）

## 四、多L3映射处理规则

### 规则说明

一个价值阶段可以对应多个L3流程。入库时**每个L3独立一行**，其余字段复制相同内容，`l3_note`字段说明关系类型。

**关系类型说明**：

| l3_note值 | 含义 | 典型场景 |
|----------|------|---------|
| 空 | 一对一映射，无特殊关系 | 大多数阶段 |
| 共享 | 该L3被多个价值流/阶段共用 | 权益相关L3被多VS使用 |
| 横切 | L1-05权益中台横切能力，跨VS消费 | VS-5持续服务交付 |

### 各阶段多L3拆分规则

**R-VS2-1：VS2-S1接触与需求诊断（3个L3）**
```
L3-IBEC → 机构商业模式与生态构建（接触阶段）
L3-IBRD → 机构业务需求诊断
L3-URD  → 联合运营需求诊断
```
每条"接触与需求诊断"阶段的价值活动，均对应这3个L3流程。入库时拆分为3行。

## 五、入库执行流程

```
Step 1：读取源文件中的价值流/价值阶段/价值活动数据
      ↓
Step 2：识别价值流编号（VS-1~VS-5）
      ↓
Step 3：对照第二节权威结构，确认价值阶段名称和阶段编号（VS{n}-S{m}）
        ├── 名称与标准不一致 → 替换为标准阶段名称
        ├── 属于旧SMPS框架（VS-4）→ 删除，不入库
        └── 无法识别 → 标记"待人工确认"
      ↓
Step 4：对照第二节的L3映射，为每条价值活动填入l3_code
        ├── 该阶段只有1个L3 → 直接填入
        ├── 该阶段有多个L3 → 拆分为多行（见第四节规则）
        └── l3_note不为空 → 填入对应备注（共享/横切）
      ↓
Step 5：验证l3_code格式符合^L3-[A-Z]{2,6}$
      ↓
Step 6：按第三节规则打上confirmation_status
      ↓
Step 7：写入dim_value_stream表
```
