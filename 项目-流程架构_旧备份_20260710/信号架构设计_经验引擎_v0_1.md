## 一、experience-engine 文件的定位与产出机制

### 1.1 文件基本信息

**文件名**：`日常持续更新_audited_results_2026-04_v2.md`
**Mark 备注**：「这个是我对自己经验的代码化第一个版本，里面包含了我对行业、公司、中台、经营、销售等全维度的判断与观点」

**文件规模**：
- 103 条 PROMOTE entries，全部含完整四字段
- 164KB，3015行

**Entry 类别分布**：

| 类别 | 条目数 | 层级 | 内容性质 |
|------|--------|------|---------|
| business_playbook | 23 | C | 具体业务场景的操作逻辑（保险销售/渠道/KA） |
| principle | 21 | A | Mark 的底层判断原则 |
| agent_config | 16 | D | AI协作的行为规范与协议 |
| decision_framework | 13 | A | 决策工具和判断框架 |
| mechanism_playbook | 13 | B | 组织/运营机制设计 |
| strategic_framework | 12 | A | 战略层框架与路径 |

**置信度分布**：HIGH 34条 / MEDIUM 52条 / LOW 21条

### 1.2 产出机制

这份文件不是 Mark 发给 Jasper 的任务指令，而是 **experience-engine 月度聚合会的审核结果文件**，是 Mark 经验库的「版本发布说明」。

产出流程如下：

```
每月一次：月度聚合会
      ↓
Mark 对候选 entry 逐条审核
（PROMOTE / DELAY / REVISE / REJECT）
      ↓
产出：audited_results_YYYY-MM_v2.md   ← 本文件
      ↓
Agent 消费：process_audit_results.py
      ↓
写入 experience-engine 数据库
（v1.0.0 已有 117 个 entry）
```

**四字段结构**（每条 entry 的标准内容）：

| 字段 | 内容 |
|------|------|
| business_framework | 业务场景描述、核心命题、适用条件 |
| causal_logic | 显性化因果链（A→B→C→结果） |
| root_cause | 底层原理、元层判断 |
| cross_layer_links | 与其他 entry 的跨层关联 |

## 二、文件在本项目中的角色

### 2.1 定位确认

**这份文件在「企业流程架构 & 经验引擎」项目中的角色：**

| 角色 | 说明 |
|------|------|
| ❌ 不是信号源 | 它不是触发洞察的外部信号 |
| ❌ 不是 Mark 任务指令 | 它是 experience-engine 的内部产出物 |

| ✅ 是阶段2的正式接入对象 | 对应上下文文件「阶段1.2：加入 experience-engine」 |

**一句话定位：它是引擎的燃料（经验参照），不是引擎的输入信号。**

### 2.2 三个项目的关系图（更新版）

```
项目A：EA数据底座（标准侧，已完成）
  → 提供「应该怎么做」的标准参照
  → 4张核心表：dim_l3 / dim_l4_activity / dim_value_stream / dim_agent_capability

**阶段2（未来）**：正式接入为经验参照层，需解决两套编号系统的映射问题（见第七章）。

## 三、整体架构的对话确认

### 3.1 Jasper 提出的架构理解

> 从任务指令到信号A，再将信号A与EA流程架构匹配，然后出信号B。信号B是洞察的输入源之一，其他输入源可能包括 experience-engine 这些文档的匹配，最终出有价值的洞察。

**Claude 评估：方向完全正确。**

### 3.2 准确的三个点

**① 信号A→信号B是核心链路**：先跑通这条是正确的阶段0策略。

**② 信号B是洞察的输入源之一，而非唯一**：experience-engine 是并行输入，不是替代关系。

**③ 阶段0暂不纳入 experience-engine**：节奏合理，保持验证焦点。

### 3.3 需要补充的一处

**信号B不只是「匹配到了什么」，还必须包含缺口分析（gap_analysis）。**

缺口信息 = 信号指向的业务行为与EA底座定义的标准之间的差距。这个缺口才是洞察真正有价值的地方，是七模块中「洞察结论」和「建议行动」的来源。

### 3.4 完整架构图

```
Mark任务指令（及未来多元输入）
        ↓
   [节点1] 任务内容解析
        ↓
   [节点2] 形成信号A（结构化信号）
        ↓
   [节点3] 信号A × EA数据底座（L3/L4/KPI匹配）
        ↓
   [节点4] 形成信号B（匹配结果 + 缺口判断）
        ↓
   [节点5] 信号B × experience-engine（阶段2启动）
        ↓
   [节点6] 洞察推理程序
        ↓
   [节点7] 输出七模块洞察结论
```

## 四、七节点信号架构详细设计

### 节点1：任务内容解析

**功能**：将多元格式的输入内容转化为可处理的文本。

**输入格式支持与优先级**：

| 格式 | 阶段0 | 阶段1 | 阶段2+ |
|------|-------|-------|--------|
| Markdown / 纯文字 | ✅ 直接处理 | ✅ | ✅ |
| PPT | ❌ 暂不支持 | ⏳ 转文字后处理 | ✅ |
| 图片 | ❌ 暂不支持 | ⏳ OCR后处理 | ✅ |
| 录音 | ❌ 暂不支持 | ❌ | ✅ Phase 3信号源 |

**阶段0原则**：格式解析不是阶段0的阻断项，先用纯文字信号跑通链路。

**节点输出**：清洁文本（可供节点2进行实体提取）

---

### 节点2：形成信号A（结构化信号）

**功能**：从清洁文本中提取关键实体，形成标准化的结构化信号。

**核心设计原则**：信号A的质量直接决定节点3匹配的准确度，是整条链路的质量基础。

**信号A标准结构**（详见第五章）

**阶段0处理方式**：手工提取，Claude执行，不依赖代码。

---

### 节点3：信号A × EA数据底座匹配

**功能**：将结构化信号与EA数据底座的四张核心表进行多路并行匹配，锁定相关的L3/L4/KPI节点。

**匹配路径（三路并行）**：

```
信号A的实体
    ├─ business_scenario  → 语义匹配  → L3（最主要路径）
    ├─ job_family         → 精确匹配  → 岗位KPI → 企业KPI → L3
    ├─ objective          → 规则匹配  → KPI编码 → L3
    └─ trigger_event      → 规则匹配  → 价值流阶段 → L3
                                              ↓
                                      confirmed L3
                                              ↓
                                      L4 + 核心交付物
                                      Agent Tier（Auto/Aug/Hybrid/Human）
                                      标准KPI关联
```

**三路并行的意义**：多路结果互相印证，提升匹配置信度。三路结果收敛到同一L3 → 高置信度；结果分散 → 低置信度，需人工裁定。

**依赖的EA底座表**：

| 表名 | 用途 |
|------|------|
| dim_l3 | 82个标准L3编码，语义匹配的目标库 |
| dim_l4_activity | L3→L4映射，含交付物+Agent Tier |
| dim_value_stream | 价值流阶段，触发事件匹配 |
| dim_agent_capability | Agent能力维度，判断自动化程度 |
| KPI穿透表（235行） | 企业KPI↔L3映射，规则匹配路径 |
| 岗位KPI表（302行） | 岗位KPI→企业KPI→L3，精确匹配路径 |

**治理规范参照**（匹配时的判断标准）：

- 价值流-L3映射：3问检验法（Q1利益相关者→Q2触发事件→Q3交付接收方）
- L1-L3映射：6类典型归属模式
- L3编码映射标准V1.1

---

### 节点4：形成信号B（匹配结果 + 缺口判断）

**功能**：整合节点3的匹配结果，并生成缺口分析，形成洞察推理的原材料。

**核心区别**：信号B ≠ 信号A + 匹配编码。信号B的核心价值在于 `gap_analysis`——将「发生了什么」转化为「和标准相比差在哪里」。

**信号B标准结构**（详见第六章）

---

### 节点5：信号B × experience-engine 匹配

**功能**：用信号B的业务场景和缺口信息，从 experience-engine 中找到相关的历史经验参照。

**启动时间**：阶段2（阶段0概念验证通过后）

**与节点3的核心差异**：

| 维度 | 节点3（×EA底座） | 节点5（×experience-engine） |
|------|----------------|---------------------------|
| 匹配对象 | 结构化编码（L3/L4/KPI） | 自然语言原则和判断 |
| 匹配方式 | 语义+规则+精确（三路并行） | 语义匹配为主 |
| 准确度 | 较高（结构化数据） | 相对较低（自然语言） |
| 提升路径 | 扩展编码覆盖率 | 建立跨系统编号对照表 |

**阶段2前置条件**：需建立「EA底座L3编码 ↔ experience-engine entry_id」对照表（见第七章待解决问题）。

---

### 节点6：洞察推理程序

**功能**：基于信号B（+经验参照）进行三步推理，生成有行动意义的洞察内容。

**这不是模板填充，而是推理程序。**

**三步推理逻辑**：

```
Step A：现象归因
  输入：gap_analysis.gap_desc
  推理：识别缺口的高概率原因（2-3个假设）
  输出：「洞察结论」模块的高概率原因

Step B：影响穿透
  输入：matched_kpi + 权重
  推理：计算缺口对企业KPI的影响范围和量级
  输出：「影响范围」模块的关联KPI和预计影响

Step C：行动生成
  输入：agent_tier + experience-engine原则（阶段2）
  推理：基于当前Agent化程度，生成可选行动方案
  输出：「建议行动」模块的选项A/B/C
```

**三步对应七模块结构的位置**：

| 推理步骤 | 对应七模块 |
|---------|----------|
| Step A 现象归因 | 模块5：洞察结论 |
| Step B 影响穿透 | 模块7：影响范围 |
| Step C 行动生成 | 模块6：建议行动 |

---

### 节点7：输出七模块洞察结论

**功能**：将推理结果组装为标准化的七模块洞察报告。

**七模块结构**：

```
─────────────────────────────────────────

触发信号：[信号类型] [信号摘要]

【模块3：经验参照】（来自experience-engine，阶段2启用）

## 五、信号A标准结构定义

```
─────────────────────────────────────────
信号A · 标准结构 v0.1
─────────────────────────────────────────
signal_id:          [唯一编号，格式：SIG-YYYYMMDD-001]
signal_date:        [日期]
signal_type:        任务指令 / 销售数据 / 录音
signal_source:      [来源标识，如 Mark_20260508]

raw_content:        [原文，不做任何修改]

─────────────────────────────────────────
extracted_entities:

  business_scenario:
    [业务场景描述]
    回答：发生了什么？涉及哪个业务领域？

  job_family:
    [涉及的岗位族，参照EA底座的岗位族编码]
    如：A族（保司交付）/ D族（理财师事业部）/ G族（佣金合规）

  objective:
    [目标或任务]
    回答：要达成什么结果？

  problem:
    [问题或障碍，若无则为 null]
    回答：有什么阻碍或待解决的问题？

  trigger_event:
    [触发事件]
    回答：什么情况/事件触发了这个信号？
    （对应治理规范3问检验法的Q2）

─────────────────────────────────────────
```

**trigger_event 字段说明**：

这是相比原上下文文件新增的字段，原因是：价值流的L3匹配逻辑中，触发事件是核心判断维度之一（3问检验法Q2：触发事件是什么？）。缺少这个字段会导致节点3的价值流匹配路径缺失，降低匹配准确度。

## 六、信号B标准结构定义

```
─────────────────────────────────────────
信号B · 标准结构 v0.1
（基于信号A + EA底座匹配结果）
─────────────────────────────────────────
signal_id:              [继承自信号A的signal_id]
source_signal_a:        [关联的信号A编号]

─────── 匹配结果 ───────

matched_value_stream:   VS-X [价值流名称]
matched_l3:             [L3编码] [L3名称]
matched_l4:             [[L4编码, L4名称], ...]
matched_kpi:            [[KPI编码, KPI名称, 权重%], ...]
match_confidence:       高 / 中 / 低

match_path:             [主要匹配路径，如「语义匹配→业务场景→L3-IRR」]
match_notes:            [匹配过程中的异常或多路径冲突说明]

─────── 缺口分析（核心） ───────

gap_analysis:
  gap_type:     缺口 / 偏差 / 优化机会 / 正常 / 待确认
  gap_desc:     [具体描述：信号行为 vs EA底座标准定义的差距]
  agent_tier:   Auto / Aug / Hybrid / Human
                [当前L4的Agent化程度，判断是否/如何介入]
  severity:     高 / 中 / 低
                [缺口对业务运行的影响程度]

─────── 经验参照（阶段2填充） ───────

experience_ref:
  matched_entry_id:   [experience-engine entry编号，阶段2填入]
  entry_name:         [entry名称]
  relevance_note:     [为什么相关，一句话]

─────────────────────────────────────────
```

**gap_analysis 字段是信号B的核心价值所在**：

它将节点3的「找到了什么」转化为节点6推理需要的「差在哪里」。没有缺口分析，洞察只是「信号发生了什么」的描述，不是「需要关注什么」的判断。

**match_confidence 的判断标准**：

| 等级 | 判断标准 |
|------|---------|
| 高 | 三路匹配路径收敛到同一L3，无歧义 |
| 中 | 两路匹配路径一致，一路不确定 |
| 低 | 三路匹配路径分散，或只有一路有结果 |

## 七、待解决的关键问题

### 问题1：两套编号系统的映射（阶段2前置条件）

**问题描述**：

EA底座使用结构化编码（如 `L3-IRR`），experience-engine 使用内部 entry_id（如 `decision_framework_004`）和内部链接编号（如 `#85`）。两套系统之间没有映射关系。

**影响**：节点5无法实现精确匹配，只能依赖语义匹配，准确度受限。

**举例**：

```
信号B匹配到：L3-IRR（合作周期管理）
节点5想找相关entry，发现有：
  decision_framework_004 · 跨保司迁移决策框架
  cross_layer_links: #85 永明深度vs多保司广度

但系统不知道 L3-IRR ↔ decision_framework_004
因为没有对照表
```

**解决方案**：建立「EA底座L3编码 ↔ experience-engine entry_id」对照表

**Owner**：待确认（Jasper主导 / Mark那边Agent辅助 / 两边各建一半）

**时间节点**：阶段1结束前完成，作为阶段2的启动条件
