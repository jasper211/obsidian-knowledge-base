# L4 核心交付物 — Agent 映射逻辑分析与标准

> **版本**: v5 (基于 `L4_核心交付物全量表_v5.csv`)  
> **生成日期**: 2026-04-28  
> **数据规模**: 400 个 L4 级核心交付物，覆盖 82 个标准 L3 流程  
> **适用范围**: 企业架构 L4 级交付物与 Agent 化可行性评估、岗位重构、技术选型

---

## 一、总体框架

### 1.1 核心概念定义

| 概念 | 定义 |
|------|------|
| **L4 核心交付物** | 企业架构 L4 级（活动级）流程的最终产出物，是可交付、可验证、可归档的业务实体 |
| **Agent 映射** | 评估每个 L4 交付物是否可由 AI Agent 完成，以及需要何种能力组合 |
| **M2 Tier** | Mark 原始评分给出的 Agent 化层级（Auto / Aug / Hybrid / Human）|
| **推导 Tier** | 基于 6 维度评分自动推导的 Agent 化层级，用于校准和补全 |
| **D1-D6** | 6 个评估维度，每个维度 0-3 分，总分 0-18 分 |

### 1.2 四层映射模型

```
┌─────────────────────────────────────────────────────────────┐
│  Tier-1: Auto (全自动)   — Agent 独立执行，人仅异常介入        │
│  Tier-2: Aug (增强型)    — Agent 主导，人在关键环节确认/审核   │
│  Tier-3: Hybrid (协作型) — 人与 Agent 协作，各负责部分环节     │
│  Tier-4: Human (人工型)  — 人主导，Agent 仅辅助参考           │
└─────────────────────────────────────────────────────────────┘
```

## 二、六维度评分体系 (D1-D6)

### 2.1 维度定义与评分标准

| 维度 | 名称 | 核心问题 | 评分标准 | 权重说明 |
|------|------|----------|----------|----------|
| **D1** | 输入结构化 | 交付物的输入数据是否可被结构化采集？ | 0=完全非结构化 / 1=半结构化 / 2=大部分结构化 / 3=完全结构化 | 高 |
| **D2** | 规则清晰 | 交付物的生成规则是否明确、无歧义？ | 0=主观判断为主 / 1=部分规则 / 2=规则较清晰 / 3=完全规则驱动 | 中 |
| **D3** | 输出可验 | 交付物产出是否可被自动验证 correctness？ | 0=无法自动验证 / 1=部分可验 / 2=大部分可验 / 3=完全可验 | 高 |
| **D4** | API可达 | 交付物生成是否需要调用外部系统/API？ | 0=纯人工 / 1=偶尔调用 / 2=频繁调用 / 3=全链路API驱动 | 中 |
| **D5** | 降级可用 | 当 Agent 失效时，交付物是否有降级方案？ | 0=无降级 / 1=简单降级 / 2=有预案 / 3=完全可降级 | 低 |
| **D6** | 合规可编码 | 交付物涉及的合规要求是否可被编码为规则？ | 0=无法编码 / 1=部分可编码 / 2=大部分可编码 / 3=完全可编码 | 高 |

### 2.2 维度与 Agent 能力映射

```
D1(输入结构化)  ──→  数据采集 + OCR/NLP + 表单识别
D2(规则清晰)    ──→  规则引擎 + 决策树 + 专家系统
D3(输出可验)    ──→  自动校验 + 对账 + 测试覆盖
D4(API可达)     ──→  系统集成 + 接口编排 + RPA
D5(降级可用)    ──→  熔断机制 + 人工兜底 + 备份流程
D6(合规可编码)  ──→  合规规则库 + 审计日志 + 风控模型
```

## 三、总分 → Tier 映射阈值

### 3.1 标准阈值（V5 数据校准后）

| Tier | 总分范围 | 典型特征 | V5 占比 |
|------|----------|----------|---------|
| **Auto** | 15-18 分 | D1≥2, D2≥2, D3≥3, D6≥2 | 19.3% (77/400) |
| **Aug** | 10-14 分 | D1≥2, D2≥1, D3≥2, 总分≥10 | 27.0% (108/400) |
| **Hybrid** | 5-9 分 | 总分 5-9，规则或验证维度偏弱 | 44.0% (176/400) |
| **Human** | 0-4 分 | D1≤1, D2≤1, D3≤1, 主观判断为主 | 9.8% (39/400) |

### 3.2 边界规则

当总分处于阈值边界时，按以下优先级规则判定：

1. **D3(输出可验) 优先**: 若 D3=3 且总分≥14 → Auto；若 D3≤1 且总分≤5 → Human
2. **D1+D6 组合**: D1=3 且 D6=3 时，总分≥12 可上浮一级
3. **D2 否决权**: D2=0 时，即使总分高，最高只能评为 Aug（规则不清无法全自动）

### 3.3 M2 Tier vs 推导 Tier 差异处理

| 场景 | 处理规则 |
|------|----------|
| M2 Tier = 推导 Tier | 直接采用，无需调整 |
| M2 Tier = Auto, 推导 Tier = Aug | 以 M2 为准（Mark 对业务场景的理解更深）|
| M2 Tier = Hybrid, 推导 Tier = Aug | 需人工复核，通常保留 Hybrid（保守原则）|
| M2 Tier = Human, 推导 Tier = Aug/Auto | 以 M2 为准（存在隐性合规或情感因素）|

## 六、数据溯源与优先级规则

### 6.1 V5 数据溯源双维度说明

V5 表存在两个独立的"来源"字段，含义不同，需区分使用：

#### 维度 A：交付物来源（核心交付物本身的来源）

| 交付物来源 | 行数 | 占比 | 说明 |
|------------|------|------|------|
| **Agent 评分** (Mark) | 250 | 62.5% | 核心交付物来自 Mark 的 Agent 评分文档 |
| **语义推导** | 109 | 27.3% | 核心交付物基于 L4 名称关键词自动推导 |
| **价值节点 (Phase2)** | 35 | 8.8% | 核心交付物来自 Phase2 价值节点识别 |
| **迁移 (v5 重映射)** | 3 | 0.8% | 非标准 L3 重映射新增行 |
| **价值节点 (手动映射)** | 2 | 0.5% | 人工手动映射的价值节点 |
| **迁移 + 修正** | 1 | 0.3% | 迁移过程中修正的数据 |

#### 维度 B：Agent 评分来源（Tier/D1-D6 评分的来源）

| Agent 评分来源 | 行数 | 占比 | 说明 |
|----------------|------|------|------|
| **Agent 评分** | 223 | 55.8% | 评分直接来自 Mark 的 Agent 评分文档 |
| **语义推导** | 177 | 44.3% | 评分基于 L4 名称关键词自动推导补全 |

#### 两个维度的关系

- 250 行交付物来源=Agent评分 中，**223 行**评分也来自 Agent 评分，**27 行**评分来自语义推导（交付物是 Mark 给的，但评分后来补的）
- 35 行价值节点(Phase2) 的评分全部来自语义推导
- 109 行交付物来源=语义推导 的评分全部来自语义推导

### 6.2 优先级规则（冲突处理）

当同一 L4 存在多个数据来源时，按以下优先级确定最终内容：

```
优先级 1: Agent 评分 (Mark)      → 以 Agent 评分为准
优先级 2: 价值节点 + Agent 都有   → Agent 优先，价值节点入备注
优先级 3: 仅价值节点             → 价值节点为准，按语义规则补全评分
优先级 4: 语义推导               → 基于关键词自动推导，准确性最低
```

### 6.3 V5 重映射特殊处理

27 行非标准 L3 (BMD/BME/MSI/MSE) 已按语义映射到标准 82 L3-L4 体系：
- **替换目标 L4**: 用 27 行数据替换原有行内容，`migration_note` 记录原始映射
- **新增目标 L4**: 标准 L4 编码从审计表获取或顺延新增
- **冲突处理**: 多个源 L4 映射到同一目标 L4 时，保留相似度最高者，其余新增编码

### 7.2 规律总结

- **VS 层级越低（越靠近操作层）→ Auto 占比越高**

- **VS-3 设计层** 数量最少（24 个），因设计工作主观性强，Agent 化难度最大

### 8.1 自动校验项

| 校验项 | 规则 | V5 结果 |
|--------|------|---------|
| L3-L4 编码一致性 | L4 编码前缀必须与 L3 编码匹配 | ✅ 400/400 通过 |

### 8.2 人工复核建议

以下场景建议人工复核：

1. **M2 Tier ≠ 推导 Tier** 的行（约 130 行）
2. **总分 = 10 或 14** 的边界行（Tier 判定模糊）
3. **D2=0 但总分≥12** 的行（规则不清却高分，可能存在误判）
4. **价值节点来源** 的行（35 行，需确认 Agent 化评估是否准确）

## 十、使用指南

### 10.1 如何使用本映射表

1. **技术选型**: 根据 `Agent 能力需求` 列确定需要的技术栈（LLM / 规则引擎 / RPA 等）
2. **岗位设计**: 根据 `人介入点` 列设计人机协作岗位和 SOP
3. **ROI 评估**: Auto 级优先投入（ROI 最高），Human 级暂不考虑 Agent 化
4. **实施路径**: Hybrid → Aug → Auto 的渐进式升级路径

### 10.2 后续迭代建议

1. **动态更新**: 随着 Agent 技术进步，定期重新评估 D4(API可达) 和 D6(合规可编码) 维度
2. **业务验证**: 对 Aug 级交付物进行 PoC 验证，校准评分准确性
3. **规则沉淀**: 将 Hybrid 级交付物中重复出现的规则逐步编码，推动向 Aug 级进化
4. **数据补充**: 对语义推导的 177 行数据，建议逐步补充业务专家评分
