## 一、调研范围与背景

本次调研覆盖企业对外对内支付的全部业务场景，目标是：

1. 摸清现有 L3 流程对支付场景的覆盖情况
2. 识别流程架构缺口（哪些支付场景没有对应 L3/L4）
3. 提出新 L3 定义方案，并明确 L1 归属与 VS 归属
4. 确定调研数据如何落地到流程数据库（DIM_PROCESS / FACT_CARD）

调研涉及的支付场景分三类：

| 类别 | 典型场景 | 调研来源 |
|------|---------|---------|
| 对外业务付款 | 佣金转介费、权益服务商款、经代机构结算 | 业务付款需求调研（15条L3） |
| 员工报销 | 管理/服务/牌照各主体员工报销 | 员工报销调研（3个主体） |
| 主体差异 | 各主体审批链与合规要求差异 | 主体差异调研（4个主体） |

## 二、现状调研核心发现

### 2.1 支付场景与现有 L3 覆盖对照

| 支付场景 | 现有 L3 | 业务侧覆盖 | 财务执行层覆盖 |
|---------|--------|----------|-------------|
| 佣金转介费应派计算与实派清单 | L3-COM | ✅ L4-COM-10~13 | ❌ 止于财务制单，未到银行到账 |
| 塞尔斯代打佣金给 KA | L3-STLM | ✅ | ⚠️ 需确认是否覆盖执行层 |
| 权益服务商付款（活动/机酒车/品牌/培训/教练/咨询/移民教育） | L3-ACTV/TRVL/BRND/TRNG/COCH/CONS/IMED | ✅ 止于 Invoice | ❌ 付款执行未覆盖 |
| 服务结算与价值核算 | L3-SSVA | ✅ 价值核算层 | ❌ 止于核算，未到付款执行 |
| 经代机构结算 | L3-BSRV | ✅ | ⚠️ 需确认 |
| 晋升权益兑现（佣金部分） | L3-FPG → L3-COM | ✅ 走佣金路径 | ❌ 同 L3-COM 缺口 |
| **员工报销** | ❌ 无父 L3 | L4-EXP-01~05 已有 | ❌ 无父 L3 |
| **财务银行转账/支票执行** | ❌ 无 | — | ❌ 全面缺失 |

**核心结论**：现有 L3 覆盖了各业务线的"应付计算与指令发起"，但**财务执行层**（收到指令后的银行操作、回执归档、账务凭证）在所有付款场景中均缺失。

### 2.5 对外支付场景全景流程覆盖分析

以下逐场景梳理从业务触发到资金到账的完整路径，标注每段的 L3 覆盖状态。

#### 场景一：佣金转介费派发（最高频，合规风险最高）

```
保司打款到牌照账户
    ↓
[L4-COM-11] 银行到账确认与实收对账        ← 财务-各牌照财务  ✅ 有L4
    ↓
[L4-COM-12] 应派金额拆分与渠道对账        ← 中台支持-蔡依娜  ✅ 有L4（付款凭证）
    ↓
[L4-COM-13] 实派清单确认与财务制单        ← MoMo             ✅ 有L4
    ↓
[L4-COM-14] 财务付款执行（银行转账/支票） ← JorJor/NANA/SOSO ❌ 缺失
    ↓
[L4-COM-15] 付款回执归档与台账更新        ← 各牌照财务        ❌ 缺失
    ↓
KA / 塞尔斯 收款
```

| 项目 | 内容 |
|------|------|
| 付款对象 | KA、塞尔斯（转介公司）|
| 付款频率 | 1个月2次（15日续保 / 30日首单）|
| 走款主体 | 各牌照主体银行账户 |
| 合规要求 | IA监管：非持牌拨出率≤50%，同行≤88% |
| 当前痛点 | 无SOP；支票操作复杂，财务无时间复核；PDF乱码导致流程临时化 |
| **覆盖缺口** | **L4-COM-14/15 缺失，财务执行层无流程记录** |

#### 场景三：权益激励兑现给 KA（理财师）

```

    ↓

    ↓

    ↓

    ↓
[L4-COM-15] 财务合规性审核                      ← 财务    ❌ 无数据表
    ↓
[L4-COM-16] 管理层授权                          ← 管理层  ❌ 无数据表
    ↓
[L4-COM-17] 银行支付执行（FACT_PAID_LEDGER）    ← JORJOR(Chaya)/NANA  ✅ 有L4
    ↓
```

| 项目 | 内容 |
|------|------|
| 付款对象 | KA（理财师）— RW理财师 / 天领理财师 / GTD理财师 |

## 三、流程架构分析：L3 设计原则判断

### 3.1 核心判断：是否需要独立 L3-PAY？

**判断框架**：L3 的"端"取决于该流程的核心业务目标，不取决于哪个部门执行最后一步。

```
如果付款是这个 L3 的核心交付物（最终结果）
  → 财务执行 L4 应在这个 L3 内，不外拆

如果付款是这个 L3 的下游后果（触发另一个流程）
  → 财务执行 L4 属于下游 L3，不强行并入
```

**结论：不建立独立 L3-PAY（财务付款执行）**

独立 L3-PAY 违反端到端原则——它的触发点在另一个 L3 的中间，没有自己的业务起点，本质上是"半截流程"。正确做法是在各业务 L3 内补全末端财务执行 L4。

### 3.2 各 L3 的付款归属判断

| L3 | 付款是核心结果？ | 处理方式 |
|---|---|---|
| L3-COM 佣金全链路管理 | ✅ 是，转介费到账是终点 | 在 L3-COM 内补 L4-COM-14/15 |
| L3-SSVA 服务结算与价值核算 | ✅ 是，服务商收款是终点 | 在 L3-SSVA 内补 L4-SSVA-04/05 |
| L3-STLM 塞尔斯结算服务执行 | ✅ 是，KA 收款是终点 | 检查现有 L4 是否覆盖执行层 |
| L3-ACTV/TRVL/BRND/TRNG/COCH/CONS/IMED | ❌ 否，终点是 Invoice/服务确认 | 不加，付款由 L3-SSVA 承接 |
| L3-FPG 晋升裂变与权益兑现 | ⚠️ 部分是 | 佣金部分走 L3-COM；非佣金权益兑现需裁定 |
| L3-EXP 员工报销（新建） | ✅ 是，付款归档是终点 | 新建 L3，L4-EXP-01~05 已有 |

### 3.3 服务商付款的流转路径

服务商 L3 保持"服务交付"的纯粹性，付款统一由 L3-SSVA 承接：

```
L3-ACTV / L3-TRVL / L3-BRND / L3-TRNG / L3-COCH / L3-CONS / L3-IMED
  └── L4-XX-03  服务确认与反馈（产出：Invoice）
                        ↓ 触发
              L3-SSVA（服务结算与价值核算）
                └── L4-SSVA-04  服务商付款执行（新增）
                └── L4-SSVA-05  账务凭证归档（新增）
```
