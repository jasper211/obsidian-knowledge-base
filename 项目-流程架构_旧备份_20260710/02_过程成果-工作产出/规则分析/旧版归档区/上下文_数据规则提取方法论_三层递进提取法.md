# 数据规则提取方法论：三层递进提取法

> **版本**：v1.0  
> **目标**：从数据表清单出发，通过结构化分析 + 针对性访谈，产出覆盖「岗位-交付物-数据表-工作流程-规则」的完整分析报告，并完成 Agent 化可行性分级。  
> **输入**：数据部门提供的数据表清单  
> **输出**：完整分析报告 + Agent 化分级建议 + SOP 梳理

---

## 一、总体方法论框架

```
数据表清单（来自数据部门）
        │
        ▼
┌──────────────────────────┐
│  第一层：表结构分析        │
│  四标签法 → 识别潜在规则   │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│      规则空白地图         │
│  已知规则 / 潜在规则 /     │
│  规则缺口                 │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│  第二层：访谈设计          │
│  五问框架 × 规则空白       │
│  → 具体访谈问题清单        │
└──────────┬───────────────┘
           │
           ▼
     访谈执行（逐岗位进行）

           │
           ▼
     SOP 梳理 + 核心命题提炼
```

## 二、第一层：表结构分析 —— 四标签法

> **核心目的**：完全基于数据表信息，零访谈成本，识别出「哪些地方一定存在规则，但规则内容未知」。  
> **输出物**：每张表的四个标签 + 初步规则信号识别。

### 2.1 标签体系总览

对每张表依次打四个标签：

| 标签 | 维度 | 核心问题 | 规则信号 |
|:---:|:---|:---|:---|
| **A** | 表角色 | 这张表在数据链里是什么身份？ | 表类型决定规则高/中/低概率 |
| **B** | 分工断点 | 谁负责填 vs 谁负责审？ | 同一人 = 黑盒；跨人 = 接口规则 |
| **C** | 验证断点 | 程序验证路径在哪里？ | 验证链断裂处 = 规则缺口 |
| **D** | 商业职能 | 这张表承载什么商业意图？ | 准入/合规/红线 = 授权规则必访 |

### 2.2 标签 A：表角色（数据链身份）

| 表类型 | 规则概率 | 信号说明 | 需关注的规则方向 |
|:---|:---:|:---|:---|
| **参数表 / 配置表** | ⚠️ 高 | 高概率存在人工维护规则 | 维护频率、触发条件、变更审批链 |
| **过程表** | ⚠️ 高 | 存在数据录入/清洗规则 | 录入标准、清洗逻辑、异常处理 |
| **事实表** | 中 | 规则在上游，本表是结果 | 追溯上游规则是否外化 |
| **聚合表** | 中 | 聚合逻辑本身是规则 | 汇总维度、计算口径、时间窗口 |
| **维度表** | 中 | 主数据治理规则 | 编码规则、更新机制、一致性校验 |

**操作提示**：标记为「⚠️ 高」的表类型，直接进入第二层重点访谈池。

### 2.3 标签 B：数据分工断点

分析表的维护责任人矩阵：

| 分工模式 | 规则信号 | 含义 |
|:---|:---|:---|
| **同一人填且审** | 🔴 规则黑盒 | 规则完全在人脑中，没有外化，离职即流失 |
| **A填 → B审** | 🟡 规则接口 | 交接处一定有隐性标准，需提取 B 的验收规则 |
| **A填 → B审 → C抽查** | 🟡 多级接口 | 每一级都可能有不同的判断标准 |
| **系统自动生成，人工仅复核** | 🟢 规则显性化程度高 | 关注复核触发条件和复核标准 |

**示例字段**：

```
表名：Config_Product_Exclusion_Range
填报人：Carrie
审核人：Carrie
标签B判定：🔴 规则黑盒（同一人填且审）
```

### 2.4 标签 C：程序验证方向

绘制表的验证链路：

```
表A → 程序验证 → 表B → 程序验证 → 表C
         ↑                  ↑
    B的生成规则在A里    C的生成规则在B里
```

| 验证链状态 | 规则信号 | 含义 |
|:---|:---|:---|
| 完整链路可追溯 | 🟢 规则显性化 | 可通过代码/配置反推规则 |
| 链路在某节点断裂 | ❌ 规则缺口 | 该节点处系统无记录，完全靠人工判断 |
| 无程序验证，纯人工 | 🔴 全人工规则 | 必须访谈补全 |

**关键动作**：在数据血缘图中标注所有「❌ 验证链断点」，这些是第二层访谈的必问点。

### 2.5 标签 D：商业职能定义

识别表所承载的商业意图：

| 商业标注 | 规则信号 | 必访方向 |
|:---|:---|:---|
| 准入确权 | 🔴 授权规则必访 | 谁有权决定？决策依据是什么？ |
| 合规红线 | 🔴 合规规则必访 | 红线定义？触线后的处理流程？ |
| 财务结算 | 🟡 核算规则需访 | 计算口径、时间节点、对账规则 |
| 风险管控 | 🟡 风控规则需访 | 阈值设定、升级机制、例外处理 |
| 日常运营 | 🟢 常规流程 | 标准化程度高，可按模板提取 |

### 2.6 第一层输出物：单表标签卡

每张表完成第一层分析后，产出标准化标签卡：

---

#### 表标签卡示例

**表名**：`Config_Product_Exclusion_Range`（产品排除范围配置表）

| 标签 | 判定结果 | 规则信号 |
|:---:|:---|:---:|
| A-表角色 | 参数表 / 配置表 | ⚠️ 高概率人工规则 |
| B-分工断点 | Carrie 填且审 | 🔴 规则黑盒 |
| C-验证断点 | 无程序验证，人工配置后直接使用 | 🔴 全人工规则 |
| D-商业职能 | 产品准入控制 | 🔴 授权规则必访 |

**初步规则信号汇总**：
- 该表存在高度人工维护的规则内容
- 规则完全由 Carrie 个人掌握，存在知识流失风险
- 无系统级验证，规则正确性依赖个人判断
- 涉及产品准入，属于授权规则，必须访谈提取

**进入第二层：重点访谈池 ★★★**

## 三、规则空白地图

### 3.1 地图结构

将所有表的标签分析结果汇总为一张矩阵地图：

| 表名 | A-表角色 | B-分工断点 | C-验证断点 | D-商业职能 | 规则空白摘要 |
|:---|:---:|:---:|:---:|:---:|:---|
| 表1 | 参数表 ⚠️ | 黑盒 🔴 | 断点 ❌ | 准入 🔴 | A/B/C/D 四维度空白 |
| 表2 | 事实表 | 跨人接口 🟡 | 完整 🟢 | 运营 🟢 | B 维度待确认 |
| 表3 | 聚合表 | 系统自动 🟢 | 断点 ❌ | 结算 🟡 | C/D 维度空白 |
| ... | ... | ... | ... | ... | ... |

### 3.2 三种空白状态的定义

| 状态 | 符号 | 定义 | 示例 |
|:---|:---:|:---|:---|
| **已知规则** | ✅ | 可从表结构、代码、文档中直接推导 | 字段类型、主外键关系、代码中的计算逻辑 |
| **潜在规则** | ❓ | 知道一定存在规则，但不知道具体内容 | "产品排除范围"——知道有排除逻辑，但不知道排除条件 |
| **规则缺口** | ❌ | 系统完全没有记录，依赖人工且未外化 | 审批人在什么情况下会say no？判断标准是什么？ |

### 3.3 空白地图的使用方式

1. **按表维度**：每张表有哪些 ❓ 和 ❌，一目了然
2. **按标签维度**：所有表的 B-分工断点 中，有多少 🔴 黑盒需要解包
3. **按优先级**：同时满足 A=⚠️ + B=🔴 + D=🔴 的表，进入优先访谈队列

## 四、第二层：访谈设计 —— 五问框架

### 4.1 五问框架定义

| 问题编号 | 问题名称 | 核心问法 | 提取目标 |
|:---:|:---|:---|:---|
| **Q1** | 岗位定位 | 「你的岗位在这张表里扮演什么角色？」 | 岗位-表关系映射 |
| **Q2** | 输入依赖 | 「你做这件事之前，需要拿到什么信息？」 | 上游数据源 + 接收标准 |
| **Q3** | 操作步骤 | 「你能一步步描述你怎么处理这张表吗？」 | 操作流程 + 判断节点 |
| **Q4** | 判断标准 | 「什么情况下你会这样做而不是那样做？」 | 规则内容（最关键） |
| **Q5** | 输出交付 | 「处理完后，你把结果交给谁？怎么交接？」 | 下游接口 + 交付标准 |

### 4.2 从规则空白 → 五问映射

规则空白地图中的每个 ❓ 和 ❌，需要映射到五问中的具体问题上：

| 空白类型 | 对应问题 | 映射逻辑 |
|:---|:---|:---|
| A-表角色不明 | Q1 + Q3 | 先定位岗位角色，再追问操作流程 |
| B-黑盒（同一人填审） | Q3 + Q4 | 重点追问操作步骤和判断标准 |
| B-接口（跨人交接） | Q5 + Q2 | 追问交付标准和上游接收标准 |
| C-验证链断点 | Q3 + Q4 | 追问断点处的人工判断逻辑 |
| D-授权/合规类 | Q4 + Q1 | 追问决策标准和授权边界 |

### 4.3 访谈问题生成示例

以第一层示例表 `Config_Product_Exclusion_Range` 为例：

**该表空白状态**：
- 标签A = 参数表 ⚠️ → 高概率人工维护规则（❓）
- 标签B = Carrie 填且审 🔴 → 规则黑盒（❌）
- 标签C = 无程序验证 🔴 → 全人工规则（❌）
- 标签D = 产品准入 🔴 → 授权规则（❌）

**映射到五问 → 生成具体问题**：

| 五问 | 具体访谈问题 | 目标规则 |
|:---|:---|:---|
| **Q1** | 「你在产品排除配置这个环节，主要职责是什么？这个表是你一个人维护吗？」 | 确认岗位职责边界 |
| **Q2** | 「你在更新这个配置表之前，会从哪些地方获取信息？比如谁告诉你某个产品要排除？」 | 提取上游信息来源 |
| **Q3** | 「你能完整描述一次更新排除范围的流程吗？从收到需求到配置完成，每一步做什么？」 | 提取操作流程 |
| **Q4** | 「什么样的产品会被排除？有没有明确的判断条件，还是靠经验判断？」<br>「有没有边界案例——某个产品你犹豫过要不要排除？当时怎么决定的？」<br>「排除范围多久更新一次？什么情况下会触发紧急更新？」 | **提取核心规则内容** |
| **Q5** | 「配置完成后，这个结果谁在下游使用？他们怎么知道排除范围变了？」 | 提取下游交付规则 |

## 五、第三层：规则匹配与填充

### 5.1 填充流程

```
规则空白地图（第一层产出）
      +
访谈原始记录（第二层产出）
      ↓
逐条填充每个 ❓ 和 ❌
      ↓
完整度检验：所有空白是否已填补？
      ↓
【是】→ 进入报告撰写
【否】→ 标记残余Gap → 补充访谈 or 接受风险
```

### 5.2 填充标准格式

对每个潜在规则（❓）和规则缺口（❌），访谈后需填充以下字段：

| 填充字段 | 说明 | 示例 |
|:---|:---|:---|
| **规则内容** | 访谈提取到的具体规则描述 | 「产品排除判断标准：①监管禁止类直接排除 ②收益率低于X的产品排除 ③历史违约产品排除」 |
| **规则外化状态** | 规则是否已被记录在某处 | □ 数据表字段 □ 业务文档 □ 口头经验 □ 完全未记录 |
| **执行方式** | 当前是人还是系统执行 | □ 全自动 □ 半自动+人工复核 □ 全人工 |
| **完整度判断** | 访谈后是否还有Gap | □ 已完整 □ 仍有Gap（说明：_____） |

### 5.3 完整度检验清单

在所有访谈完成后，逐项核对：

- [ ] 第一层标记为 ❓ 的所有项，是否已有规则内容填充？
- [ ] 第一层标记为 ❌ 的所有项，是否已有规则内容填充？
- [ ] 所有 🔴 规则黑盒，是否已解包（规则已外化）？
- [ ] 所有 ❌ 验证链断点，是否已补全人工判断逻辑？
- [ ] 是否存在新发现的规则（访谈中暴露的第一层未识别到的规则）？
- [ ] 残余Gap是否已标记风险等级（高/中/低）并指定跟进人？

```
┌─────────────┐
│    岗位      │  ← 谁在做什么
├─────────────┤
│   交付物     │  ← 产出什么

│   数据表     │  ← 用什么数据

```

| **D1-D6分级表** | Agent化可行性 | 技术团队评估自动化落地顺序 |

## 七、D1-D6 Agent化分级标准

### 7.1 分级维度

每个岗位-交付物组合从以下维度打分：

| 维度 | 说明 | 高分标准 |
|:---|:---|:---|
| **规则完整度** | 规则是否已全部提取且无Gap | 规则100%提取，无残余Gap |
| **规则外化度** | 规则是否已从人脑外化为可读取的形式 | 有文档/数据表记录，非纯口头 |
| **流程标准化** | 操作流程是否标准化、少例外 | 流程清晰，例外情况<10% |
| **输入输出明确度** | 输入数据和交付物是否定义清晰 | 输入输出均可结构化描述 |
| **系统依赖度** | 是否依赖特定系统的特殊功能 | 可在通用平台实现 |

### 7.2 六级定义

| 等级 | 名称 | 定义 | 特征 | 下一步行动 |
|:---:|:---|:---|:---|:---|
| **D1** | 完全自动化 Ready | 规则完整、外化、标准化，可直接配置为Agent | 五维度全高分 | 进入Agent开发队列 |
| **D2** | 高可行-需少量标准化 | 规则基本完整，需补充少量文档或标准化例外处理 | 规则完整度/外化度略低 | 补标准化文档后进入开发 |
| **D3** | 可行-需规则补全 | 主要规则已提取，但存在残余Gap需补充 | 规则完整度中等 | 补充访谈+填补Gap |
| **D4** | 低可行-需大量规则工作 | 规则提取不足，或例外情况过多 | 规则完整度低或例外>30% | 专项规则提取项目 |
| **D5** | 当前不可行-人脑依赖高 | 规则高度依赖个人经验，难以外化 | 规则外化度极低 | 先解包黑盒，再评估 |
| **D6** | 不适用自动化 | 需要人类判断、创意、或复杂协商 | 涉及战略决策/创意/谈判 | 保持人工 |

### 7.3 分级决策树

```
开始分级
  │
  ├─ 规则是否涉及战略判断/创意/谈判？
  │     └─ 是 → D6
  │
  ├─ 规则是否100%提取且无Gap？
  │     └─ 否 → 进入下方判断
  │     └─ 是 → 继续
  │
  ├─ 规则是否已外化（有文档/配置，非纯口头）？
  │     └─ 否 → D5（先解包黑盒）
  │     └─ 是 → 继续
  │
  ├─ 流程标准化程度？
  │     ├─ 例外>30% → D4
  │     ├─ 例外10-30% → D3
  │     └─ 例外<10% → 继续
  │
  ├─ 输入输出是否100%结构化？
  │     └─ 否 → D2（补标准化）
  │     └─ 是 → D1（Ready）
```

## 八、SOP 梳理指南

### 8.1 从分析报告到 SOP

第三层产出的逐岗位详细分析，可直接转化为标准化SOP：

```
逐岗位详细分析中的「工作流程」
         +
逐岗位详细分析中的「规则清单」
         ↓
    结构化SOP文档
```

### 8.2 SOP 标准结构

| 章节 | 内容 | 来源 |
|:---|:---|:---|
| **目的** | 这个SOP解决什么问题 | 岗位定位 |
| **适用范围** | 适用于什么场景/不适用什么场景 | 访谈Q1 |
| **角色与职责** | 谁负责什么 | 岗位-交付物映射 |
| **流程图** | 可视化流程 | 工作流程分析 |
| **步骤说明** | 每一步的操作细节 | 访谈Q3 |
| **判断标准** | 每个决策点的判断依据 | 访谈Q4（核心） |
| **输入输出** | 需要什么、产出什么、交给谁 | 访谈Q2+Q5 |
| **常见问题** | 边界案例、例外处理 | 访谈中的追问 |
| **变更记录** | 版本历史 | 持续维护 |

### 8.3 SOP 质量检查清单

- [ ] 一个没做过这个岗位的人，按照SOP能独立完成工作吗？
- [ ] 所有判断节点都有明确的标准吗？
- [ ] 边界案例都有覆盖吗？
- [ ] 输入输出来源都清晰吗？
- [ ] 例外情况的处理路径都定义了吗？

### 附录C：术语表

| 术语 | 定义 |
|:---|:---|
| **规则黑盒** | 规则仅存在于个人经验中，未以任何形式外化，他人无法获取 |
| **规则接口** | 跨岗位/跨人交接处的隐性标准，交接双方可能对同一标准有不同理解 |
| **规则缺口** | 系统、文档、流程中均没有任何记录，完全依赖临时判断的环节 |
| **规则外化** | 将人脑中的经验转化为可读取、可传递、可执行的形式（文档/配置/代码） |
| **验证链断点** | 数据血缘中，程序无法自动验证数据正确性的节点 |
