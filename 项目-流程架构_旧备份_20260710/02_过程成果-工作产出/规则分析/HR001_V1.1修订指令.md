## 修订项一：C2信号定义修正（Issue-1）

**问题**：岗位治理来源的业务定义字段被批量归入C2（含手工计算），导致C2信号失去区分度。

**涉及表**：dim_position / dim_position_grade / dim_job_family / config_position_alias（部分字段）/ bridge_position_grade（部分字段）

**修订规则**：对这批字段按以下标准重新归类——

| 原归类 | 字段特征 | 修订归类 |
|---|---|---|
| C2 | 有枚举约束（career_track / job_family / sub_family / proficiency_level / parent_family_code / default_career_track / career_track_code / entity_type等） | 改为 **C5**（FK/枚举约束） |
| C2 | 纯人工维护、无计算逻辑（position_name / position_name_standard / family_name / grade_name / grade_label / description等命名/描述类字段） | 改为 **C1**（人工录入） |
| C2 | **保留C2**（有真实计算口径或人工判断逻辑的字段） | current_headcount / confidence / alias_type / is_default / is_active / reporting_level |

## 修订项二：P1-003条目修订（Issue-2）

**位置**：规则空白地图 → P1级 → P1-003（fact_performance_eval）

**原文**：
```
| P1 | fact_performance_eval | 绩效评估结果置信度规则（rating_confidence字段）未定义，影响奖金计算准确度 | 语义盲区 | Q3+Q4 | D2+D3 | HR绩效经理 | rating_confidence的评分标准是什么？... |
```

**修订为**：
```
| P1 | fact_performance_eval | 绩效评估加权总分（total_weighted_score）的加权系数来源及权重分配规则未文档化，评估结果争议处理机制未定义 | 语义盲区 | Q3+Q4 | D2+D3 | HR绩效经理 | total_weighted_score的加权计算规则是什么（attitude/ability/achievement各项权重如何分配）？权重调整由谁决定？评估结果有争议时的处理流程是什么？ |
```

**修订原因**：rating_confidence字段不存在于fact_performance_eval（15字段）的数据字典中，原条目基于不存在的字段设计。修订后聚焦于真实存在的total_weighted_score（ETL计算字段）的口径问题。

## 修订项三：P0-003五问和D维度扩充（Issue-3）

**位置**：规则空白地图 → P0级 → P0-003（AGG_labor_cost_monthly）

**原文**：
```
| P0 | AGG_labor_cost_monthly | 聚合口径用户决策字段（includes_outsource/includes_consultant）每次聚合可能不同，无版本溯源 | 计算黑盒 | Q3+Q4 | D2+D3 | HR数据负责人 | ... |
```

**修订为**：
```
| P0 | AGG_labor_cost_monthly | 聚合口径用户决策字段（includes_outsource/includes_consultant）每次聚合可能不同，无版本溯源；触发条件未定义，授权主体不明 | 计算黑盒 | Q1+Q3+Q4+Q5 | D1+D2+D3+D6 | HR数据负责人 | includes_outsource和includes_consultant由谁在每个聚合周期决定？聚合ETL的触发时间和触发主体是什么？历史版本的聚合口径是否可追溯（aggregation_method字段的版本控制规则）？财务部门引用时是否知情该决策字段的存在？ |
```

**修订原因**：「includes_outsource由谁决定」是Q5授权问题（D6），「ETL何时触发」是Q1触发条件问题（D1），原映射仅覆盖Q3+Q4（计算口径+验收），遗漏了触发和授权两个关键维度。
