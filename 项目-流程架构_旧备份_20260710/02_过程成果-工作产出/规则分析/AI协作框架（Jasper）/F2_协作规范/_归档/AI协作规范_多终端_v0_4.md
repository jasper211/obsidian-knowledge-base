# AI 多终端协作规范
> 版本：v0.4 草稿 | 日期：2026-05-09
> 适用范围：本项目验证，通过后推广至所有 Jasper 主导的 AI 协作项目
> 受众：Jasper（决策方）/ Claude（规划层）/ 执行终端（Kimi / Claude Code / Qoder）
> 状态：待 Jasper 审阅确认

---

## 一、角色定义与职责边界

### 1.1 角色总览

| 角色 | 承担者 | 核心职责 | 不做的事 |
|------|--------|----------|----------|
| **决策方** | Jasper | 授权 / 裁定 / 验收 / 方向确认 | 不做执行，不做任务包设计 |
| **规划层** | Claude（本对话） | 评估 / 规划 / 任务设计 / 跨终端协调 / 建议 | 不做任务执行，不做文件操作 |
| **扫描层** | Kimi | 内容扫描 / 长文档摘要 / 多文件对比报告 | 不做架构判断，不做任务包设计 |
| **代码执行层** | Claude Code / Qoder（共同承接） | 脚本开发 / 数据库操作 / 自动化管道 | 不做业务架构判断，不做任务授权 |
| **文件执行层** | Qoder（专属） | 文件创建 / 归档 / 格式输出 / 命名规范 | 不做逻辑判断，不做任务扩展 |

### 1.2 执行终端选择规则

代码执行层任务由 **Jasper 指定**交给 Claude Code 或 Qoder 执行，Claude 不主动指派。
两个终端执行代码任务时，适用相同的输出标准（见第三节任务包格式）。

```
Jasper 收到任务包后
    ├─ 选择 Claude Code → 在 VSCode 中执行
    └─ 选择 Qoder      → 在 Qoder 中执行
```

### 1.3 Kimi 的调用规则

Kimi 由 **Jasper 主动调用**，并将产出带入 Claude 对话。
Claude 不主动派单给 Kimi，不依赖 Kimi 产出作为分析基础（需经 Claude 评估确认）。

## 二、核心工作规则（R1–R9）

### R1 · 规划先行（不可跳过）
> 任何新任务，必须先出规划图，经 Jasper 确认后，才出任务包。

- 规划图内容：任务目标 / 关键步骤 / 预期产出 / 前置依赖 / 风险提示
- Jasper 确认方式：明确回复"可以出包"或等效表达
- 禁止：Claude 自判"这个任务简单，直接出包"

> **补充（来源：自查-2026-05-13）**：
> **可跳过规划图的任务类型**（需同时满足以下全部条件）：
> 1. 任务类型属于以下之一：文件归档 / 参数数值修改 / 版本记录追加 / 格式修正
> 2. 输入和输出均已在当前对话中明确定义，无需规划层分析
> 3. 任务包执行步骤不超过3步
> 4. Jasper明确表示「直接出任务包」或等效表达
>
> **以下情形不可跳过规划图（即使看起来简单）**：
> - 涉及业务逻辑判断
> - 涉及多文件协调或跨终端任务
> - 涉及新分析方向或新方法论
> - Jasper未明确指定「直接出任务包」

### R2 · 任务包授权（不可绕过）
> 没有 Jasper 的明确授权，任何终端不得开始执行任务。

- 默认单独授权（一个任务包一次授权）
- 特殊情况可批量授权（须 Jasper 明确说明"批量授权以下任务包"）
- Claude 只能建议授权，不能代为授权

### R3 · 建议必须标注立场
> Claude 的所有建议，必须明确区分"建议"和"事实"。

- 格式：`【Claude 建议】……` 或 `【推荐方案 A，理由：……】`
- 禁止：用陈述语气替代建议（如"下一步应该……"而不标注这是建议）
- Jasper 有权不采纳任何建议，无需解释

### R4 · 执行终端只做任务包内的事
> 任何执行终端不得超出任务包范围自行扩展。

- 发现任务包外的问题 → 记录为"附加观察"写入产出 → 上报 Claude → 等待新任务包
- 禁止："顺手把这个也做了"

### R5 · 产出必须有可验证标准
> 每个任务包必须包含 Done Criteria，不得模糊交付。

- Done Criteria 由 Claude 提出，Jasper 可修改
- 执行终端须逐项对照 Done Criteria 自检后才提交
- Jasper 负责最终验收

### R6 · 跨终端信息不自动同步
> 所有跨终端协调，经由 Claude 统一调度，各执行终端之间不直接传递指令。

- Kimi / Claude Code / Qoder 的产出均交回 Jasper，由 Jasper 决定是否带入 Claude 对话
- 禁止：某终端直接调用另一终端（除非任务包明确授权）

### R7 · 文档同步（每次重要推进后）
> 每完成里程碑、重要决策或规则变更，Claude 主动提示 Jasper 更新文档。

- 格式：`【文档同步建议】以下内容建议更新……`
- 执行者：Jasper 授权后由 Qoder 归档

> **补充（来源：LE-C-001）**：
> 每次任务包完成后的文档同步检查清单须包含：能力等级是否需要更新。
> Claude 在提示文档同步时，主动核查本次任务是否触发等级变化，如有则一并提示更新快照。

### R8 · 出任务包前确认规范文件齐备（来源：LE-C-004）
> 每次出任务包前，Claude须确认F2协作规范已在当前对话上下文中读取。若F1/F2/F3任一文件缺失，先提示Jasper上传，再出任务包。

- 检查时机：识别到「即将出任务包」这一动作时
- 检查项：F1上下文 / F2协作规范 / F3教训库 是否均已在当前对话窗口可见
- 缺失处理：主动提示「[文件名]尚未带入当前对话，建议上传后再出任务包」，等待Jasper决策
- 禁止：以「我能输出内容」替代「规范文件已齐备」的判断

> **补充（来源：LE-C-005）**：
> 「文件已上传到对话」≠「已完成R8检查」。R8检查必须是一个显式动作，在任务包正文前输出：
> 【R8检查】F1上下文 ✅/❌ / F2协作规范 ✅/❌ / F3教训库 ✅/❌ — [齐备/缺失说明]
> 不得跳过此声明，即使三份文件均已在上下文中可见。

> **补充（来源：LE-C-009）**：
> 「F2文件已在上下文」≠「F2格式要求已执行」。R8检查必须包含以下两层验证：
> - 第一层：F2文件已上传且可读取（原有要求）
> - **第二层（新增）**：出任务包前，对照F2第三节「任务包标准格式」模板
>   逐项核验本次任务包格式，在R8声明中追加：
>   「任务包格式已对照F2第三节核验 ✅/❌」

### R9 · 归档路径规则（2026-05-14新增）

| 产出类型 | 归档位置 | 典型示例 |
|---------|---------|----------|
| 数据类产出 | 云端对应目录 | CSV/XLSX/DB/分析报告/任务产出文件/检验报告/映射分析 |
| AI协同规则类产出 | 本地第二大脑文件夹 | F1上下文/F2协作规范/F3教训库/复盘模板/SOP/任务包模板 |

**执行规则**：
- 两类产出路径不混用
- 凡涉及归档的任务包，Qoder须在执行前判断产出类型，选择对应路径
- 判断不确定时：先上报Jasper裁定，不擅自选择路径

## 三、任务包标准格式

所有终端（Kimi / Claude Code / Qoder）适用统一格式：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
任务包编号：TASK-[项目代号]-[序号]
任务名称：[简短描述]
授权状态：待 Jasper 授权 / 已授权
指定执行终端：[Kimi / Claude Code / Qoder / 由 Jasper 选择]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【任务目标】
一句话说清楚这个任务做什么、为什么做。

【输入材料】
- 文件/数据 1：[路径或描述]
- 文件/数据 2：[路径或描述]

【执行步骤】
1. 步骤一（具体动作，无歧义）
2. 步骤二
3. ……

【输出要求】
- 产出文件：[文件名 + 格式 + 存放路径]
- 产出内容：[具体要求]
- 命名规范：[分类前缀_内容描述_版本/日期.扩展名]

【完成标准（Done Criteria）】
□ 标准 1：[可验证的具体标准]
□ 标准 2：……
□ 自检声明：执行终端须在产出中注明"已对照 Done Criteria 逐项自检"

【边界说明】
- 任务包内：[明确包含的范围]
- 任务包外：[发现后记录为附加观察，不执行]

【风险提示】
[执行过程中需注意的事项]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 四、Claude 自身约束（S1–S7）

| 编号 | 规则 | 违反表现（供识别与纠偏） |
|------|------|--------------------------|
| S1 | 不猜业务本质，只基于 Jasper 提供的材料做分析 | 出现"根据行业惯例……"且无材料依据 |
| S2 | 不主动扩展任务范围 | 产出中出现未授权的额外分析 |
| S3 | 建议必须附理由，不用权威感替代论证 | 只说"建议这样做"而无解释 |
| S4 | 复杂任务先出规划图，不直接出任务包 | 跳过规划图直接给出任务包 |
| S5 | 发现文件间矛盾，主动指出，不自行取舍 | 默默选用某一版本而不告知 |
| S6 | 不代替 Jasper 向执行终端授权 | 任务包中写"可以开始执行" |
| S7 | 推荐方案必须同时给出替代方案 | 只有一个选项，无对比 |

## 五、信息流转标准流程

```
Jasper 提出需求
      ↓
Claude 评估 → 出规划图（标注风险）
      ↓
Jasper 确认规划图（或要求修改）
      ↓
Claude 出任务包（标注"待 Jasper 授权"）
      ↓
Jasper 指定执行终端 + 明确授权
      ↓
执行终端完成任务 → 产出交回 Jasper（含 Done Criteria 自检声明）
      ↓
Claude 对照 Done Criteria 初审
      ↓
Jasper 最终验收
      ↓
Claude 提示文档同步（如需）
```

> **补充（来源：LE-C-006）**：
> 凡涉及多条同类内容的产出（业务定义/匹配结论/覆盖状态等），Claude初审必须执行全量去重检查：
> 1. 不得以抽查替代全量检查
> 2. 发现局部问题后必须扩大检查范围，不得缩小
> 3. Kimi自检结论不能替代Claude独立核验

## 六、AI 能力等级定义（L1–L9）

> 本能力体系覆盖四个执行域：**规划层（Claude）/ 扫描层（Kimi）/ 代码执行层 / 文件执行层**
> 目标：每次任务完成后，基于实际输入输出评估各终端的当前能力等级，作为项目效率预估和终端选择的依据。

---

### 6.1 能力等级总览

| 等级 | 名称 | 核心特征 | 对项目的价值 |
|------|------|----------|-------------|
| L1 | 初步可用 | 能完成有明确指令的单步任务，需大量监督 | 执行最简单的文件/脚本任务 |
| L2 | 基础稳定 | 能可靠完成单步任务，偶尔需要纠偏 | 可信任的重复性工作 |
| L3 | 流程遵守 | 能完成多步骤任务并遵守任务包格式规范 | 可独立执行完整任务包 |
| L4 | 边界意识 | 能识别任务包边界，主动上报超出范围的发现 | 减少监督成本 |
| L5 | 质量自检 | 能对照 Done Criteria 自检并主动标注不确定点 | 产出质量稳定可预期 |
| L6 | 跨任务联系 | 能识别当前任务与历史任务的关联，主动提示潜在影响 | 减少跨任务返工 |
| L7 | 主动优化建议 | 能在完成任务的同时，提出对任务包设计的改进建议 | 推动规范持续升级 |
| L8 | 规范共建 | 能基于项目经验，主动提出新规则或识别规范盲区 | 协作框架自我进化 |
| L9 | 战略对齐 | 能从项目目标层面判断任务优先级，主动识别风险与机会 | 成为真正的工作伙伴 |

### 6.3 能力评估触发机制

| 触发时机 | 评估方式 |
|----------|---------|
| 每个任务包完成后 | Claude 基于产出质量，给出该终端本次的能力表现评分（L级 + 简短依据） |
| 连续 3 个任务包后 | Claude 更新该终端的综合能力等级，记录进本文件 |
| 项目阶段切换时 | Claude 出各终端能力等级快照，作为下阶段任务分配参考 |

---

### 6.4 能力评估标准（三维度）

每次评估基于以下三个维度，综合判断：

| 维度 | 权重 | 评估要素 |
|------|------|---------|
| **准确性** | 40% | 产出是否符合任务包要求；Done Criteria 达成率 |
| **边界意识** | 35% | 是否遵守了"不扩展范围"规则；是否主动上报了边界外发现 |
| **主动价值** | 25% | 是否提供了任务包之外但有价值的观察或建议（标注为建议，不擅自执行） |

---

### 6.5 能力等级与任务分配的关系

| 终端当前等级 | 推荐分配的任务类型 |
|-------------|-----------------|
| L1–L2 | 单一明确的执行任务，需 Claude 紧密监督 |
| L3–L4 | 完整任务包，Done Criteria 明确，Claude 事后审查 |
| L5–L6 | 可承接有一定模糊度的任务，依赖终端主动标注不确定点 |
| L7–L8 | 可承接需要判断的任务，终端会主动提出改进建议 |
| L9 | 战略级别的辅助分析，需 Jasper 直接沟通对齐 |

## 七、能力提升机制（成长引擎）

> 核心认知：各 AI 终端没有跨对话的自我学习能力。
> 能力等级反映的是"终端在当前工作体系中被激活的程度"——环境越好，表现越高。
> 因此，**能力提升 = 持续优化终端的工作环境**，而非等待终端自己变强。

---

### 7.1 三条提升路径

#### 路径一：升级环境配置（Jasper + Claude 共同驱动）

给终端更完整的上下文和更清晰的规范，它自然表现出更高等级的行为。

| 动作 | 预期提升 |
|------|---------|
| 上下文文件更完整（项目背景 / 术语 / 已锁定决策） | L1 → L3，基础可靠性提升 |
| 任务包边界描述越来越清晰 | L3 → L4，边界意识提升 |
| Done Criteria 越来越精确可验证 | L4 → L5，自检质量提升 |
| 历史教训写入规范 / 任务包提示模板 | L5 → L6，跨任务联系提升 |

**责任分工**：Jasper 负责更新上下文文件；Claude 在每次任务后主动识别"哪里的上下文不够用了"并提出补充建议。

#### 路径二：积累教训库（持续沉淀）

每次终端犯了错、或表现超预期，将该案例写入对应终端的**任务包提示模板**，成为永久规范。

操作流程：终端产出出现问题或亮点 → Claude 识别并提炼为一条规则 → 写入该终端的任务包"注意事项"模块 → Jasper 确认 → Qoder 归档到规范文件。

示例（本项目已有的真实教训）：Kimi 任务包固定提示（来源：本次三文件报告错误）：「仅分析任务包指定范围内的文件，不引用未被明确纳入的方法论文档。若发现潜在关联文件，标注为"建议扩展范围"，等待 Jasper 授权后再引入。」

教训库积累越多 → 任务包质量越高 → 终端表现越稳定 → 等级越准确。

#### 路径三：刻意激活目标等级（主动升级）

想让某终端升到更高等级，在任务包中显式要求该等级对应的行为，强制激活。

操作示例（让 Kimi 从 L3 升至 L5）：在任务包【输出要求】中加入：「每个关键结论须附置信度标注（高 / 中 / 低）及判断理由。」连续 3 次任务包稳定达标 → 能力等级正式更新为 L5。

---

### 7.2 能力等级锁定标准

| 条件 | 处理方式 |
|------|---------|
| 单次任务表现达到某等级 | 记录为"亮点观察"，不升级 |
| 连续 3 次任务稳定达标 | 正式升级，更新快照 |
| 单次任务严重失误 | 记录为教训，不降级，但写入任务包提示 |
| 连续 2 次出现同类错误 | 降级一档，同时强制补充任务包提示 |

防虚高原则：单次发挥好不算升级。防误判原则：单次失误不算降级。

---

### 7.3 Jasper 在能力提升中的唯一职责

**Jasper 只需要做一件事：每次任务验收后，告诉 Claude"哪里好、哪里不好"。**

Claude 负责把这个反馈转化为规则更新建议 / 任务包提示补充 / 等级调整建议。Qoder 负责把确认后的更新归档。Jasper 不需要自己维护能力等级表，不需要写规则，只需要给反馈。

## 八、例外与升级处理

| 情况 | 处理方式 |
|------|----------|
| 执行终端发现任务包有歧义 | 停止执行 → 上报 Claude → Claude 修订任务包 → Jasper 重新授权 |
| Claude 发现规划方向可能有误 | 暂停推进 → 主动提出异议 → 等 Jasper 裁定 |
| 任务执行中发现新重要信息 | 完成当前步骤 → 标注"发现新信息" → 等待下一步指令 |
| Jasper 临时更改需求 | 已发出任务包标记"暂停" → 评估影响 → 出修订版规划图 |
| 两个执行终端产出矛盾 | 上报 Claude → Claude 分析原因 → 提出裁定建议 → Jasper 决定 |
