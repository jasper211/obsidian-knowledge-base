## 四、系统设计：三层架构

### 第一层：信号采集与结构化
```
输入：外部信号原文
处理：识别信号类型 → 提取关键实体（业务场景/岗位/目标/问题）
输出：结构化信号
  {
    signal_id: 唯一ID
    signal_type: 任务指令/销售数据/录音
    signal_date: 日期
    raw_content: 原文
    extracted_entities: {
      business_scenario: 业务场景描述
      job_family: 涉及的岗位族
      objective: 目标/任务
      problem: 问题/障碍（若有）
    }
  }
```

### 第二层：信号×架构匹配
```
输入：结构化信号 + dim表
处理：
  语义匹配 → 找到最相关的L3/L4
  规则匹配 → KPI变化对应的L3关联
  精确匹配 → 关键词直接对应编码
输出：匹配结果
  {
    matched_l3: [L3编码列表]
    matched_l4: [L4编码列表]
    matched_kpi: [KPI编码列表]
    match_confidence: 高/中/低
    gap_type: 缺口/偏差/优化机会
  }
```

### 第三层：洞察生成与输出
```
输入：匹配结果 + experience-engine相关entry
处理：
  对照dim_l4_activity的标准（交付物/Agent Tier）
  结合experience-engine的历史经验和原则
  生成结构化洞察
输出：七模块洞察报告（见第五节）
```

## 十、上下文管理规则（Context Window SOP）

> 来源：2026-05-12 实战教训 LE-C-003

### 10.1 为什么需要主动管理

Claude的上下文窗口有容量上限。对话越长，早期内容被压缩的概率越高，回复质量下降。本项目使用三份F类文件（F1上下文/F2协作规范/F3教训库）作为跨对话记忆载体，必须在正确时机切换新对话并带入文件。

### 10.2 开新对话的触发条件（Claude判断，Jasper决策）

| # | 触发条件 | 说明 |
|---|---------|------|
| T1 | 对话持续超过**5天** | 跨越5个自然日必须启动，不论任务量多少 |
| T2 | 本对话累计任务包数量超过**50组** | 含所有TASK-EEP-XXX编号，达到50组时在下一个任务间隙提示 |
| T3 | Claude分析文档数量超过**80个** | 含上传文件、项目知识库调用、对话内读取的文件，累计超过80个时提示 |
| T4 | 新任务判断为**独立任务且与当前对话任务链无依赖**，由Jasper主导发起 | Claude判断新需求与当前对话任务链无承接关系时提示，由Jasper决定是否另开 |
| T5 | Claude主动判断**回复质量存在风险** | 被动托底，感知到上下文压缩导致回复质量下降时提示 |

**决策机制**：Claude识别触发条件后主动提示，是否开新对话由Jasper决定，Claude不自行切换。
