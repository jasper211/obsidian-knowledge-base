## 四、系统设计：三层架构

### 第一层：信号采集与结构化
```
输入：外部信号原文
处理：识别信号类型 → 提取关键实体（业务场景/岗位/目标/问题）
输出：结构化信号
  {
    signal_id: 唯一ID
    signal_type: 任务指令/销售数据/录音
    signal_date: 日期
    raw_content: 原文
    extracted_entities: {
      business_scenario: 业务场景描述
      job_family: 涉及的岗位族
      objective: 目标/任务
      problem: 问题/障碍（若有）
    }
  }
```

### 第二层：信号×架构匹配
```
输入：结构化信号 + dim表
处理：
  语义匹配 → 找到最相关的L3/L4
  规则匹配 → KPI变化对应的L3关联
  精确匹配 → 关键词直接对应编码
输出：匹配结果
  {
    matched_l3: [L3编码列表]
    matched_l4: [L4编码列表]
    matched_kpi: [KPI编码列表]
    match_confidence: 高/中/低
    gap_type: 缺口/偏差/优化机会
  }
```

### 第三层：洞察生成与输出
```
输入：匹配结果 + experience-engine相关entry
处理：
  对照dim_l4_activity的标准（交付物/Agent Tier）
  结合experience-engine的历史经验和原则
  生成结构化洞察
输出：七模块洞察报告（见第五节）
```

## 五、洞察结构模板（七模块）

每一条洞察的标准输出格式：

```
─────────────────────────────────────────
洞察ID：INS-[日期]-[序号]
触发信号：[信号类型] [信号摘要]
匹配节点：[L3编码+名称] → [L4编码+名称]
─────────────────────────────────────────

【现象描述】
基于信号内容的客观描述，1-3句话

【架构定位】（来自EA数据底座）
- 所在价值流：VS-X [阶段名]
- 当前Agent化程度：Auto/Aug/Hybrid/Human
- 标准交付物：[来自dim_l4_activity]
- 关联企业KPI：[KPI编码+名称]

【经验参照】（来自experience-engine，若有）
- 历史类似信号：[时间+情况]
- 当时解决路径：[简述]
- 相关原则：[P-XXX 原则名称]

【洞察结论】
高概率原因：[1-2句]
需要确认：[1-2个验证问题]

【建议行动】（供决策方选择）
选项A：[具体行动]
选项B：[具体行动]
选项C：[若有]

【影响范围】
关联企业KPI：[KPI名称]（权重X%）
预计影响：[量化描述，若可得]
─────────────────────────────────────────
```

### 阶段1.0：概念验证（无代码，纯分析）

**目标**：验证洞察结构是否真的有价值，工程投入前先跑通一次

**任务0**（第一个任务）：
1. 取Mark最近3-5条任务指令
2. 手动做一次信号解析（提取实体）
3. 对照dim_l4_activity做匹配
4. 生成1-2份样本洞察
5. 评估：洞察是否有行动意义？七模块结构是否合适？

**验证问题**：
- 匹配准确率是否可接受？
- 洞察粒度是Mark级还是岗位负责人级更合适？
- 七模块结构有哪些需要调整？

### 阶段1.1：轻量管道（最小可运行版本）

概念验证通过后，用Python脚本实现：
- 读取Mark指令文档→结构化解析

- 输出标准洞察MD文件

### 阶段1.2：加入experience-engine

接入experience-engine的117个entry，补充洞察的经验参照模块

### 阶段1.3：扩展信号源
