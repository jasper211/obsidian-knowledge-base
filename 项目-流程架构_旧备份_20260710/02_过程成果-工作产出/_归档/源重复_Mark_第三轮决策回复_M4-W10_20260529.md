## 二、P1 技术决策 (Q5/Q7/Q8/Q9/Q10)

### Q5 · FCT_CHANNEL/FCT_PRODUCT 拆 2 张

**判断依据**: FCT_CHANNEL_partner(partner_code x month, 791行) 与 FCT_CHANNEL_ka(ka_id x month, 501行) 主键不同、JOIN 路径不同(bridge_partner_ka)、字段集不同。FCT_PRODUCT_id 与 sku 同理。强行合并一张表增加消费侧查询复杂度。

**推荐**: 拆 2 张。

**理由**: 业务粒度不同(partner != ka, product_id != sku)，拆开零成本(多两张视图)，消费侧不需要 WHERE discriminator。

**风险**: 消费侧可能误以为 5 张表是 5 种独立事实。缓解 -- P1 文档 Section 2 已标注"FCT_CHANNEL拆 partner+ka 两张、FCT_PRODUCT拆 id+sku 两张，对应任务书 2 张表"。

**结论**: x 同意拆 2 张。

---

### Q7 · VIEW vs MATERIALIZED VIEW

**判断依据**: P1 四张表行量 <3,000，实时 JOIN 毫秒级。MATERIALIZED VIEW 引入刷新延迟 + 运维脚本 + 存储开销。

**推荐**: Phase 1 普通 VIEW。

**理由**: 行量级决定性能差异不显著。CP2 后行量暴增再评估升级，改造成本极低(CREATE MATERIALIZED VIEW 一句)。

**风险**: BI 复杂聚合场景下普通 VIEW 可能不如物化视图快。当前阶段(总行数 < 5,000)此风险不成立。

**结论**: x 同意 Phase 1 普通 VIEW。

---

### Q8 · 时间粒度 month only

**判断依据**: quarter/year 可在消费侧 DATE_TRUNC 实时聚合，不需预物化。多粒度物化会使视图数量 x3。

**推荐**: 只做 month。

**风险**: 零。

**结论**: x 同意。

**结论**: x 同意。

### Q10 · v_fact_sales_activity v2.2 多事件升级

**判断依据**: Carrie 在 5-27 Q1=A 落地的"成果记录表"基础上，主动从 v1(2,918行, 单一 event_type POLICY_SIGN) 升级为 v2.2(11,253行, 5 个 event_type: RESERVATION/POLICY_SIGN/SUBMISSION/APPROVAL/CANCEL)。升级理由: 命名 `sales_activity` 暗示多事件流，v1 单事件名不副实。v2.2 同时暴露业务流程洞察(预约->签单 4.7天 / 签单->递交 2.6天 / 递交->批核 23.5天)。

**推荐**: 接受 v2.2。

**理由**:
1. 功能无损 -- P1 全部视图加 WHERE event_type='POLICY_SIGN' 维持一保单一行聚合，验收时用此条件仍可查 2,918 行
2. 额外收益 -- 多事件视角可回答"保单全生命周期多少天""批核卡在哪个环节"等业务问题
3. 回退成本极低 -- 如后续发现问题，5 分钟改回 v1

**风险**: 多事件导致行数膨胀(2,918->11,253)，RENEWAL/CANCEL 事件占比高，BI 不做 event_type 过滤直接 SUM 会重复计算。缓解 -- Carrie 已在 P1 文档 Section 2 显式警告，所有 P1 视图均加过滤。

**结论**: x 接受 v2.2。
