# 企业架构与岗位分析系统 — Agent架构完整分析
> 版本：V1.0 | 日期：2026-04-22 | 用途：项目规划参考

---

## 一、背景与分析框架

本文基于两个视角的结合：

- **视角A（阶段性实战）**：当前项目数据不完整、持续更新的真实情况下，分阶段实现"输入岗位→输出报告"的目标所需的Agent
- **视角B（恒常运转）**：数据完整、系统成熟后，维持系统长期自动运转所需的Agent

两个视角的Agent有重叠，但优先级和触发条件不同。

---

## 二、视角A：阶段性实战Agent分析

> 针对现实：数据有缺口、文件持续新增、结论待Mark确认、架构还在迭代

### 核心挑战
```
数据缺口        → 报告有空白，需要标注而非报错
数据持续更新    → 今天的底座明天就过时
Mark决策未锁定  → 部分字段是"推导"不是"确认"
多模型并行      → output(Claude)/隔离，不能互相污染
```

### 阶段一：现在 → 数据底座跑通（当前阶段）

**需要的Agent：1个**

**A1 — 数据修复与补全Agent**
- 触发：每次有新文件上传或发现断裂点时
- 职责：
  - 识别编号格式差异 → 输出对照样本 → 等人工确认 → 批量修复
  - 识别缺失字段 → 判断能否从现有文件推导 → 推导并标注来源
  - 识别版本冲突（如A族V0 vs V0.2）→ 按最新版本规则处理
- 当前具体任务：
  - L3/L4编号格式对齐（Phase 4-1）
  - VS-1补录"授权与合同"阶段（Phase 4-2）
  - VS-2/3/4 l3_mapping补录
  - bridge_l4_job责任类型细化
- 特殊规则：所有推导数据必须在source_file字段标注"推导来源+待确认"
- 执行环境：VS Code Claude Code
- 人工介入点：编号对照确认、推导内容确认

---

### 阶段二：数据底座稳定 → A族报告原型跑通

**需要的Agent：2个（新增1个）**

**A1继续运转**（同上，处理新增文件）

**A2 — 缺口感知报告生成Agent**
- 触发：用户输入岗位名称或场景描述
- 与恒常版本的核心区别：**能感知数据缺口并在报告中明确标注**
- 职责：
  - 查询数据库 → 识别哪些板块有数据、哪些是空白
  - 有数据的板块：正常生成报告内容
  - 空白板块：不报错，而是输出"⚠️ 此板块数据待补充：[具体缺口描述]"
  - 推导数据板块：标注"📌 推导自[来源文件]，待[Mark/架构小组]确认"
- 输出格式：结构化JSON → 前端渲染（Teresa界面）
- 人工介入点：用户看到缺口标注后可触发补录流程

---

### 阶段三：多族报告跑通 → 持续更新闭环

**需要的Agent：4个（新增2个）**

**A1+A2继续运转**

**A3 — 增量更新感知Agent**
- 触发：03老板输出文档有新增或修改（定期扫描或手动触发）
- 职责：
  - 对比新旧文件 → 识别变更内容（新增EP/修改KPI/调整编制等）
  - 判断变更影响哪些表的哪些字段
  - 生成"变更影响清单" → 推送给你确认 → 确认后写入数据库
  - 同时标记受影响的已生成报告为"需重新生成"
- 人工介入点：变更内容确认（避免自动写错）
- 输出：变更影响清单.md + 数据库更新日志

**A4 — 版本管理Agent**
- 触发：任何JD文件版本升级时（如A族从V0.2→V1）
- 职责：
  - 识别新旧版本差异字段
  - 更新dim_job_family对应记录
  - 将旧版本归档到version_history表（不删除）
  - 标记受影响的报告缓存失效
- 人工介入点：版本升级确认（防止误覆盖）

## 三、视角B：恒常运转Agent分析（数据完整后）

> 系统成熟、数据稳定、Teresa架构已上线的目标态

### 第一层：数据维护Agent（后台常驻）

**B1 — 文档解析Agent**
- 触发：03文档新增/更新时自动触发
- 职责：解析新md/csv/txt → 识别结构化字段 → 更新数据库
- 与A3的区别：A3需要人工确认变更，B1在数据稳定后可以更高比例自动写入

**B2 — 数据质量巡检Agent**
- 触发：每周定期 + 每次数据库更新后
- 职责：检查空值/断裂点/版本冲突 → 质量报告 → 仅推送异常

### 第二层：分析生成Agent（查询时触发）

**B3 — 岗位匹配Agent**
- 触发：用户输入岗位名称或工作场景描述
- 职责：自然语言 → 数据库查询参数

**B4 — 架构分析Agent**
- 触发：B3输出后
- 职责：拉取L1-L5 + VS旅程 + Agent评分 → 组装结构化数据

**B5 — 报告生成Agent**
- 触发：B4输出后
- 职责：按模板填充 → 生成M0-M8/L1-L5/KPI/成长路径/Agent边界各板块

**B6 — 洞察推理Agent**
- 触发：M4阶段，管理层需要跨岗位分析时
- 职责：横向比较多岗位 → 识别协同缺口 → 主动洞察

### 第三层：交互与更新Agent

**B7 — 报告交互Agent**
- 触发：用户在界面追问
- 职责：补充查询 → 更新报告局部

**B8 — 反馈回写Agent**
- 触发：Mark/管理层对报告内容有修改或确认
- 职责：结构化修改内容 → 写回数据库 → 更新版本状态（草稿→确认→锁定）

## 四、汇总：完整Agent架构

### 4.1 全景图

```
用户输入（岗位/场景描述）
         ↓
    B3/A2 岗位匹配+缺口感知
         ↓
    B4 架构分析  ←────────────── 数据底座（SQLite→Teresa）
         ↓                              ↑         ↑
    B5 报告生成                    A1/B1 文档解析  A3 增量更新
         ↓                         A4 版本管理  B2 质量巡检
    Teresa交互界面
         ↓
    B7 报告交互  ←── 用户追问
         ↓
    B8 反馈回写 ──→ 数据底座更新

后台常驻：
    B2 数据质量巡检（每周）
    B6 洞察推理（M4阶段）
```

### 4.2 全部Agent一览表

| 编号 | 名称 | 层级 | 视角 | 启动阶段 | 触发方式 | 人工介入 |
|------|------|------|------|---------|---------|---------|
| A1 | 数据修复补全 | 数据层 | 实战 | 现在 | 手动触发 | 高（确认规律和推导内容） |
| A2 | 缺口感知报告生成 | 报告层 | 实战 | 数据底座稳定后 | 用户查询 | 中（看到缺口后决定是否补录） |
| A3 | 增量更新感知 | 数据层 | 实战 | 多族报告跑通后 | 文件变更 | 高（变更内容确认） |
| A4 | 版本管理 | 数据层 | 实战 | 同上 | JD版本升级 | 高（版本升级确认） |
| B1 | 文档解析 | 数据层 | 恒常 | 数据成熟后 | 文件新增/更新 | 低（异常才介入） |
| B2 | 数据质量巡检 | 数据层 | 恒常 | 数据成熟后 | 每周定期 | 低（仅推送异常） |
| B3 | 岗位匹配 | 分析层 | 恒常 | Teresa上线后 | 用户输入 | 无 |
| B4 | 架构分析 | 分析层 | 恒常 | 同上 | B3输出后 | 无 |
| B5 | 报告生成 | 报告层 | 恒常 | 同上 | B4输出后 | 无 |
| B6 | 洞察推理 | 报告层 | 恒常 | M4阶段 | 按需触发 | 中（洞察结论确认） |

| B8 | 反馈回写 | 交互层 | 恒常 | 同上 | Mark确认/修改 | 高（写回前必须人工确认） |

**合计：12个Agent（4个实战阶段性 + 8个恒常）**

### 4.3 实战与恒常的演进关系

```
A1 数据修复补全  ──演进为──→  B1 文档解析（人工介入降低）
A2 缺口感知报告  ──演进为──→  B5 报告生成（去掉缺口感知逻辑）
A3 增量更新感知  ──合并入──→  B1 文档解析
A4 版本管理      ──成为──→   B1的一个子功能模块
```

**关键洞察**：实战阶段的Agent本质是恒常Agent的"带训练轮版本"，核心差异是**人工介入的比例**。数据越完整、规则越清晰，人工介入越少，Agent越自主。
