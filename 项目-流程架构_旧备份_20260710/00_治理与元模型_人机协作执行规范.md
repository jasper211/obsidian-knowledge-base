# EA知识库项目 — 人机协作执行规范

> 基于Pipeline项目5天返工经验 × 外部权威最佳实践 × EA知识库实际需求
> 三方交叉验证后提炼的可执行规则

> **来源说明**：本文件为Mark下发的执行铁律，基于Pipeline项目经验提炼。

## 一、Pipeline返工教训 → EA项目可借鉴的7条铁律

### 铁律1：Spec先于实现（Pipeline教训ROI最高项，8x回报）

**Pipeline实证**：
- Spec跳步：4轮反工~8h，改一轮发现新bug
- Spec-driven重启：1h catch 20 bugs，后续任务发现已隐式完成

**外部验证**：
- Confluent Data Contracts：schema + 完整性约束 + 元数据 + 演化规则
- SVEF (Nature 2026)：6维schema评估框架

**EA项目适用**：
```
Pipeline 的 4 件套              →   EA 知识库的 4 件套
────────────────────            ────────────────────
schema.json (字段定义)          →   doc-meta-schema.yaml (文档元数据定义)
style-guide.json (样式契约)     →   L3-definition-schema.yaml (L3定义模板)
STYLE-GUIDE.md (命名约定)       →   NAMING-CONVENTION.md (编码/命名/版本规范)
extract_ref_styles.py (验证)    →   validate_kb.py (知识库自动验证脚本)
```

**具体规则**：在修改任何L3定义/RACI/岗位方案之前，先更新schema，再改内容，最后跑验证。

---

### 铁律2：禁止词停机（Pipeline教训中防止自作主张简化）

**Pipeline实证**：v1 PPT shape只有参考17%-36%，因为AI默认选了"简化版"。整体废弃。

**EA项目禁止词扩展**：

| Pipeline禁止词 | EA项目新增禁止词 | 触发场景 |
|---------------|----------------|---------|
| "简化版"/"占位符" | "暂不处理" | 发现RACI冲突但不上报 |
| "差不多"/"应该够用" | "应该一致" | 两份文件说法矛盾但不交叉校验 |
| "MVP"/"先跑通" | "先把框架搭起来" | 知识条目只有标题没有内容 |
| "为了节省时间" | "数量太多先跳过" | 22份协同框架批量处理但跳过校验 |

---

### 铁律3：_source三类标注（Pipeline最有价值的元数据机制）

**Pipeline实证**：9个_source误标导致无限循环调试。区分ref-extracted/design-upgrade/convention是消除歧义的核心。

**外部验证**：
- HBR "Provenance原则"：每条知识标注来源（人类创建 vs AI生成 vs 混合）
- MIT "Knowledge Co-Creation Loop"：AI草拟→人类校准→AI结构化→人类治理

**EA项目适用**：

| Pipeline的_source | EA知识库的_source | 含义 |
|-------------------|-------------------|------|
| ref-extracted | **source-doc** | 从源头文档(PDF/访谈/调研)提取的事实 |
| design-upgrade | **team-decision** | Teresa/赵琦/Mark团队决策 |
| convention | **ai-generated** | Claude生成，待人类校准 |

**具体规则**：每条L3定义、每个RACI判定、每份岗位方案，必须标注_source。AI生成的内容标注`ai-generated`，经Mark确认后升级为`team-decision`。

---

### 铁律4：验证后才能声明完成（Pipeline的规则4，贴原始数值）

**Pipeline实证**：禁止说"通过了"而不附数字。必须跑验证命令，贴原始输出。

**外部验证**：
- FedEx质量门：每层有客观指标+通过/不通过阈值
- ABS质量框架：6维质量评估，每个门预先约定阈值

**EA项目验证指标**：

```yaml
# quality-gate.yaml — EA知识库质量门定义
phase_1_底座:
  pass_criteria:
    l3_code_unique: true           # L3编码注册表无重复
    raci_conflict_count: 0          # RACI冲突清零
    zero_width_char_count: 0        # 零宽字符清零
    ssot_file_exists: true          # 流程主清单.xlsx存在
  
phase_2_穿透:
  pass_criteria:
    l3_with_definition: ">= 34"    # 34个核心L3均有定义
    l3_with_flowchart: ">= 34"     # 34个核心L3均有流程图
    capability_map_fill_rate: ">= 0.95"  # 业务能力地图填充率95%+
    kpi_penetration_rate: ">= 0.90"  # KPI穿透到L5比率90%+
  
phase_3_重组:
  pass_criteria:
    jd_v3_count: ">= 10"           # 核心岗位JD V3.0产出
    org_chart_approved: true        # 组织架构图经Mark审批

phase_4_AI化:
  pass_criteria:
    l5_ai_coverage: ">= 0.50"      # 50% L5有AI工作流
    efficiency_model_output: true   # 人效模型产出
```

### 铁律5：单任务深度优先（Pipeline的规则5，不跳到下一个）

**Pipeline实证**：同一session不主动跳到下一个slide，除非当前diff达标。

**EA项目适用**：
- 不跳到Phase 2直到Phase 1的4个pass_criteria全绿
- 每个L3文件夹补全后逐个验证，不批量跳过
- RACI 8处冲突逐条裁定记录，不打包说"都解决了"

**外部验证**：
- McKinsey知识管理：项目结束mandatory debrief，产出1-pager
- BCG 10/20/70：70%投入在组织变革(深度)而非技术(广度)

---

### 铁律6：源头文档先读，框架后搭（Pipeline NGP v1.0返工教训）

**Pipeline实证**：
- 先基于42份md会议纪要做NGP执行方案v1.0
- 完成后才读V3战略框架docx → 发现60%素材V3里已有
- 导致v1.1重做

**EA项目适用**：
- 已在本项目中严格执行：先全量读取100份文档，再设计架构
- 后续Phase中，任何新的L3定义工作，必须先读该业务线的源头调研纪要+业务资料(03模块)，再动手

**外部验证**：
- APQC KM框架5步：Create→Identify→Collect→**Organize**→Share。Organize之前必须完成Collect。
- KCS "Solve-Evolve"：先搜索现有知识→没有才创建

### 铁律7：外部反问句模板（Pipeline的spec跳步检测器）

**Pipeline版本**：
1. "这个数据是怎么提取的？" — catch估值/记忆冒充事实
2. "如果换ref，这个字段会自动更新吗？" — catch硬编码
3. "schema跟实际值是同一份吗？" — catch契约脱节
4. "这个bug下次会自动被catch吗？" — catch一次性修复

**EA项目扩展版**：
1. "这个L3定义的_source是什么？你读过源头文档了吗？" — catch AI编造
2. "这个RACI判定跟协同框架、岗位方案一致吗？" — catch跨文件矛盾
3. "如果Teresa修改了L3流程，RACI和岗位方案会自动被校验吗？" — catch人工同步
4. "这个知识条目过期后，谁负责review？" — catch无主文档
5. "32个KPI中哪些已经穿透到L5？拿出穿透矩阵。" — catch假穿透

## 二、外部最佳实践 → EA项目可借鉴的5个机制

### 机制A：知识衰减(Decay)机制
**来源**：HBR "Human-in-the-Loop Knowledge Architecture"

```yaml
# 每份文档frontmatter必填
valid_until: "2026-06-30"      # 过期日期
confidence: "verified"          # verified | draft | needs-review | expired
last_reviewed: "2026-04-10"    # 最后审核日期
owner: "teresa"                 # 文档Owner（离职需交接）
```

月度cron自动扫描：`valid_until < today` 的文档标记为`expired`，从索引中降权。

---

### 机制B：Knowledge Co-Creation Loop（4阶段人机循环）
**来源**：MIT Sloan Management Review

```
阶段1: AI草拟(Draft)      → Claude从源头文档提取L3定义初稿
阶段2: 人类校准(Calibrate) → Teresa/Mark审核补充隐性知识
阶段3: AI结构化(Structure) → Claude将校准后的内容编入标准化格式(schema)
阶段4: 人类治理(Govern)    → 定期审计质量、处理冲突、归档过期
```

**Pipeline对照**：这正是pipeline项目的实际工作模式——Claude生成代码，你review微调，Claude结构化，你最终签收。

---

### 机制C：EA as Code（架构制品代码化）
**来源**：Gartner "Composable Enterprise Architecture"

核心：将EA制品存储为机器可读格式(JSON/YAML/CSV)，而非Word/PPT。

**EA项目已实现的部分**：
- L3编码注册表.csv — 机器可读
- INDEX.md + CHANGELOG.md — 可追踪
- 6层目录结构 — 可程序化扫描

**待补充**：
- `doc-meta-schema.yaml` — 文档元数据schema
- `validate_kb.py` — 自动验证脚本
- Git版本管理 — 当前还不是git repo

---

### 机制D：RACI自动冲突检测
**来源**：综合RACI方法论文献 + 自建脚本

检测规则（将编码为`validate_raci.py`）：
1. 每个L3有且仅有1个A（Accountable）
2. 每个L3至少有1个R（Responsible）
3. A和R不应是同一角色（除非团队<3人）
4. 单人R超过阈值(如>10个L3)则预警过载
5. 协同框架中的R/A必须与RACI矩阵一致（交叉校验）

---

### 机制E：BCG 10/20/70法则（AI转型投入比例）
**来源**：BCG AI Transformation Research

```
10% — 算法/模型（Claude的Prompt链和工作流）
20% — 技术基础设施（知识库结构、验证脚本、MCP/RAG）
70% — 组织变革与流程重设计（RACI对齐、岗位重组、人效模型）
```

**对照你的Phase规划**：
- Phase 1-2 (底座+穿透) ≈ 20% 技术基础
- Phase 3 (组织重组) ≈ 70% 组织变革
- Phase 4 (AI化) ≈ 10% 算法/模型

比例合理。最大风险是Phase 3被跳过或压缩——BCG数据显示，跳过组织变革的AI项目失败率>80%。
