### 1.3 岗位族映射的三源交叉逻辑

**岗位族字段不在任何L5源文件中——这是我推导补充的。**

#### 源1: L4_Auto_JD_Mapping.csv（02中`M3_组织重组\L4_Auto_JD_Mapping.csv`）

- 80条 L4→岗位族 映射
- 字段: l3_code, l4_code, l4_name, value_stream, **job_family**, job_family_name, supervisor
- 精确度: **高**——这是Mark+Claude在M3阶段产出的JD映射

#### 源2: 核心介入点清单.csv（02中`M3_组织重组\核心介入点清单.csv`）

- 126条 L4→岗位族 映射
- 字段: EP编号, L3, L4编号, L4名称, Tier, 物理交付物, **岗位族**, 介入类型...
- 精确度: **最高**——这是M3阶段识别的88核心介入点（实际126条）
- 注意: 岗位族字段存的是中文名如"A_保司战略官"，不是代码"A"

#### 源3: RACI矩阵（02中`A6_RACI矩阵\` 下3个CSV）

- 32个 L3 有RACI角色数据
- 可从角色列推导"谁负责这个L3"，但角色粒度粗（"中台"而非具体岗位）
- 精确度: **低**——仅作参考，未在本次映射中直接使用

#### 我的推导优先级:

```
L5活动行的岗位族 = 
  1. 精确匹配: (L3编号, L4编号) 在源2介入点清单中 → 直接取岗位族
  2. 精确匹配: (L3编号, L4编号) 在源1JD映射中 → 直接取岗位族
  3. L3回退: L3编号 在交叉映射表中 → 取该L3的主要岗位族
  4. 负责人推导: "负责人"字段含关键词(BD→B族, 产品经理→F族等) → 推导
  5. 无法匹配 → 岗位族留空
```

#### 业务域推导（38个L3的岗位族来自业务域启发式映射）:

当L3不在介入点清单中时，我从L3注册表的"业务域"字段推导：

| 业务域关键词 | → 映射到岗位族 | 可信度 |
|------------|-------------|-------|
| 保司VS-1 | A_保司战略官 | ⚠️ 中（保司线应A+B族，但简单映射到A） |
| KA | B_保司BD/关系经理 | ✓ 高（KA线确实由BD负责） |
| 经代 / VS-2 | C_机构BD/交付 | ⚠️ 中（经代线可能涉及多岗位族） |
| 代理人 / VS-4 | D_代理人事业部负责人 | ✓ 高 |
| 理财师VS-4 | E_理财师辅导长 | ✓ 高 |
| L1-05权益中台 / VS-5企业客户 | F_权益中台负责人 | ⚠️ 中（权益线涉及F+C族） |
| 佣金 | G_佣金合规专家 | ✓ 高 |

**⚠️ 关键风险**：业务域推导是"一个L3只映射一个岗位族"，但实际中一个L3可能涉及2-3个岗位族（如L3-IAC保司授权，A族做战略决策，B族做合同执行）。当前的映射丢失了这个多岗位族维度。

## 三、如何从02开始搭建准确的数据底座

### 原则：02是唯一权威源，我只做映射和聚合，不做发明

当前我的脚本做了三类事:
1. **直采搬运**（无风险）: CSV列名对齐、行数统计
2. **编码归一化**（有依据但硬编码）: L3旧编码→新编码
3. **推导补全**（需验证）: 岗位族映射、业务域推导

**正确的搭建路径是：让02中的数据自己说话，减少推导层。**

### Step 1: 在02中建立5张标准维度表（让02自己成为数据底座）

不是在output中另建，而是直接在02的`00_治理与元模型/`下建5张CSV作为SSOT：

```
02_知识库/00_治理与元模型/
├── 维度表_L3注册表.csv       ← 已存在，需补"主岗位族"列
├── 维度表_L3岗位族映射.csv   ← 新建，从介入点清单+RACI精确提取
├── 维度表_L5活动标准.csv     ← 新建，6条业务线统一15列标准格式
├── 维度表_L4Agent化.csv      ← 已存在(L4-Agent化严谨评分.csv)
└── 维度表_KPI穿透链.csv      ← 新建（当前为空，等Mark确认32个KPI）
```

### Step 2: 补"主岗位族"列到L3注册表（消除业务域推导）

当前L3注册表10列无岗位族。应新增1列"主岗位族"，数据来源:

| 24个有介入点的L3 | → 直接从介入点清单取（精确） |
| 38个无介入点的L3 | → 人工确认（从协同框架txt中的RACI提取，或从RACI矩阵确认） |

**具体操作**：逐个打开53个L3协同框架txt，从中提取"主责A"角色，填入L3注册表的"主岗位族"列。这比业务域推导准确一个数量级。

### Step 3: 补L5活动到17个无覆盖的L3（消除最大缺口）

17个L3没有L5活动CSV，但02中53个L3有协同框架txt。协同框架的5节结构中：
- 第3节"流程图"中有L4步骤
- 每个L4步骤下可推导出L5经营活动

**具体操作**：对每个无L5活动的L3，从协同框架txt中提取：
```
协同框架第3节 → 每个KN(关键节点) → 就是L4
KN下的具体步骤 → 就是L5
KN的输入/输出 → 就是L5的输入/输出
```

### Step 4: 统一6条业务线L5 CSV的列结构（消除列名不一致）

当前6个L5 CSV列名各不相同。应以15列标准格式重写回02的`04_项目工作区/`下各业务线文件夹。

标准15列: 价值流, 价值阶段, 价值活动, L3编号, L3名称, L4编号, L4名称, L5编号, 序列, 经营活动, 活动描述, 输入, 输出, 负责人, 岗位族

### Step 5: 建KPI穿透链（最终交付物的核心缺失）

当前02中完全没有"KPI→L3→L5"的挂载关系。需Mark确认32个KPI指标后，新建：
```
维度表_KPI穿透链.csv
列: KPI编号, KPI名称, 挂载L3, 挂载L4, 负责岗位族, 度量方法, 目标值, 频率
```
