## 板块2：数据链全景

同行经代的业务数据，从"第一次接触"到"最后付佣金"，一共经过三类表：
**档案表**（谁是谁）→ **规则表**（怎么算钱）→ **付款表**（钱打给谁）。
目前档案表和规则表都有重要字段没有定义清楚。

**本次分析覆盖的1个价值节点**

【VN-IBRD-01 · 合作伙伴尽调记录】🟢通过
  Gate状态：Gate①挂数=PASS　Gate②落地=PASS　Gate③追溯=PASS
  起点A：业务端（白博文、江通等）推送的同行机构信息
  终点Z：尽调完成 → 判断合作路径（JF/UNIVIN/DW）→ 移交商务谈判
  生产方：菲菲（江通线）/ MoMo（白博文线）　消费方：L3-NG商务谈判与合同制定
  涉及数据表：
    dim_partner（合作伙伴档案）← 存所有合作伙伴的基本信息，业务人员手工维护Excel后同步进系统 ← ★P0：同行经代的分类和状态还没在系统里"落户口"
    dim_license（牌照档案）← 存牌照类型和有效期，业务人员手工维护 ← ★P0：牌照类型决定走JF还是UNIVIN，但系统和判断规则之间没挂钩
    dim_binder_agreement（协议档案）← 存合作协议类型和有效期，驱动结算逻辑 ← ★P1：协议类型和实际结算方式之间的对应关系没定
    config_partner_routing（牌照路由规则）← 按条件决定用哪张牌照算佣金，Agg2步骤四读取 ← ★P0：同行经代专属的路由规则行还是空的
    partner_tier_rules（佣金档位规则）← 按条件决定适用哪个佣金比例，Agg2步骤三读取 ← ★P0：同行经代的佣金档位没有默认标准
    map_partner_payee（收款人映射）← 决定佣金拆给哪些人、各分多少 ← ★P1：同行经代场景下的拆分规则未定义
    dim_payee（收款人档案）← 存银行账户和最低起付金额 ← ★P2：同行经代的最低起付标准未单独设定
    dim_comm_scheme / dim_strategy / bridge_strategy_routing（激励策略体系）← 战略激励顶层配置，IBRD适用 ← 暂无紧急缺口
    fact_target（目标业绩表）← 存各维度业绩目标，同行经代通过segment_code关联 ← 暂无紧急缺口

## 板块3：集群风险

**本次发现1类集群风险：config配置维护岗位同时掌控4张核心表的写入权限，且无独立复核**

config配置维护岗位（当前由业务人员手工维护Excel后同步）同时负责以下4个环节，且均无独立复核机制：

| 环节 | 操作内容 | 涉及表 |
|---|---|---|
| 合作伙伴分类维护 | 定义谁是同行经代、谁是个人顾问、谁是KA | dim_partner |
| 牌照信息维护 | 录入牌照类型、有效期、业务范围 | dim_license |
| 佣金路由配置 | 决定同行经代用哪张牌照（JF/UNIVIN/DW）算佣金 | config_partner_routing |
| 佣金档位配置 | 决定同行经代适用哪个佣金比例 | partner_tier_rules |

**通俗比喻**：
一家餐厅的菜单定价、会员等级、折扣规则、收款账户，全由同一个人手写维护。写错了没人核对，客人结账时系统按这些表自动算钱。等发现价格算错了，款已经打完，要倒查根源还得依赖这一个人手里的Excel。

## 板块4：P0规则空白（4条，立即处理）

### P0-001：合作伙伴档案缺少同行经代分类
**技术描述**：dim_partner（合作伙伴维度）/ partner_category字段，同行经代枚举值未定义，与B-01业务模式字段无映射
**调研状态**：✅ 已确认（调研批次8确认存在"同行经代"业务分类，但系统无对应编码）
**关联节点**：VN-IBRD-01 · 合作伙伴尽调记录
**访谈岗位**：菲菲 / Carrie
**通俗说法**：
- 系统里的合作伙伴分类，目前还没有"同行经代"这个类别。
- 菲菲和MoMo靠Excel和经验来区分谁是同行、谁是KA，换人就乱。
- 分错了类，佣金计算会用错规则，钱可能发错对象。
**期望做到**：系统在合作伙伴建档时，能自动或半自动识别"同行经代"类别，并与前端交接模板中的业务模式字段对应。

### P0-002：合作伙伴状态流转没有标准
**技术描述**：dim_partner（合作伙伴维度）/ partner_status字段，状态机未定义，与尽调结论（JF/UNIVIN/DW/暂不推进）无映射
**调研状态**：✅ 已确认（B-01 Q-16确认退回后一季度观察期关闭，但系统状态未跟进）
**关联节点**：VN-IBRD-01 · 合作伙伴尽调记录
**访谈岗位**：菲菲 / Terresa
**通俗说法**：
- 同行从"刚接触"到"签约"再到"终止"，系统里没有标准状态。
- 现在靠人记：谁还在观察期、谁已经签了、谁该关闭了。
- 人记就会漏，该关闭的没关，该跟进的没跟，年底对账一团乱。
**期望做到**：系统有完整的状态流转（潜在→意向→尽调中→签约→活跃→暂停→终止），尽调结论能自动驱动状态变更。

### P0-003：牌照类型和合作路径之间没挂钩
**技术描述**：dim_license（牌照维度）/ license_type字段，与A-02决策树三条路径（JF/UNIVIN/DW）的数据表映射未建立
**调研状态**：✅ 已确认（A-02 v1.2判断节点0已明确流程规则，但系统未配置自动映射）
**关联节点**：VN-IBRD-01 · 合作伙伴尽调记录
**访谈岗位**：MoMo / Carrie
**通俗说法**：
- 牌照类型决定走JF还是UNIVIN，这个判断现在靠菲菲或MoMo人工查。
- 系统里牌照类型和合作路径之间，没有自动挂钩。
- 查错了牌照，整个合作路径就错了，合同主体也会签错，后续佣金结算全错。
**期望做到**：录入牌照信息后，系统能根据牌照类型自动初判合作路径（JF/UNIVIN/DW），减少人工判断依赖。

### P0-004：同行经代的佣金"价目表"还是空的
**技术描述**：config_partner_routing（牌照路由）+ partner_tier_rules（档位规则），partner_category_condition中同行经代匹配条件未配置，assigned_license_code和档位未定义
**调研状态**：✅ 已确认（调研批次8确认档位由BD判断+贡献度调整，但系统无默认配置）
**关联节点**：VN-IBRD-01 · 合作伙伴尽调记录
**访谈岗位**：Carrie / 菲菲 / MoMo
**通俗说法**：
- 佣金计算的两张"价目表"，同行经代那一栏还是空的。
- 现在系统可能按默认规则跑，同行经代套用个人顾问的佣金比例。
- 比例错了，不仅钱算错，还可能引发合同纠纷，公司多付或同行不满。
**期望做到**：config_partner_routing和partner_tier_rules中，同行经代有专属的规则行和默认档位，系统能自动匹配。

## 板块5：P1规则空白（5条，尽快补全）

**[关于协议与结算]**

**P1-001**（MoMo）：协议类型和结算方式之间的对应关系没定
→ 合作协议签了，但系统里"同行推荐"对应哪种结算方式，JF和UNIVIN的签约主体不同，系统不会自动区分。每次要靠人手工选，选错了付款对象就错了。
▸ VN-IBRD-01

**P1-005**（Terresa）：合作协议到期了，系统不会提醒
→ 现在靠人记到期日，忘了续约就可能多付佣金或少付。没有自动预警，合同过期了业务还在继续，合规风险很大。
▸ VN-IBRD-01

**[关于佣金计算]**

**P1-002**（Carrie）：佣金"价目表"的优先级没有冲突检查
→ 新增规则时没人检查会不会和旧规则冲突。两条规则同时命中同一个同行，系统只取第一条，排错了顺序佣金就用错的规则算。
▸ VN-IBRD-01

**P1-003**（菲菲 / MoMo）：同行经代的佣金档位没有默认标准
→ MoMo说很多同行报的业务量是"烟雾弹"，实际贡献和说的不一样。档位定高了公司吃亏，定低了同行不愿意合作，现在全靠个人判断。
▸ VN-IBRD-01

**[关于佣金支付]**

**P1-004**（MoMo）：同行经代的佣金打给谁、怎么分，没有明确规则
→ 有的同行要分一部分给公司、一部分给个人，比例怎么定没人写。分错了账，财务对不上，同行也会来扯。
▸ VN-IBRD-01
