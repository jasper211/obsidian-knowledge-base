## 表1: 【产品SKU列表】/ DIM_PRODUCT_SKU
所属域：产品与供应域 | 表类型：维度表 | 字段数：20 | 审核状态：待审核

### A · 表类型规则洞察
维度表天然存在「主数据一致性」与「生命周期管理」规则风险。本表作为产品主数据入口，SKU与Product_ID的映射关系、保障/缴费年期范围的边界定义、上架状态的流转规则（Draft→上架→下架→淘汰）均可能缺乏显性规则。尤其「产品类型」与「业务线」字段若缺乏跨系统对齐标准，将导致下游佣金计算口径分裂。

### B · 分工断点与字段唯一责任
- 分工结构：数据分工=李思齐 / 填写人=Mia / Owner=产品专员 / Steward=Mia
- 责任模式：有分离（填写人Mia≠分工李思齐，存在交接）+ 判断理由：产品专员为Owner/Steward，但日常填写由Mia执行，需明确Mia是否有权修改非空核心字段（Product_SKU、Carrier_Code等）。
- 核心字段责任：Product_SKU（Owner=产品专员）、Carrier_Code（Owner=产品专员）、Product_Category（Owner=产品专员）、Business_Line（Owner=产品专员）——全部非空核心字段均由产品专员单点持有，但填写人并非产品专员本人，存在「指令-执行」断点。

### C · 程序验证路径与断点
- 验证路径：程序验证：佣金准入表→佣金事实表
- 在链位置：中间
- 验证盲区：程序验证仅能检测SKU在下游事实表中是否存在（格式/关联性正确），但无法检测「同一SKU关联了错误Product_ID」或「保障年期范围填写错误（如20年写成25年）」等语义错误。

### D · 商业职能与授权
- 职能定义：商业建模与结构定型 → 授权级别：中
- 审核状态匹配：匹配 + 理由：商业建模类表处于「待审核」，意味着产品主数据标准尚未固化，后续变更可能引发结构性调整。
- 合规风险：中 + 存在数据分工与填写人不一致，交接规则缺失易导致责任真空。

### 规则空白汇总（每表最重要的1-2个空白）
⚠️ Product_SKU与Product_ID的映射规则缺乏变更审批机制（谁有权发起映射调整、调整后如何通知下游） → 对应五问：Q3 → 对应D维度：D2
⚠️ 保障年期范围与缴费年期范围的填写缺乏与保司产品手册的自动化比对，依赖人工录入易出错 → 对应五问：Q4 → 对应D维度：D3

## 表4: 【产品佣金计算公式】/ CONFIG_PRODUCT_COMMISSION_FORMULA
所属域：费率确认域 | 表类型：参数表 | 字段数：13 | 审核状态：审核通过

### A · 表类型规则洞察
参数表的规则风险集中在「变更审批」「生效冲突检测」与「版本回滚」。本表存储佣金计算公式，直接影响财务支出，但多条公式针对同一产品SKU、同一合作伙伴、重叠生效日期时的冲突解决规则（优先级/覆盖逻辑）可能缺失。参数表若无生效/失效的自动化校验，易出现「同一时段存在两个有效公式」或「公式已失效但未触发下游重算」的规则黑洞。

### B · 分工断点与字段唯一责任
- 分工结构：数据分工=刘敏然 / 填写人=刘敏然 / Owner=刘敏然 / Steward=MOMO
- 责任模式：有分离（分工=刘敏然，填写人=刘敏然，但Owner=刘敏然/Steward=MOMO）+ 判断理由：Owner与Steward分离（刘敏然 vs MOMO），但填写人与Owner为同一人，需关注刘敏然修改公式后MOMO是否实际执行Steward复核职责。
- 核心字段责任：first_year_formula（Owner=刘敏然）、renewal_year_formula（Owner=刘敏然）、basic_rate_from（Owner=刘敏然）、extra_rate_from（Owner=刘敏然）、smpa_rate_from（Owner=刘敏然）——单点责任字段：first_year_formula与renewal_year_formula（直接决定首期/续期佣金计算结果，错误将直接造成财务偏差）。

### C · 程序验证路径与断点
- 验证路径：程序验证：佣金准入表→佣金事实表
- 在链位置：中间
- 验证盲区：程序验证能检测公式配置是否成功写入并向下游流转，但无法检测「公式逻辑本身是否数学正确」（如续期公式中引用了一个不存在的字段）或「佣金率超出了保司协议上限」等业务语义错误。

### D · 商业职能与授权
- 职能定义：None → 授权级别：未定义
- 审核状态匹配：缺失（无商业职能定义，无法评估匹配度） + 理由：无商业职能定义，但审核已通过；作为直接影响财务支出的参数表，缺乏「高授权级别」标注是重大规则空白。
- 合规风险：中 + 参数配置错误可能向下游传导，需关注生效规则与冲突检测机制。

### 规则空白汇总（每表最重要的1-2个空白）
⚠️ 同一产品SKU+合作伙伴在重叠生效日期存在多条公式时的冲突解决规则缺失 → 对应五问：Q3 → 对应D维度：D2
⚠️ 公式变更后的下游佣金重算触发机制与通知规则缺失（修改公式后，历史保单佣金是否重算） → 对应五问：Q1/Q5 → 对应D维度：D3

## 表5: 【牌照保司路由】/ CONFIG_LICENSE_CARRIER_MAPPING
所属域：费率确认域 | 表类型：参数表 | 字段数：13 | 审核状态：审核通过

参数表的规则风险在于「授权时效性」与「合规边界」。本表定义牌照与保司的授权映射，直接关系到平台出单合法性，但「授权状态」与「生效/失效日期」的联动规则（如授权状态=已过期时是否自动阻断出单）、同一牌照在不同时间窗口映射不同保司时的版本切换规则可能缺失。参数表若缺乏与合规系统的实时联动，易出现「授权已失效但映射仍生效」的合规红线突破。

### B · 分工断点与字段唯一责任
- 分工结构：数据分工=刘敏然 / 填写人=Momo / Owner=刘敏然 / Steward=MOMO
- 责任模式：有分离（填写人=Momo≠分工=刘敏然）+ 判断理由：数据分工与填写人不一致，存在交接规则。Owner=刘敏然/Steward=MOMO，但日常填写由Momo执行，需明确Momo的修改权限范围及刘敏然的复核触发条件。
- 核心字段责任：License_Code（Owner=刘敏然）、Carrier_Code（Owner=刘敏然）、Effective_From/To（Owner=刘敏然）、Is_Active（Owner=刘敏然）——单点责任字段：Is_Active（授权开关字段，误操作将直接导致无照经营风险）。

### C · 程序验证路径与断点
- 验证路径：程序验证：佣金准入表→佣金事实表
- 在链位置：中间
- 验证盲区：程序验证能检测映射记录是否流入佣金事实表，但无法检测「授权状态=有效但保司资质已过期」或「映射类型（临时/正式）填写错误导致合规审计不通过」等语义错误。

### D · 商业职能与授权

- 合规风险：高 + 涉及准入确权或合规红线，规则缺失将直接导致业务违规或财务损失。

⚠️ 授权状态与保司资质有效期的自动化联动规则缺失（保司资质过期时，映射是否自动失效） → 对应五问：Q3/Q4 → 对应D维度：D4

## 表6: 【佣金事实表】/ FACT_COMMISSIOM_RATE
所属域：费率确认域 | 表类型：事实表 | 字段数：36 | 审核状态：—

### A · 表类型规则洞察
事实表的规则风险在于「数据来源溯源」「计算口径一致性」与「时效性」。本表是佣金计算的核心事实记录，涉及36个字段，但字段级Owner与填写人信息在Sheet1中缺失，导致责任归属不清。事实表天然需要「计算规则版本标记」（用哪个版本的公式计算）与「数据来源批次追踪」（来自哪次ETL运行），若缺失将导致佣金差异无法追溯。此外，basic_rate/extra_rate/smpa_rate等多个费率字段同时存在时的优先级规则可能模糊。

### B · 分工断点与字段唯一责任
- 分工结构：数据分工=—（Sheet1缺失） / 填写人=—（Sheet1缺失） / Owner=刘敏然 / Steward=MOMO
- 责任模式：交接模糊 + 判断理由：Sheet1无此表记录，但Sheet2显示Owner=刘敏然/Steward=MOMO；CSV显示该表为ETL计算产出（非人工填写），但字段级Owner仍标记为刘敏然，需明确ETL生成字段与人工维护字段的责任边界。
- 核心字段责任：basic_rate（Owner=刘敏然）、extra_rate（Owner=刘敏然）、smpa_rate（Owner=刘敏然）、fyc_rate（Owner=刘敏然）、ryc_rate（Owner=刘敏然）——单点责任字段：basic_rate与extra_rate（直接决定佣金金额，但ETL计算逻辑若出错，Owner是否具备排查能力存疑）。

### C · 程序验证路径与断点
- 验证路径：程序验证：佣金准入表→佣金事实表（基于CSV推断，同链上游）
- 在链位置：中间
- 验证盲区：程序验证能检测数据是否从上游完整流入，但无法检测「公式应用错误（如应使用产品A的公式却使用了产品B）」、「佣金率小数位精度错误（如0.05写成0.5）」或「首期/续期佣金类型判断错误」等语义错误。

### D · 商业职能与授权
- 职能定义：准入确权与交付授权（基于CSV核心目的推断） → 授权级别：高
- 审核状态匹配：缺失（Sheet1无此表记录，审核状态未知） + 理由：作为核心财务事实表，缺乏表级审核状态跟踪是重大治理缺口。
- 合规风险：高 + 佣金事实表涉及财务结算，数据错误直接影响付款准确性与合规审计。

### 规则空白汇总（每表最重要的1-2个空白）
⚠️ Sheet1缺失导致表级责任归属与审核状态完全空白，存在治理黑洞 → 对应五问：Q5 → 对应D维度：D6
⚠️ basic_rate/extra_rate/smpa_rate同时存在时的优先级与互斥规则未显性定义 → 对应五问：Q3 → 对应D维度：D2

## 表7: 【源头佣金宽表】/ AGG_SOURCE_COMMISSION_WIDE
所属域：费率确认域 | 表类型：聚合表 | 字段数：15 | 审核状态：审核通过

### A · 表类型规则洞察
聚合表的规则风险在于「ETL计算逻辑透明性」「维度一致性」与「回滚机制」。本表将佣金事实表打平为宽表，所有15个字段在Sheet2中均标记为非空=否且Owner/Steward为空，意味着聚合规则（哪些字段GROUP BY、哪些字段SUM/MAX）缺乏责任人。聚合表若缺乏计算口径文档，业务人员无法判断宽表数值与原始事实表的差异是ETL逻辑导致还是数据错误导致。

### B · 分工断点与字段唯一责任
