## 二、M3期间的认知跃迁

### 跃迁1: M3北极星 = M4组织接口 (D-M3-005)
- **触发**: Mark灵魂拷问 — "这个模块我们到底总体要实现什么?"
- **之前**: M3 = 组织重组(一个独立的阶段)
- **之后**: M3 = M2流程和M4 agent之间的桥梁(一个接口层)
- **影响**: 写入CLAUDE.md第七·五节; 产出Global Rule 8(北极星先于战术)
- **意义**: 没有这次校准,M3会沦为"画组织架构图+写JD"的机械执行,无法真正服务M4
- **教训**: **每个里程碑开始时必须先锁定"这个模块到底服务什么",否则战术再精也是空转**

### 跃迁2: 岗位本质匹配 (D-M3-011, LE-M3-5)
- **触发**: Mark质疑 — "保司交付这个岗位与我减负还有关系吗?"
- **发现**: V0把战略设计/创意判断类授权给了执行型岗位 — 这不是"授权不够大胆",而是"授权跨越了岗位本质"
- **影响**: A族JD从"战略放大器"重定义为"规则执行器"; 减负清单V0→V0.2全面重构
- **意义**: 组织设计中最隐蔽的错误不是"少授权"或"多授权",而是"给错了类型的岗位"
- **教训**: **授权不能跨越岗位本质 — 执行型岗位只能承接执行/分析/谈判/评估,不能承接战略设计/创意判断/规则定义**

### 跃迁3: 永明战略关系是Mark的核心价值 (D-M3-014)
- **触发**: VS-1局部图评审时Mark明确 — "永明关系还是需要我来维护"
- **发现**: 不是所有"Mark保留"都是负担。顶级保司(永明)战略维护是Mark自愿承担的核心工作,是CEO核心价值表达
- **影响**: 减负清单区分"可减"vs"价值观保留" — 这是两种完全不同的"Mark保留"
- **意义**: 减负不是"把Mark清单减到零",而是"让Mark只做他应该做且愿意做的事"
- **教训**: **CEO保留项需要区分"还没减掉的负担"和"这就是CEO该做的核心工作",两者不能混为一谈**

### 跃迁4: KPI防火墙 = 防功能漂移的组织机制 (D-M3-017)
- **触发**: D+E族设计时发现理财师辅导长(E)容易被代理人事业部(D)业务压力同化
- **创新**: 3条KPI防火墙 — 内容100%非业务 / 考核权三方联签 / 红线事件保护
- **影响**: 首次在MGA组织设计中引入"防火墙"概念,从"靠人的自觉"升级为"靠机制的约束"
- **意义**: 授权容易,防止权力漂移难。KPI防火墙是比授权更底层的组织设计机制
- **教训**: **组织设计中,防止功能漂移的机制(防火墙)比功能授权本身更重要**

### 跃迁5: 减负清单需滚动校准 (D-M3-018, LE-M3-6)
- **触发**: D+E族JD写完后发现EP-101/125两条应由Mark保留
- **发现**: 减负清单不是一次性锁定。每份JD完成后都需要回溯审视,因为岗位设计会暴露新的"Mark必须保留"项
- **影响**: V0.2→V0.3, 保留项从9升至11条
- **意义**: 这不是"减负失败",而是"减负精度提高" — 每次校准都让清单更准确
- **教训**: **减负清单是动态资产,不是静态交付物。每个岗位设计完成后必须强制回溯**

### 跃迁6: 外部数据不是ground truth (HR数据返工)
- **触发**: HR提供的xlsx数据与预期不符,字段缺失、格式混乱
- **发现**: 直接使用HR数据做分析导致返工,浪费了M3早期的时间
- **影响**: 产出Global Rule 7(外部数据必须审计后使用); 产出HR数据质量审计报告
- **意义**: 这个教训普适性极强,不限于HR数据 — 任何从外部获取的数据都不能当作ground truth
- **教训**: **外部数据在使用前必须经过字段完整性、跨源一致性、时间覆盖、实体完整性四项审计**

## 三、关键成功经验 (SE)

### SE-1: 7族逐个JD + 分叉决策模式
- **做法**: 每族设计前先呈现3~4个分叉点让Mark裁定,再基于裁定写JD
- **收益**: 7份JD零返工(V0→V1一次过),因为方向在分叉时就确认了
- **可复用性**: **任何岗位设计前先做分叉决策,不要直接写JD。分叉决策的成本是10分钟,JD返工的成本是2小时**

### SE-2: 局部图→全图集成模式
- **做法**: 先画4张局部架构图(VS-1/VS-2/VS-4/L1-05),最后集成全图
- **收益**: 每张局部图可独立评审,全图集成时冲突极少
- **可复用性**: **组织架构设计应先局部再全图。局部图对应业务逻辑边界,天然减少跨域冲突**

### SE-3: Mark会议时间优化
- **做法**: 规则化会议从10次×2h=20h优化为4次×2.5h=10h(按主题合并)
- **收益**: Mark时间减半,节奏更紧凑,每次会议有完整的业务逻辑闭环
- **可复用性**: **多个小话题按业务逻辑合并为少数大会议,减少切换成本**

### SE-4: 5个组织创新符号
- **做法**: 战略双线 / KPI防火墙 / 双向考核 / 虚拟委员会 / M4预留横切层
- **收益**: 每个创新都有明确的组织治理问题对应 — 不是为创新而创新,而是为解决具体问题而设计
- **可复用性**: **这5个模式构成MGA组织设计的"符号系统",可用于其他AI组织化项目**

### SE-5: Ivan任务清单 = 跨职能"翻译"
- **做法**: 从"架构师语言"翻译为"HR执行指南",含5条拒绝权+4条加速权
- **收益**: HR不被架构师思维绑架,有自主空间判断执行优先级
- **可复用性**: **跨职能任务下达时必须翻译为对方的专业语言,不能用自己的行话**

## 四、关键教训 (LE) — 避免重犯

### LE-M3-1: 北极星必须在Day1锁定
- **事件**: M3启动时缺少北极星,前几个小时浪费在"作废的人效基线"上
- **原因**: 直接开始战术执行,没有先定义M3到底服务什么目标
- **教训**: 每个里程碑启动时必须先锁定北极星,不允许"边做边找方向"
- **预防**: Global Rule 8已强制 — "北极星先于战术,3个turn不回检北极星就暂停"

### LE-M3-2: 授权不能跨越岗位本质
- **事件**: A族V0把战略设计类授权分配给执行型岗位,导致V0→V0.2全面返工
- **原因**: 默认"减负=把Mark的事都分出去",没有区分事项性质与岗位本质的匹配度
- **教训**: 执行型岗位只能承接执行/分析/谈判/评估;战略设计/创意判断/规则定义只能由战略型岗位或Mark本人承担
- **预防**: JD设计前先确认岗位本质(执行/战略/专业),再匹配授权类型

### LE-M3-3: 外部数据不是ground truth
- **事件**: HR提供的xlsx直接用于分析,字段缺失导致返工
- **原因**: 信任"HR给的数据就是对的",未做任何审计
- **教训**: 任何外部数据必须经过字段完整性/跨源一致性/时间覆盖/实体完整性四项审计后才能使用
- **预防**: Global Rule 7已强制 — 外部数据审计是硬门槛,审计不过不允许进入分析

### LE-M3-4: 减负清单是动态的,不是一次性的
- **事件**: V0(29→20)→V0.2(20→保留9)→V0.3(保留9→11),每次JD完成后都发现新保留项
- **原因**: 减负清单在岗位设计之前做,而岗位设计会暴露新的"Mark必须保留"项(如EP-101/125)
- **教训**: 减负清单需滚动校准 — 不是"做完就锁定",而是"每份JD完成后强制回溯"
- **预防**: 建立机制: 每份JD完成 → 回溯减负清单 → 更新版本号

### LE-M3-5: 阶段可以并行,不必严格串行
- **事件**: D-M3-025 Mark决策P3 hold + P4.1并行启动
- **原因**: 默认"P3做完才能做P4",但P4.1基础设施(数据管道/规则引擎/告警)对P3的组织定型无依赖
- **教训**: 阶段之间不是严格串行,基础设施类工作天然可并行
- **预防**: 每阶段启动时评估"哪些下阶段任务可并行启动",不要等上阶段100%完成

## 六、元规则 (M3教会的底层规律)

1. **组织设计的颗粒度 = 介入点,不是L4数量** — 126个介入点(EP)决定了组织结构,不是300+ L4。L4是agent的边界,EP是人的边界,两者维度不同。

2. **减负是滚动的,不是一次性的** — 每个岗位设计都会暴露新的保留/授权/规则化需求。减负清单的"版本号增长"不是失败,是精度提高。

3. **防火墙比授权更重要** — 授权是"给权力",防火墙是"防权力漂移"。MGA组织中,业务压力同化专业岗位是真实风险,KPI防火墙是核心机制。

4. **"不是负担"的保留项 = CEO的核心价值表达** — Mark保留永明关系不是"还没减掉",是"这就是CEO该做的"。减负的目标是"精准",不是"清零"。

5. **阶段可以并行,不必串行** — P4.1与P3并行启动。基础设施(数据管道/规则引擎/告警)对组织定型无依赖。阶段之间的串行假设需要逐条验证。

6. **跨职能下达必须"翻译"** — 架构师给HR的任务清单不能用架构师语言。每个职能有自己的概念体系和判断标准,任务下达时必须翻译。

## 七、对M4的警告

### 警告1: M4.1基础设施选型需POC验证
- **风险**: M4 Agent优先级V0的技术栈(Drools/数据管道/告警)是概念级,未做任何技术选型
- **要求**: M4启动前需IT/Carrie做至少3个技术栈POC(规则引擎/数据管道/告警系统)
- **后果**: 不做POC直接建设 = 建在沙子上,返工概率极高

### 警告2: 80条Auto L4的"主人"需从JD反查
- **风险**: V0写了"A/B/C/D/E/F/G各族使用的agent",但具体哪条L4→哪个岗位→哪个人尚未精确映射
- **要求**: M4.1启动前需完成L4→岗位族→具体人员的三级映射
- **后果**: Agent没有明确"主人" = 没人为Agent的产出质量负责

### 警告3: P4.1的<=100万HKD预算假设需验证
- **风险**: D-M3-025把M4.1基础设施从430万降到100万(开源+内部方案),这是未验证的假设
- **要求**: Carrie需在M4启动前做实际成本估算
- **后果**: 如果100万不够,需要Mark重新裁定预算和范围

### 警告4: Mark规则化会议(M3.3)是M4的"规则引擎输入"
- **风险**: 10份规则文档 = P4.1规则引擎的业务规则输入源
- **要求**: M3.3的4次会议需按计划完成,产出可机器解析的规则文档
- **后果**: M3.3延迟 → P4.1 Week 8~12规则引擎灌入延迟 → 整个M4后半段滑坡

### 警告5: 过渡路径(M3.5)是M4人员到位的前置条件
- **风险**: 没有过渡路径,新岗位人选无法确定,Agent"主人"无法指派
- **要求**: HR模板回传是硬阻断,需催促Ivan按M3.5任务清单执行
- **后果**: 过渡路径延迟 = M4启动时"有agent无主人",组织接口断裂

### 警告6: M4不要重复M3的"北极星缺失"错误
- **风险**: M3 Day1因缺北极星浪费了时间在"作废的人效基线"上
- **要求**: M4启动时必须先锁定: "M4结束时,公司运营模式是什么样的? 哪些岗位已经有Agent辅助? 人效指标从多少到多少?"
- **后果**: 北极星缺失 = 战术空转,M3已经证明了这个代价
