## 4. 关键发现

### 4.1 有数据 vs 空表

- **有数据**: 26张表 (67%)
- **空表**: 13张表 (33%) — 集中在策略叠加域(6张)、财务结算域(3张)、公共域(2张)

### 4.2 数据阶段判断

| Kimball层 | 阶段 | 状态 |
|-----------|------|------|
| DIM (维度) | config导入 | 大部分到位，dim_date/dim_customer_type需补 |
| CONFIG (配置) | config导入 | 基本齐全 |
| FACT1 (费率) | Agent FACT1 | 已完成 — 12,505行 |
| FACT_POLICY (保单) | Agent ETL | 已完成 — 24行(测试量级) |
| Agg1 (佣金宽表) | Agent Agg1 | 已完成 — 2,741行 |
| Agg2 (层级费率) | Agent Agg2 | 已完成 — 6,804行 |
| Agg3 (业绩底表) | Agent Agg3 | 已完成 — 25行(测试量级) |
| 策略叠加 | 未开始 | 6张空表，对应Agg2/Agg3的策略叠加输入 |
| 财务结算 | 未开始 | 3张空表，下游结算尚未建设 |

### 4.3 数据质量观察

1. **fact_policy 仅24行** — 测试数据，非全量保单。全为2026年4月，仅SLHK保司
2. **fact_commission_rate 分布极不均衡** — SLHK占83% (10,437/12,505)，其余17家保司仅占17%
3. **fact_target vs fct_target 重名** — DDL用 `fact_target`(0行), Excel导入用 `fct_target`(62行), 需统一
4. **dim_date 为空** — 日期维度需脚本生成 (非Excel导入)
5. **策略叠加域完全为空** — 6张表0行，说明 strategy/scheme 功能还未配置

### 4.4 Kimball 数据流向

```
Layer 0 (33 insurer xlsx)
    ↓ 人工整理
Layer 1 (13 config/*.xlsx → 21张CONFIG/DIM表)
    ↓ Agent ETL
Layer 2 (Agent产出 → 5张FACT/AGG表)
    ↓ 未来
Layer 3 (策略叠加 → 6张Strategy表 = 当前空)
    ↓ 未来
Layer 4 (财务结算 → 3张Settlement表 = 当前空)
```
