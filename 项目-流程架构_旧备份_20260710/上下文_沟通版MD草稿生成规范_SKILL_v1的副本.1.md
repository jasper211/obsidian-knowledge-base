# SKILL：沟通版MD草稿生成规范
## 适用：三层递进提取法 · 第一层产出后 · 沟通版MD草稿（Step 2）
> 版本：v1.1 | 制定日期：2026-05-20 | 修订日期：2026-05-25
> v1.1修订：新增价值节点视角的板块2/板块3.5/板块4-6格式规范及板块1 Gate状态摘要卡，基于FIN001-V2实际执行后的结构缺失修复
> 配套文件：沟通版HTML报告生成标准_v1.3.md（HTML渲染规范，Step 4使用）
> 经验来源：佣金域（EFA005）/ HR域（HR001）/ 财务域（FIN001）三轮实操验证

---

## 一、这份SKILL的定位

**你的任务（Step 2）**：
读取第一层MD（四标签+规则空白地图），产出一份**沟通版MD草稿**，让没有数据背景的业务岗位也能读懂分析结论。

**你不需要做的事**：
- ❌ 不需要补充新的分析内容
- ❌ 不需要渲染HTML（那是Step 4的工作）
- ❌ 不需要修改或质疑第一层MD的结论

**你只需要做的事**：
- ✅ 把第一层MD的8类信息，按固定8板块结构重新组织
- ✅ 为每条P0/P1条目写一段「通俗说法」（≤3句话，日常语言）
- ✅ 产出一份完整的MD文件，交给Jasper审阅

## 二、输入材料识别

执行Step 2前，先识别输入材料中的以下信息：

| 需要识别的项 | 在第一层MD的位置 | 用于哪个板块 |
|---|---|---|
| 规则空白总数+P0/P1/P2分布 | 执行声明 / 汇总统计 | 板块1 |
| 所有分析表的数据链顺序 | 标签卡C标签（在链位置）/ 任务包（数据链分层） | 板块2 |
| C4信号（Owner≠实际维护方）的集中情况 | C4信号清单 / B标签 | 板块3 |
| 全部P0条目（含调研填充状态） | 规则空白地图P0区块 | 板块4 |
| 全部P1条目 | 规则空白地图P1区块 | 板块5 |
| 全部P2条目 | 规则空白地图P2区块 | 板块6 |
| 质检修订记录 | 版本记录 / 修订说明 | 板块7 |
| 访谈岗位+归口条目+问题草稿 | 规则空白地图「访谈岗位」列 | 板块8 |

**集群风险判断规则**（板块3的触发条件）：
```
有集群风险：满足以下任意一条
  条件A：同一岗位归口P0级空白 ≥ 2条，且该岗位对应表数 ≥ 3张
  条件B：C4信号（Owner挂名）命中字段数 ≥ 20个，且集中在同一域

无集群风险：不满足上述条件
  → 板块3写：「本次分析未发现集群风险」+ 1句简要说明原因
```

### 执行前判断：分析视角识别（v1.1新增）

在产出MD草稿前，先判断本次使用的分析视角：

| 判断条件 | 分析视角 | 影响板块 |
|---|---|---|
| 输入文件**不含**价值节点清单（无VN-PAY编号） | **表视角**（原有）| 板块1-8按原有格式执行 |
| 输入文件**含**价值节点清单（有VN-PAY编号+Gate状态） | **价值节点视角**（v1.1新增）| 板块1/2/3.5/4/5/6按v1.1新增格式执行 |

**判断依据**：
- 第一层MD执行声明中写明「分析单元：价值节点视角」→ 价值节点视角
- 规则空白地图含「关联价值节点」列（VN-PAY-XX）→ 价值节点视角
- 其他情况 → 表视角（原有格式）

### 板块1：执行摘要

**内容**：固定表格，从第一层MD执行声明/汇总统计中取数。

**格式**：
```markdown
## 板块1：执行摘要

| 指标 | 数量 | 通俗说明 |
|---|---|---|
| 规则空白总数 | **[X]条** | 发现的、没有写成文档的判断规则 |
| P0 · 立即处理 | **[X]条** | 现在就可能出问题，或出了问题无法追责 |
| P1 · 尽快补全 | **[X]条**[如有升级备注加括注] | 规则存在于脑子里，依赖个人经验，没有写下来 |
| P2 · 可计划推进 | **[X]条** | 目前正常运作，遇到边界情况会有争议 |
| [按需增行] | [数值] | [通俗说明] |
```

**按需增行规则**（根据域的特性选择性增加）：
- 有调研记录（情景3）→ 增加「P0已调研确认」行
- 有C1-C5全量扫描报告 → 增加「高风险字段信号」行
- 有待实施表 → 增加「已实施/待实施」行
- 有待确认问题（Q-V类） → 增加「待确认问题」行
- 有反向建表 → 增加「字段清单待补全」行
- 价值节点视角时 → 必须增加「价值节点Gate状态一览」行，格式如下（固定，不可省略）：

| 指标 | 数量 | 通俗说明 |
|---|---|---|
| 通过节点（🟢+🟡）| X个 | 已进入规则分析，本报告覆盖范围 |
| 熔断节点（🔴）| X个 | 当前无法进入规则分析，需优先补建 |
| P0规范化节点（🟡） | X个 | 通过但有改善项，规则空白地图已标注 |

### 板块2：数据链全景

**内容**：用文字+缩进代码块，展示数据链的分层顺序和每张表的通俗一句话。

**格式模板**：
````markdown
## 板块2：数据链全景

[1-2句总括，说明数据从哪里来、经过什么、到哪里去]

```
【段/层名称1】← [维护方/职责]
  表名（英文）← [通俗一句话：这张表是干什么的]
  表名（英文）← [通俗一句话]
  ↓ [连接说明，如：脚本处理/手工填写/自动聚合]
【段/层名称2】
  ...
```
````

**通俗一句话的写法规则**：
- 说「这张表存的是什么」+「谁来维护」+「如果这张表出问题会怎样」
- ❌ 错误：「聚合层核心事实表，按组织维度汇聚薪资和人员数据」
- ✅ 正确：「财务部门看人工成本的"总账"，含用户决策字段，每次口径可能不同」

**P级标注规则**：在表名行末尾加标注
- `← ★P0：[1句风险描述]`
- `← ★P1：[1句风险描述]`
- 无风险或P2：可不标注，保持简洁

**如有领域特有规则**（如v2.2明确的4条业务规则），在板块2末尾单独列表：
```markdown
**[本域]已明确的[N]条业务规则**：

| 规则 | 通俗说法 |
|---|---|
| [规则名] | [1-2句白话描述] |
```

**价值节点视角时的格式（v1.1新增）**：

当使用价值节点视角时，板块2从「数据表链路」改为「价值节点×数据表」双层结构：

````markdown
[1-2句总括，说明数据从哪里来、经过什么节点、到哪里去]

**[本次分析覆盖的X个价值节点]**

【VN-PAY-XX · 节点名称】[🟡P0规范化 / 🟢通过]
  Gate状态：Gate①挂数=[状态] Gate②落地=[状态] Gate③追溯=[状态]
  起点A：[输入]　终点Z：[输出]
  生产方：[姓名]　消费方：[下游]　频次：[月×N]
  涉及数据表：[表名1（通俗一句话）] / [表名2（通俗一句话）]
  ★本节点规则空白：[P0-XXX/P1-XXX，一句话描述核心缺口]

【VN-PAY-XX · 节点名称】...
（重复上述格式）

**待补建链路（X个熔断节点）**（详见板块3.5）
[用1句话点出熔断节点的核心意义，引导读者去板块3.5]
````

**V3.0已明确业务规则表格**（有价值节点清单时必须保留）：
保留原有「已明确的N条业务规则」表格，格式不变。

**P级标注规则（价值节点视角时）**：
- 节点行末标注：[🟡P0规范化] 或 [🟢通过]，不再标★P0/★P1
- 涉及数据表行保留 ← ★P0/★P1 的标注方式

### 板块3.5：熔断节点·优先补建清单（价值节点视角时必须存在，v1.1新增）

**触发条件**：使用价值节点视角，且有≥1个熔断节点（🔴）。

**定位**：比P0更高的优先级——熔断节点是连规则分析都进不去的环节，必须先完成补建，才能进入三层递进。

**在MD中的位置**：紧接板块3集群风险之后，P0之前（读者顺序：集群风险 → 熔断节点补建 → P0 → P1 → P2）。

**格式**：

````markdown
## 板块3.5：熔断节点·优先补建清单（X个，比P0更紧迫）

> 以下X个环节在三重Gate验证中失败，当前没有足够的物理交付物或数据支撑，无法进入规则分析。需要[裁定责任人]联合裁定补建路径后，才能进入后续的规则提取和SOP制定。

| 节点ID | 价值节点 | 当前核心缺口（一句话） | 熔断原因 | 裁定责任人 |
|---|---|---|---|---|
| VN-PAY-XX | [节点名] | [缺口描述] | [Gate失败类型] | [责任人] |

**通俗说法**：[≤3句话，用日常比喻说明为什么这些节点连分析都进不去]

**下一步**：[裁定责任人]需在[时间]前完成裁定，确认补建路径后通知Jasper，方可将这些节点纳入规则分析范围。
````

**无熔断节点时**：
写「本次分析无熔断节点，全部价值节点均已通过Gate验证，直接进入规则空白分析。」

## 四、通俗说法写作规则（核心，5条）

### 规则1 · 比喻锚定
必须用受访者日常能接触到的场景类比，不用IT术语做比喻：
- ✅ 账本、开关、价目表、地图、控制面板、流水线、总账、操作工
- ❌ 数据库、ETL管道、API接口、配置文件、聚合层

### 规则2 · 风险后果前置
格式：「如果[具体操作/情况]，会[发生什么后果]」
- ✅「如果费率被改错，后续所有应收应派金额都会出错」
- ❌「费率表存在双人维护无审批的风险，建议引入复核机制」

### 规则3 · 字段名保留但降权
字段名放括号或灰色表达，不作主句主语：
- ✅「账单的14种状态（包括hold/不派/已转户等），判断标准全在蔡依娜脑子里」
- ❌「account_status字段的14种枚举值的状态转换逻辑依赖人工判断」

### 规则4 · 长度限制
每条通俗说法 ≤ 3句话，每句 ≤ 30字。

### 规则5 · ✅已确认空白用确定语气
调研已锚定的空白不用「可能」「也许」，用已发生事实描述：
- ✅「访谈已确认：支票操作流程中没有独立的金额核对步骤」
- ❌「可能存在支票操作无复核的情况」

## 五、跨域适配说明

本SKILL为通用模板，以下内容须按领域适配，其余保持原样：

| 适配项 | 说明 |
|---|---|
| 导言「不是看数据X」 | 替换X为该域的业务语言：佣金域用「对不对」，HR域用「准不准」，财务域用「算得对不对」 |
| 数据链描述 | 完全按该域的数据链重写，不套用其他域的语言 |
| 集群风险主体 | 按实际归口岗位命名，不强制「MOMO集群」「蔡依娜SPOF」等具体人名风格 |
| 通俗比喻选材 | 贴近该域受访者的日常用语：财务域用「账本/打款/开支票」，HR域用「考勤/档案/工资单」，佣金域用「价目表/路由/出单」 |
| 访谈岗位 | 按实际归口分配，不强制特定数量 |
| SPOF关联说明 | 仅在发现集群风险时引用Masaki离职教训（mp_086），不强制出现 |

## 六、常见错误与修正（来自三域实操）

| 错误类型 | 错误示例 | 正确做法 |
|---|---|---|
| 通俗说法过长 | 写了5句话详细解释C2信号的定义和风险含义 | 压缩到3句，聚焦「现在是什么情况」+「出了问题会怎样」 |
| 技术术语未降权 | 「C4信号命中字段导致Owner与维护方不一致」 | 「这张表上签了名字的负责人，实际上不是在维护这张表的那个人」 |

| 集群风险无通俗比喻 | 只列了「三权合一×5张配置表」的技术描述 | 必须加一段「通俗比喻」，用流水线/控制面板等比喻说明后果 |
