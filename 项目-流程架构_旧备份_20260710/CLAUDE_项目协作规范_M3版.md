## 一、项目本质（必读）

**这不是一个普通的文档整理项目**。这是：

## 二、商业模式（必读）

**本公司 = 保险行业MGA平台** (S2B2A模型)
- **S** = 平台/中台(本公司) — MGA授权+牌照+运营能力
- **B** = TOB机构(经代/家办) + KA/TOA(个人IP)
- **A** = 理财师/代理人
- **C** = 终端客户

**MGA核心价值 (Mark明确)**:
> MGA不是渠道合作，是"替保司运营半个业务"。我们从保司获取分销/定价/创新权，整合保司资源，并通过营销/销售/场外支持/一线培训全面赋能保司。

## 三、核心方法论（强制遵守）

### 3.1 价值流 vs 价值链 vs 业务能力

**权威依据**: TOGAF / BIZBOK / Porter (详见 `01_方法论与标准/价值流与价值链方法论纠偏.md`)

| 概念 | 数量 | 视角 | 本项目对应 |
|------|------|------|-----------|
| **价值链** | 企业唯一1条 | 内部(我们怎么运作) | L1飞轮模型(L1-01~05) |
| **价值流** | 多条 | 外部(利益相关者怎么获得价值) | 5条VS (VS-1~VS-5) |
| **业务能力** | 多个 | 能力抽象 | L2(18个) |
| **业务流程** | 多个 | 跨部门执行 | L3端到端流程 |
| **横切能力** | 多个 | 跨VS的中台能力 | L1-05权益中台能力层 |

### 3.2 强制禁用术语 (M1后锁定)

❌ **禁用**:
- "价值体系"(BIZBOK无此概念,是旧框架伪构件)
- "MORM/SMPS/MDF/PACE/CESV"(原5大价值体系,已废弃)
- "价值流"作为18条"洞察市场需求/展示资源解决方案"这类命名(那是价值阶段,不是价值流)
- 把SMPS/MDF当作价值流(它们的利益相关者是内部团队,违反外部性)
- 把权益称为"客户权益"(权益是横切能力,机构/理财师/客户三套独立产品线)

✅ **使用**:
- VS-1~VS-5 + L1-05权益中台
- "终端客户服务旅程"(原错误:"客户权益服务旅程")

### 3.3 四条强制检验规则

任何涉及"价值流"的工作都必须通过以下检验:

**检验1: 外部性 (Stakeholder Externality)**
- 利益相关者必须是企业外部角色(客户/合作伙伴/供应商)
- 如果触发者是"中台""支撑组织""业务部门"→ 不是价值流,是内部能力

**检验2: 端到端完整性**
- 有独立进入条件 + 独立退出条件
- 能独立交付完整价值,不是其他流程的中间片段

**检验3: 价值链唯一性**
- 企业只能有1条价值链(L1飞轮)
- 出现多条"价值链"时,它们实际是价值链的不同活动,应合并

**检验4: 层级命名**
- 价值流 → 价值阶段(Stage) → 价值活动(Activity)
- 任何命名要对照 `价值流与价值链方法论纠偏.md` 的层级表

## 四、协作规则 (M1复盘提炼)

### 4.1 Mark的决策模式

1. **批量park** — Mark明确说"所有判断留在里程碑后统一确认",不要每件事都问
2. **里程碑一次性勾选** — 到里程碑结束时才生成确认书,一次勾完20项
3. **裁定项必须用5块结构**: 【背景】【选项】【推荐】【理由】【风险提示】
4. **推荐必须明确**,并用粗体标注方案字母(如 **B(推荐)**)
5. **简单的确认项可批量呈现**,复杂的判断项逐条展示

### 4.2 AI的工作原则

1. **Spec先于实现** — 先写方法论/规范,再写分析,最后写实现
2. **权威外部校验** — 架构性工作前必须搜TOGAF/BIZBOK/Porter做校验
3. **不要猜业务** — 业务本质只能Mark讲,AI不能凭文档猜
4. **裁定是挖掘** — 最好的裁定不是选A还是B,是Mark讲出一句话让A/B都失效
5. **V0产出必须标注源数据+待评审对象** — 避免AI凭空编造的嫌疑
6. **每一次validate_kb.py必须8/8 PASS** — 任何重大变更后立即跑

### 4.3 裁定中的关键行为

**在裁定看起来简单的问题时,主动问"这个结构有没有漏掉什么"**

历史证据:
- D-04权益L3别名问题 → Mark澄清权益是横切能力(三套独立产品线)
- E-06 VS-1 5条L3认可 → Mark澄清MGA本质是"替保司运营半个业务"

这两次都是裁定时看似简单的问题,触发了结构性洞察。要保持这种开放性。

## 五、强制性项目规则

### 5.0 L4唯一物理交付物原则 (M2 G3-5a生效)
**任何L4切分必须挂一个唯一的物理价值交付物** (single physical deliverable)

- 一个L4 = 一个交付物 = 一个A责任人 = 一段可独立完成的流程
- 物理交付物: 可被他人接收/审计/引用的具体产物(文档/数据表/系统记录/签字文件/凭证)
- 不是: "完成某动作"、"状态变化"、"服务动作组合"
- 建立L4时必须通过判定checklist 5项
- 权威依据: `01_方法论与标准/价值流与价值链方法论纠偏.md` 规则5

### 5.0.1 L4 Agent化评估原则 (M2 L4评估完成后新增, 2026-04-11)
**每个L4必须评估其Agent化潜力,分4档**:
- **Auto** (可完全agent化,人监督) — M4 P0先建
- **Aug** (agent主导+人审批) — M4 P1同步建
- **Hybrid** (人主导+agent辅助) — M4 P2辅助建
- **Human** (必须人工,agent不介入) — 保留人工

**核心原则**: 
- **L4颗粒度越细越好** — 每个颗粒对应一个agent边界,颗粒越细agent越专精,交付质量越高
- **反对human-centric思维** — 不要用"人力管不过来"限制L4数量
- **L4爆炸不是问题,是AI组织化的基础设施**

**强制要求**:
- 任何新L4必须填 `agentifiability` 字段(auto/aug/hybrid/human)
- L3-definition-schema.yaml 已纳入
- 建议M4启动前对每个L4做6维度严谨打分
- 权威依据: 
  - `00_治理与元模型/L4-Agent化评估框架.md`
  - `00_治理与元模型/L4-Agent化清单.csv`
  - `00_治理与元模型/L4-Agent化评估报告.md`

**Mark战略愿景**:
- 未来工作模式 = 肉身 + N个专精Agent
- 人效400→800万 = 每人管理的agent数量 从 1:0 → 1:10~20
- M3组织重组不再基于L4数量,而是基于"核心肉身介入点"(~88条)

### 5.1 里程碑自动复盘 (每里程碑后必须执行)

**触发时机**: 任何里程碑完成后的下一次会话或当次会话结束前

8. 复盘动作闭环

### 5.2 M3组织设计原则 (M3复盘提炼, 2026-04-13)

**原则1: 组织颗粒度 = 介入点, 不是L4数量**
- 126个核心介入点(EP)决定组织结构, 不是300+ L4
- 每个EP = 需要肉身判断/签字/谈判/审批的最小工作单元

**原则2: 岗位本质匹配 (LE-M3-5)**
- 执行型岗位只能承接: 执行/分析/谈判/评估
- 不能承接: 战略设计/创意判断/规则定义
- JD设计前先确认岗位本质(执行/战略/专业), 再分配EP

**原则3: 减负清单滚动校准**
- 减负清单不是一次性锁定, 每份JD完成后强制回溯
- V0→V0.2→V0.3: 每次岗位设计都会暴露新的保留项

**原则4: 防火墙比授权更重要**
- 授权容易, 防止权力漂移难
- 5个组织创新符号: 战略双线/KPI防火墙/双向考核/虚拟委员会/M4预留横切层
- KPI防火墙3条: 内容100%非业务 / 考核权三方联签 / 红线事件保护

**原则5: 阶段可并行**
- P4.1基础设施与P3组织定型并行启动 (D-M3-025)
- 每阶段启动时评估"哪些下阶段任务零依赖可提前"
