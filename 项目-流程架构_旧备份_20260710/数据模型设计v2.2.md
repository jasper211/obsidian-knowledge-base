## 一、本版核心修订

### 修订 1：业务类型字段的明确定义

**之前的疑问**：为什么 J001036（天领贴牌）在代理人 sheet、U000910（合伙转介）在事业部？

**明确答案**：
- **代理人业务** = 业务细分 ∈ {天领业务、永领致远、成事家办} → 3 类，**特征是有人员关系费用**
- **事业部** = 其他所有业务细分（永明经代、BK业务、同行经代、合伙转介业务、ICLUB业务）→ 5 类，**"事业部" 只是结算人员自定义的命名**，没有业务含义

**模型字段设计**：
```
fact_settlement_referral.业务类型 ∈ {'代理人', '事业部'}
  ↓ 派生规则
IF 业务细分 IN ('天领业务', '永领致远', '成事家办') → 代理人
ELSE → 事业部
```

这是个**派生字段**，不是独立维护的——可以从"业务细分"100% 推断。

### 修订 2：权益激励的档位 + hold 机制

**之前的疑问**：剩余待派HKD 和已派发激励HKD 是怎么动的？

**明确答案**：
- 权益激励按**合同档位**结算，匹配维度：业务细分 + 市场分层 + KEY ACCOUNT + 机构 + 合作伙伴
- 触发档位的两个条件：
  - **折标保费（美金）**：达到门槛
  - **累积使用服务价值**：达到一定阈值
- **当服务价值不够时 → hold 住激励金**，状态变成"待结算"或"部分结算"
- **每半月从权益部门更新服务价值** → 自动重算可派发金额
- 派发后：已派发激励 += 本次派发，剩余待派 -= 本次派发

**示例数据**（来自权益计算表）：
| 合作伙伴 | 累积服务价值 | 激励TOTAL | 状态 | 备注 |
|---------|------------|----------|------|------|
| 刘梦妮 | 62,946 | 28,080 | 待结算 | 无协议（hold）|
| 张艳忠 | 108,930 | 0.00 | 部分结算 | 服务价值不够 |
| 廖小凤 | 14,687 | 13,104.01 | 已结算 | - |

**模型设计变更**：
- 新增独立的 `fact_equity_hold_status` 表跟踪 hold 历史（不仅是续保有 hold，权益激励也有）
- `dim_equity_rule` 不只是字典，是**带状态的工作流表**：业务细分+市场分层+...→ 激励档位 + 当前状态

### 修订 3：V1 → V3 的收款人合并规则

**之前的疑问**：J001276 里 V1 的"一代育成=白博文 + 推荐人2=吴竞"在 V3 里合并成"雨泽家族办公室"，规则是什么？

**明确答案**：
- **默认规则**：按人名合并——同一人在多个字段里出现，V3 合并为一行
- **特殊规则（业务约定）**：**吴竞 → 归入白博文**，两人共用同一收款方（雨泽家族办公室）

**数据印证**：V1 里 32 个订单都是这个模式（一代育成=白博文 + 推荐人2=吴竞），全部按这规则处理。

**模型设计变更**：
- 新增 `dim_payee_mapping` 表：人员姓名 → 实际收款方（含特殊约定）
- V1 → V3 转换时的 SQL 伪代码：
```sql
-- 默认按人名分组
SELECT 订单编号, 人名, SUM(金额) FROM (按字段炸开后) GROUP BY 订单编号, 人名

-- 特殊约定先重映射：吴竞 → 白博文
-- 再按"实际收款方"映射
JOIN dim_payee_mapping ON 人名 = dim.人员姓名
GROUP BY 订单编号, dim.实际收款方
```

### 修订 4：德约的多层分润机制

**之前的疑问**：续保表里"德约佣金率/德约应派/机构应派/机构剩余/德约剩余"等字段的关系？

**明确答案 + 数据验证**：

德约的拆分结构（**全部应派=德约应派**，再拆两笔支付）：

```
实收金额（如 J000062 = 3,120 HKD）
    ↓
牌照端先付给德约总部：
  德约应派 = 实收 × 德约佣金率
         = 3,120 × 3.4% = 2,652 HKD ← 这就是"全部应派"
  总部利润 = 实收 - 德约应派 = 468 HKD（牌照公司留存）
    ↓
德约总部收到 2,652 后，拆 2 笔支付：
  1) 理财师应派 = 实收 × 理财师费率
              = 3,120 × 2% = 1,560 HKD
  2) 德约剩余 = 德约应派 - 理财师应派
            = 2,652 - 1,560 = 1,092 HKD（德约总部留存）
```

**还有第三层（机构线）的并存机制**：
```
机构应派 = 实收 × 机构佣金率
       = 3,120 × 3.06% = 2,386.80 HKD
机构剩余 = 机构应派 - 理财师应派
       = 2,386.80 - 1,560 = 826.80 HKD（机构留存）
```

**对模型的含义**：
- 这是续保表里特有的"多层分润"，是德约业务的**专属结构**
- 在 V3 应派单层面，**德约一个订单可能拆出 2 行**：理财师应派 + 德约剩余
- 数据上字段已经全（德约应派/德约剩余/机构应派/机构剩余/牌照端实派总数/总部利润），不需要新增字段
- 153 条续保都涉及德约相关字段

**模型设计变更**：
- `fact_settlement_renewal` 的字段需要增加这套"多层分润"结构
- V3 应派单的"支付类别"需要识别"德约剩余"作为独立类别

### 2.3 关键关系：V1 → V3 收款人合并

```sql
-- Step 1: 从 V1 宽表炸开，每一行变成多行（每个有人名+金额的字段一行）
WITH unpivoted AS (
  SELECT 订单编号, '推荐费' AS 类别, 推荐人员 AS 人名, 推荐费HKD AS 金额 FROM v1 WHERE 推荐人员 IS NOT NULL
  UNION ALL
  SELECT 订单编号, '一代育成', 一代育成人员, 一代育成应派HKD FROM v1 WHERE 一代育成人员 IS NOT NULL
  UNION ALL
  SELECT 订单编号, '所辖费用', 所辖人员, 所辖津贴HKD FROM v1 WHERE 所辖人员 IS NOT NULL
  -- ... 其他人员关系字段
)
-- Step 2: 应用特殊约定（如吴竞→白博文）
, remapped AS (
  SELECT u.订单编号, u.类别, COALESCE(d.合并到人名, u.人名) AS 实际人名, u.金额
  FROM unpivoted u
  LEFT JOIN dim_payee_mapping d ON u.人名 = d.原人名
)
-- Step 3: 按"实际人名" merge，输出 V3
SELECT 订单编号, 类别, 实际人名, SUM(金额) AS 本期费用
FROM remapped
GROUP BY 订单编号, 类别, 实际人名

-- Step 4: 通过 dim_payee_mapping 再映射到"最终收款方"（如白博文 → 雨泽家族办公室）
```

### 2.4 关键关系：德约多层分润

```python
# fact_settlement_renewal 在德约业务上有 6 层数值
实收佣金HKD = 3120
   ↓
德约应派HKD = 实收 × 德约佣金率 = 2652   # 牌照端付给德约总部
总部利润HKD = 实收 - 德约应派 = 468     # 牌照公司留存
   ↓
理财师应派HKD = 实收 × 理财师费率 = 1560  # 德约总部付给理财师
德约剩余HKD = 德约应派 - 理财师应派 = 1092  # 德约总部留存

# 并行的"机构线"
机构应派HKD = 实收 × 机构佣金率 = 2386.80
机构剩余HKD = 机构应派 - 理财师应派 = 826.80

# V3 应派单上德约订单会拆成 2 行
# 行1: 支付类别='转介费'(理财师), 本期费用=1560, 收款人=理财师
# 行2: 支付类别='德约剩余', 本期费用=1092, 收款人=德约总部
```
