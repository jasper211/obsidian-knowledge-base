## 第二结论：EA源项目现行真相更像“交付对象组”，不是“原子碎片组”

从源项目本体看，当前更稳定的知识单元并不总是单个原子概念，而更常是：

1. `交付批次`
2. `权威数据组`
3. `治理规范文件`
4. `D1-D4成套交付`
5. `现行关系表 / crosswalk / dictionary`

例如：

- `交付清单.md` 记录的是交付批次、现行版本、归档关系、接受状态
- `权威数据/` 记录的是当前版 D1 / D2 / D3 / dim / registry / crosswalk
- `治理规范/` 记录的是标准、规则、审计、映射逻辑、裁定口径

这说明：

- EA 当前现行知识的稳定载体，很多已经是“文件级对象”或“成套交付对象”
- 而 vault 旧提炼更像“把内容切成很多细原子”

两者的抽取单位不一致

## 第三结论：vault里的EA旧提炼不能再直接默认是现行真相

原因至少有 3 个：

### 1. 版本明显滞后

源项目里当前可见的现行对象已经推进到：

- `D1_价值节点清单_V3.62`
- `D2_价值节点_L3映射表_V2.19`
- `D3_L3调整记录_V1.28`
- `dim_kpi_v3.4`
- `能力问题全集_v2.7`
- `流程库状态监控表_L3成熟度跟踪_V3.18`

而 vault 中大量 EA 原子来自更早阶段的内容提炼。

### 2. 源项目有明确的“现行 / 归档 / 待接受 / 待重验”状态机

比如：

- `交付清单.md` 会写清楚批次、当前版、归档版、`PUBLISHED-PENDING-MARK-ACCEPTANCE`、`BUSINESS-FACT-ACCEPTED` 等状态
- `L3_L4完整性审计报告.md` 里出现 `legacy_published_pending_revalidation`

这说明 EA 本体已经有显式发布状态。

而 vault 旧提炼层大多没有把这种“现行状态机”完整带进来。

### 3. 源项目里已有严格的可见性与验收规则

例如：

- `OB-GATE Obsidian持续更新与验收可见性规则 v1.0`

它强调：

- Mark 验收看的是真正进入 EA Vault 且可检索的现行内容
- 索引、门检、探针、回执、最终状态都要可追溯

这说明 EA 本体的治理已经明显进化，不再只是“内容提炼”问题。

## 第四结论：旧提炼的问题不只可能是过期，也可能是结构不再匹配

这点很关键。

本轮盘点后，旧提炼潜在问题至少分两类：

### A类：内容老了

表现：

- 引用的版本旧
- 规则已被新文件替代
- 现行关系表已经更新

这类问题的处理是：

- 更新来源
- 切换主引用
- 把旧内容退役

### B类：抽法本身不再适配现行结构

表现：

- 旧提炼过度按“原子碎片”切分
- 但源项目现行口径是“交付批次 + 权威数据组 + 治理规范 + 状态机”
- 旧提炼很难表达“哪个版本现行、哪个已归档、哪个待验收、哪个需重验”

这类问题的处理不是简单更新，而可能需要：

- 重做提炼单位
- 重做专题挂接方式
- 重做“现行对象 -> 原子解释”的关系结构

---

## 当前判断：EA旧提炼至少要分 4 类处置

### 1. 可直接保留

条件：

- 仍是稳定概念
- 不强依赖具体版本
- 仍适合作为长期知识原子

例如：

- 某些概念定义
- 某些治理原则
- 某些跨项目可复用的判断方式

### 2. 需要换源校准

条件：

- 主题仍成立
- 但现行依据已经换成源项目新版文件

例如：

- Gate
- 熔断
- 审计
- Crosswalk
- KPI / D1 / D2 / D3 相关对象

### 3. 需要改结构重提

条件：

- 旧页按原子切法写成
- 但现行更适合按“交付对象组”组织

例如：

- D1-D4 套件
- 权威数据组
- 交付批次
- 现行关系表组

### 4. 需要退役或降级

条件：

- 已无现行价值
- 与现行结构冲突
- 只是早期过程痕迹

---

## 对 EA 后续推进逻辑的直接修正

从这一轮开始，EA 推进逻辑要改成：

1. 先看 EA 源项目本体
2. 识别现行交付对象、权威数据组、治理规范组
3. 再反查 vault 里已有旧提炼
4. 对旧提炼做：
   - 保留
   - 换源
   - 重提
   - 退役

也就是说：

- EA 不再是“继续在 vault 内补结构”
- 而是“以源项目现行为准，对 vault 进行校准重构”
