# RW知识域到底座挂接导航 MOC

## 一句话定义

这页把 `RW知识域` 如何挂到公司级治理底座上，整理成一张可浏览、可回跳、可给 agent 调用的导航页。

它回答的是：

- 六张公司级底座卡在 RW 里分别优先对应什么问题
- 想看 RW 的主链、验收、交接、判断、状态、异常治理时，应先调哪张底座卡
- 后续 RW 接入 OB 时，agent 应如何从底座回落到 RW 业务真相

---

## RW 挂接公司级底座的总图

先把 RW 当前的挂接关系压缩成一句话：

`先用公司级底座扫清权益交付的治理骨架，再回到 RW 找交付、验收、例外与履约真相。`

对应关系可以先理解成两层：

### P0：结构治理挂接

- `公司级通用流程与验证标准` -> `RW 主链 / 验收 / 通过标准`
- `公司级Owner与边界规则` -> `RW 角色职责 / 收口责任 / 升级责任`
- `公司级交接与共享对象原则` -> `RW 交付对象 / 验收对象 / 共享主档案`

### P1：高阶治理挂接

- `公司级判断决策闭环` -> `RW 例外履约 / 升级裁定 / 豁免补偿判断`
- `公司级状态一致性与Crosswalk校验` -> `RW 验收状态 / 履约状态 / 正式确认状态`
- `公司级SOP质量与异常暴露机制` -> `RW 异常履约 / 交付偏差 / 服务异常暴露`

### 这组挂接主要回答什么

- 权益业务主链是否已经明确
- 哪些节点算完成
- 验收证据应该是什么

### 适合 agent 的默认调用方式

当问题更像：

- “这项权益服务算交付完成了吗”
- “验收到底靠什么确认”
- “这一步缺的是动作还是通过标准”

优先先调 `公司级通用流程与验证标准`，再回落到 `RW知识域定义` 和后续 RW 主链材料。

- “同一个客户权益对象是不是被拆散了”
- “服务确认对象和交付对象是不是同一份”

### 这组挂接主要回答什么

### 适合 agent 的默认调用方式

- “这笔权益到底是 pending 还是 done”
- “为什么内部说完成了，客户侧还没确认”
- “方案版本能不能直接当正式履约依据”

优先先调 `公司级状态一致性与Crosswalk校验`，再回落到 RW 的交付与验收状态。

### 这组挂接主要回答什么

### 适合 agent 的默认调用方式

当问题更像：

- “为什么每次到客户投诉才发现”
- “异常履约有没有标准暴露机制”
- “RW 的 SOP 是不是只能保证表面不出错”

优先先调 `公司级SOP质量与异常暴露机制`，再回落到 RW 的异常与例外问题。

## 一个最简单的调用顺序

后续不管是人还是 agent，处理 RW 问题时，都可以优先按这套顺序走：

1. 先判断问题属于流程、边界、交接、判断、状态还是异常治理
2. 先调用对应的公司级底座卡
3. 再回落到 RW 知识域和后续 RW 主链材料
4. 最后再下钻到 RW 的结果性文件或原子
