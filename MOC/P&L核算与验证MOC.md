# P&L核算与验证 MOC

## 一句话定义

这页负责把 `P&L知识域` 里的核算、验证、复核类知识收成一个专题入口，重点回答：

- P&L 的结果为什么成立
- 核算过程靠什么验证
- 哪些节点必须人工复核、审批确认或版本校验

它的作用，是让后续 OBagent 在处理 P&L 报表、分析、复盘时，不只是拿到结果，而是能追到结果成立的验证链。

---

## 为什么这页重要

如果只有口径定义，没有核算与验证链，P&L 仍然会停留在“解释型知识”，还不足以支撑正式决策。

核算与验证这一层真正解决的是：

- 结果是否可信
- 过程是否可复核
- 异常是否会被拦截
- 正式版本是否真的通过了确认

所以这页的重点不是再讲一次计算，而是讲：

- 哪些结果靠系统验证
- 哪些结果靠人工复核
- 哪些结果靠审批、确认或对账成立

---

## P&L 核算与验证的骨架

当前建议先把这条链分成 4 组来看。

### 1. 核算规则

关注：

- 指标如何计算
- 输入数据来自哪里
- 计算过程中有哪些关键判断点

后续建议沉淀的正式对象：

- `核算逻辑`
- `计算规则`
- `输入前置条件`

### 2. 验证标准

关注：

- 一份结果靠什么证明成立
- 哪些校验是必须项
- 哪些结果只有在满足特定证据后才算正式

后续建议沉淀的正式对象：

- `验证标准`
- `通过标准`
- `证据要求`

### 3. 复核与审批

关注：

- 哪些结果必须人工复核
- 复核失败由谁接
- 哪些节点必须审批通过才可进入正式版本

后续建议沉淀的正式对象：

- `复核链`
- `审批链`
- `失败升级机制`

### 4. 状态与版本校验

关注：

- 草稿版、分析版、审批版、正式版是否被清楚区分
- 同一结果在不同系统或文档中的状态是否一致
- 哪一版可用于正式经营判断

后续建议沉淀的正式对象：

- `状态定义`
- `版本边界`
- `正式发布条件`

---

## P&L 验证最常见的四类缺口

### 1. 有结果、无证据

报表或分析已经出来，但缺少明确验证依据。

### 2. 有计算、无复核

结果算得出来，但没有足够的人工复核或职责确认。

### 3. 有复核、无唯一正式版

多个版本都被讨论过，但没有唯一可引用的正式结果。

### 4. 有异常、无拦截闭环

偏差、超预算、复核失败被发现了，但没有稳定升级路径和回写机制。

## 这页主要回答什么

后续这页应该能稳定回答下面几类问题：

- “这份经营分析为什么能被采信”
- “利润结果到底靠什么验证”
- “这一步必须人工复核吗”
- “这版报表已经正式了吗”
- “复核失败或数据偏差时应该走哪条升级路径”

### 这组候选包当前已经能回答什么

基于这三份材料，当前已经可以先看到一条比较完整的“验证链骨架”：

- 勾稽主链：`Statement -> 收款 -> 凭证 -> 分月收入`
- 成本与分成链：`IF转介费 -> 京东卡权益 -> 爱保分成 -> Marketing Fee例外`
- 证据组织方式：真实证据应进入唯一物理路径，不在清单页重复存放
- 核验留痕方式：文件路径、核验状态、缺口说明需要进入证据登记表

也就是说，这组材料已经不只是“我们大概要验证什么”，而是已经开始说明：

- 该验证哪些对象
- 这些对象之间如何穿行
- 哪些证据还缺
- 缺口由谁补

### 为什么当前只挂候选层，不晋升主库

这组材料当前仍不宜直接作为 P&L 主库级验证规则，原因很明确：

- `收入成本勾稽穿行工作底稿` 仍是 `v0.1 框架，待证据填充`
- `财务证据目录与待补清单` 仍有 E1-E16 大量材料处于 `待归档 / 待完成`
- `证据文件登记表` 当前还是模板化起始登记状态，尚未形成真实核验结果

因此它们虽然很有价值，但目前代表的是：

- `验证链施工面`

而不是：

- `验证链正式规则真相`

### 当前候选层的最小稳定结论

这组候选包当前至少可以稳定支持以下判断：

1. P&L 的验证不能只看结果数值，必须追到原始证据链
2. 收入验证至少要走 `Statement -> 收款 -> 凭证 -> 分月收入`
3. 成本与分成验证至少要覆盖直接成本、分成规则与例外项
4. 未核验的文件不能被标记为 `已验证`
5. 证据必须有唯一物理路径，不能因为分析需要复制成多份“正式版本”

### 当前距离主库晋升还差什么

这组材料后续如果要从候选层晋升到主库，至少还需要满足：

- 出现至少一组真实季度可复算样例
- 关键证据从 `待归档` 变成 `已收到 / 已核验`
- 差异解释和通过条件被写成稳定规则，而不是过程补件说明
- 能明确回答“什么情况下这份结果算验证通过”

当前最适合的用法是：

1. 作为 P&L 第一批核算与验证类白名单材料的收口入口
2. 先调用已挂接的验证链候选包，判断当前缺的到底是证据、规则还是核验状态
3. 作为未来 `验证标准 / 复核链 / 审批链 / 状态校验` 等正式卡片的继续挂载页
4. 作为 agent 判断“这份结果为什么成立、是否正式”的第一跳入口

当后续 P&L 正式材料逐步补入后，这页就会从“专题框架”升级为“正式验证导航页”。
