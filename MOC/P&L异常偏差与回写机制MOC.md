# P&L异常偏差与回写机制 MOC

## 一句话定义

这页负责把 `P&L知识域` 里的异常暴露、偏差上报、升级路径、修复动作与规则回写类知识收成一个专题入口，重点回答：

- P&L 的异常和偏差如何被及时看见
- 看见以后由谁上报、谁升级、谁收口
- 处理完后如何真正回写到口径、验证、责任、状态和复盘规则里

它的作用，是让后续 OBagent 在处理 P&L 问题时，不只看到“出了问题”，还能够继续追到“有没有暴露、有没有升级、有没有回写成下一轮默认机制”。

---

## 为什么这页重要

如果没有这张页，前面已经补起来的 5 条主线仍然会停在“结构完整”，但还不是真正闭环。

因为真实的 P&L 运行里，一定会发生：

- 超预算
- 数据偏差
- 复核失败
- 版本误用
- 口径漂移
- 结论迟迟没有进入正式规则

真正决定知识库是否有治理价值的，不是“有没有异常”，而是：

- 异常能不能被及时看到
- 被看到后能不能稳定进入上报和升级
- 处理完后能不能反哺前面的所有主线

所以这页的重点，是把 `异常暴露 -> 升级处理 -> 修复动作 -> 规则回写` 串成闭环终点。

## P&L 异常偏差与回写机制的骨架

当前建议先把这条链分成 4 组来看。

### 1. 异常与偏差定义

关注：

- 什么算异常
- 什么算偏差
- 什么算必须升级的问题
- 什么只是可记录但不必升级的波动

后续建议沉淀的正式对象：

- `异常定义`
- `偏差定义`
- `升级阈值规则`

### 2. 暴露与上报通道

关注：

- 谁来发现问题
- 发现后去哪里报
- 上报时需要什么最低信息
- 是否区分草稿问题、正式问题和高风险问题

后续建议沉淀的正式对象：

- `异常上报格式`
- `偏差暴露通道`
- `最小上报字段`

### 3. 升级与修复动作

关注：

- 异常进来后由谁分流
- 谁负责先止损、再裁定、再补动作
- 哪些异常需要立刻升级，哪些可以进入待跟踪池

后续建议沉淀的正式对象：

- `异常升级链`
- `修复动作模板`
- `待跟踪池规则`

### 4. 回写与复发预防

关注：

- 这次异常最终回写到哪一层
- 是回写到口径、验证、责任、状态还是复盘裁定
- 下次遇到同类异常时，是否已经不需要再临时解释

后续建议沉淀的正式对象：

- `规则回写记录`
- `检查项补建记录`
- `复发预防条件`

## P&L 异常治理最常见的四类风险

### 1. 异常总在结果发布后才被发现

说明前面缺少足够的可见信号和中途暴露机制。

### 2. 异常被发现了，但没人正式上报

说明暴露通道不清，或者上报成本过高。

### 3. 异常处理完只补当前，不补规则

说明修复动作没有进入回写闭环。

### 4. 异常反复发生，但大家都当成“个例”

说明知识库没有把重复偏差上升为正式治理输入。

后续这页应该能稳定回答下面几类问题：

- “这类复核失败有没有标准修复路径”
- “这次异常最后改了哪条规则”
- “下次怎么避免同类异常再重复”

### 这组候选包当前已经能回答什么

基于这组材料，当前已经可以先固定以下异常治理结论：

- `P0` 问题需要在 24 小时内指定 Owner
- 影响 Gate 的事项需要直接升级
- 规则和数据未通过 Gate 时，只允许 `Prototype`，不能当正式管理数字
- 正式结论以会后纪要及签批文件为准
- 交付状态需要按统一状态机更新，不能跳过 `待评审 / 已通过Gate` 直接冒充 `已发布 / 已验收`
- RAID 记录至少要包含：缺什么、影响什么、谁负责、何时补齐、临时怎么处理、升级对象

### 为什么当前只挂候选层

原因是：

- 这些材料目前分散在汇报材料、交付清单和模型卡 RAID 区
- 它们已经很接近异常治理规则，但还没有收敛成单独成文的正式制度
- 当前更像“异常治理结构已经存在”，而不是“异常治理规范已经冻结”

### 当前最合适的用法

当前最适合把它们作为：

1. `Slot-06` 的候选层主材料包
2. Agent 判断“这类问题是否已经进入正式暴露和升级链”的参考入口
3. 后续等待单独异常制度出现后，再评估是否晋升主库
