# 公司级通用流程与验证标准

## 一句话定义

这页把 `EA` 已经成型的流程验证骨架，和 `Jasper AI协同经验引擎` 中关于验证、状态、显式化的治理纪律，抽成一套可被 `RW`、`P&L` 及未来新项目复用的公司级默认标准。

它回答的是：

- 一个流程怎样才算真正完成
- 哪些验证必须内置在流程里
- 哪些节点必须人工复核
- 哪些结果必须由外部证据确认
- 什么情况下不能判定为“已通过”

---

## 为什么要先抽这张卡

目前 OB 最大的问题已经不是“有没有流程材料”，而是不同项目后续进入后，如果没有统一验证语言，就会再次出现：

- 流程动作很多，但完成标准不一致
- 项目内部自证完成，却缺少外部证据
- 草稿、口头同步、临时说明被误当成正式通过
- agent 能串流程，但不能稳定判断“是否真的闭环”

所以这张卡适合作为 `公司级治理底座` 的第一张实用标准卡。

---

## 这张卡的适用边界

适用于：

- 需要定义流程完成标准的项目
- 需要区分自动通过、人工复核、外部验收的场景
- 需要把“完成”变成可核查状态的 agent 设计

不直接覆盖：

- 某个项目特有的业务口径
- 某个节点专属的指标阈值
- 只在单一项目里成立的例外流程

这些内容仍应留在对应项目知识域。

---

## 公司级默认判断

公司级默认判断可以先收敛为 5 条。

### 1. 流程完成不等于动作做过

一个节点只有在 `动作完成 + 验证通过 + 证据可追溯` 时，才应被判定为真正完成。

如果只有动作，没有验证或没有证据，那么它最多只能算：

- 已执行
- 待验证
- 待验收

而不应直接标记为完成。

### 2. 验证应尽量内置在流程里

优先设计成：

- 做这一步时就完成校验
- 产出结果时就生成验证证据
- 交接前就完成通过判断

不要把验证长期留成流程外的补动作，否则最容易变成“流程做完了，但没人知道是否达标”。

### 3. 高风险节点必须有人工复核

凡是涉及以下情况，默认都应有人工复核或指定角色复核：

- 真实资金
- 合规与外发
- 敏感信息
- 授权审批
- 高损失风险动作

这类节点不应只靠自动规则直接放行。

### 4. 对外交付结果必须由外部证据确认

凡是对外生效、对外承诺、对外交付的结果，不能只由内部自证完成。

应优先要求：

- 客户/合作方签署
- 外部系统状态
- 第三方回执
- 正式审批记录
- 可核验的交付物证据

这条来自 Jasper 的核心纪律：`验证须来自外部`。

### 5. 状态必须与成熟度一致

流程状态不是标签问题，而是治理问题。

如果一个对象仍是草稿、待确认、待落库、待复核，就不应在别的系统或文档里被当成：

- 已上线
- 已通过
- 已投产
- 已交付

这条来自 Jasper 的另一条核心纪律：`状态必须对齐`。

## 公司级验证结构

建议把跨项目验证统一理解成 4 层。

### 第一层：流程内置验证

适用场景：

- 边界清晰
- 输入输出清楚
- 可直接通过规则判断

默认要求：

- 验证步骤尽量嵌入流程
- 验证结果能留下记录
- 失败时能明确阻断或转异常路径

### 第二层：人工复核关卡

适用场景：

- 风险高
- 自动判断不可靠
- 需要责任人承担签核

默认要求：

- 复核角色明确
- 复核对象明确
- 复核结论有记录
- 未复核不能直接放行

### 第三层：外部确认型验收

适用场景：

- 对外交付
- 合同/服务/结算生效
- 需要第三方确认结果

默认要求：

- 有独立于执行方的确认来源
- 验收证据可回查
- 无外部确认时只能算“内部完成”，不能算“正式闭环”

### 第四层：成熟度验证

适用场景：

- 不是验证单一步动作
- 而是验证整个节点是否达到可持续运行标准

默认要求：

- 有稳定挂数或系统记录
- 有实际物理/系统产物
- 有审核与追溯链
- 关键失败可触发熔断或补建

这层是从 EA 的 Gate 成熟度体系里抽上来的。

## 默认 Gate 设计原则

跨项目设计 Gate 时，建议至少满足 4 条原则。

### 1. Gate 要对应明确风险

每个 Gate 都应能回答：

- 它防的是什么风险
- 如果不设会怎样
- 通过与失败分别意味着什么

如果 Gate 只是形式存在，就不应保留。

### 2. Gate 要有可观察证据

不能依赖“感觉通过了”或“大家都知道已经完成”。

Gate 必须能指向某种证据，例如：

- 正式源文件
- 系统状态
- 复核记录
- 验收回执
- 可追溯交付物

### 3. Gate 失败后必须有后续动作

Gate 失败不能只停留在“发现问题”。

至少应定义：

- 阻断
- 返工
- 升级
- 补建
- 熔断

否则 Gate 只是报错提示，不是治理机制。

### 4. Gate 条件必须显式化

不要依赖隐含理解。

应尽量显式写出：

- 进入条件
- 通过条件
- 失败条件
- 责任人
- 后续路径

这条来自 Jasper 的 `显式化方法`。

## 默认通过判断模板

后续不管是 EA、RW、P&L 还是新项目，都可以优先用下面这套判断模板：

1. 这一步的目标结果是什么
2. 什么证据能证明结果存在
3. 证据来自内部还是外部
4. 是否需要人工复核
5. 当前状态是否与真实成熟度一致
6. 如果失败，走返工、升级还是熔断

如果这 6 个问题答不清，一个流程节点通常还不适合直接进入 OB 主知识层作为“成熟流程真相”。

---

## 对 agent 设计的直接要求

如果后续要让 OBagent 真正利用这套标准，那么 agent 不应只会抽流程步骤，还应至少能补出：

- 当前节点的验证类型
- 当前节点的通过证据
- 当前节点是否需要人工复核
- 当前节点是否需要外部确认
- 当前节点的状态是否可信
- 当前节点失败后的默认路径

否则 agent 仍然只能做“流程浏览”，不能做“流程治理辅助”。

## 当前仍然保留的边界说明

截至 2026-08-12，这张卡已经可以作为公司级默认标准的第一版，但仍有一个清楚边界：

- 它的流程验证骨架主要来自 EA
- 还需要 RW、P&L 及未来项目继续做印证和修正

也就是说，它已经适合当“默认起点”，但还不是最终定版。
