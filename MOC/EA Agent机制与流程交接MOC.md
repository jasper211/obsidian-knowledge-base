# EA Agent机制与流程交接 MOC

## 一句话定义

这页负责回答 EA 主库里另一条关键执行链：

**谁负责 -> 谁协作 -> 在哪里交接 -> 交接后谁继续持有上下文与责任。**

它的作用，是把前面“规则空白 / 熔断治理”专题进一步接到执行面，避免问题被识别出来以后，仍然卡在边界不清和交接不稳。

---

## 为什么这页重要

当前 EA 主库里，很多问题不是“没有规则”，而是：

- 有规则但没人明确接
- 有交付但没有唯一 owner
- 有 Agent 分工，但交接点没有显式化
- 有协作关系，但上下文对象被拆散

这类问题如果不单独整理，OBagent 后续即使能识别风险，也不容易把风险准确落到执行角色和交接动作上。

---

## 这条执行链怎么理解

建议把这条链拆成 4 个问题：

1. 谁是 owner
2. 谁与谁协作
3. 在哪个节点完成交接
4. 交接后共享什么对象、保留什么责任

当前最重要的判断是：

- 很多交接不是“交完就结束”
- 它们依赖共享档案、共享上下文对象、共享持久化单位
- 如果对象被拆散，后续 Agent 会在不同版本的信息上继续工作

这也是为什么 `共用同一份项目档案`、`共享同一张保司档案表` 这类原子价值很高。

## 从流程角度怎么看这页

如果从流程而不是从 Agent 名字出发，建议重点观察三类信号：

### 1. 是否存在唯一 owner

如果没有唯一 owner，后面即使有交付也容易无人收口。

### 2. 是否存在显式交接点

如果只是“默认下一方会接”，而没有明确进入条件或确认动作，这种交接不稳定。

### 3. 是否存在共享上下文对象

如果前后 Agent 实际上共用同一项目对象、同一档案表、同一持久化对象，却被拆成多份记录，后续会出现上下文漂移。

## 对 OBagent 的直接价值

这页会直接提升三件事：

1. **上下文包质量**：不仅能返回规则，还能返回责任主体和交接对象
2. **风险判断质量**：边界不清、owner 缺失、共享对象断裂可以被识别为结构问题
3. **后续治理可执行性**：回答不再停在“有问题”，而能推进到“应由谁接、在哪个节点接、交接后保留什么对象”

---

## 当前还缺什么

虽然这条线已经能被串起来，但还缺两层更细的东西：

1. `L3/L4流程 -> 交接点 -> Agent/SOP/Owner` 的系统化映射
2. `Jasper经验库` 中关于边界、owner、自首、协作纪律的治理经验，与 EA 实际交接问题的映射

所以在这页之后，最自然的下一步就是：

- `Jasper经验 -> EA应用映射MOC`

这样可以把 EA 的具体执行问题，接到 Jasper 区的治理经验底座上。
